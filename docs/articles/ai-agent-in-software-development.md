# 别再手写简历筛选标准了：我是怎么把招聘流程写成代码的

去年下半年开始招 AI 后端开发，收到的简历一天比一天多。

问题来了：什么样的人能真正干活？

看多了你会发现，简历里写"熟悉 AI"的人分两种。一种是真的在用 Cursor、Claude Code 这类工具干活，代码写得又快又稳。另一种是网页版 ChatGPT 用户，复制粘贴改半天，最后还不敢上生产。

更麻烦的是 AI 生成简历。有的人确实做过东西，用 AI 润色一下文字；有的人项目经历全是 AI 编的，满篇"赋能""驱动"，细节问三句就露馅。

我不想每次筛简历都重新想一遍这套逻辑。所以我把标准写死了，固化成一个 Claude Code skill，扔给 AI Agent 去执行。

这篇文章就讲这个：怎么把招聘这种"看起来需要人判断"的事情，变成可以让 Agent 自动跑的流程。

## 为什么要用 Agent 做这件事

传统的招聘流程是这样的：

1. HR 收简历
2. 技术负责人看简历，凭感觉筛
3. 筛出来的人进面试
4. 面试时发现不少人根本不符合要求，浪费时间

问题在哪？**标准不够明确，执行不够稳定。**

今天手感好，可能放宽一点；明天累了，可能卡严一点。看到大厂背景就容易放水，看到小公司就容易一刀切。

更要命的是，这套标准只在你脑子里。HR 不知道，其他面试官也不知道。每个人都是凭自己的理解在筛，最后进来的人质量参差不齐。

所以我想的是：**能不能把这套标准写成代码，让 AI Agent 按规则执行？**

不是说 AI 比人聪明，而是说：
- 标准明确了，就不会因为心情好坏产生偏差
- 流程固化了，就可以复用、可以迭代
- 执行交给 Agent，人只需要做最后的判断

这才是 Agent 的价值：**不是替代人的判断，而是把可以标准化的部分自动化掉。**

## 我的实现方案：把筛选标准写成 Skill

具体怎么做？我的方案是写一个 Claude Code skill。

Claude Code 有个 skill 系统，可以让你把一套判断逻辑、执行流程封装成一个技能，然后在对话里直接调用。

我的 skill 叫 `ai-backend-resume-screening`，核心就是把筛选标准拆成几层：

### 第一层：硬门槛（一票否决）

有些东西是底线，碰到就直接淘汰：
- 工龄超过 10 年（太资深的人不适合这个岗位）
- 第一学历专科及以下（这个岗位需要本科起步）
- 年龄超过 30（大厂或强 AI 落地经历可以放宽到 35）

这一层是闸门。过不了就不用往下看了。

### 第二层：能力门槛（必须有证据）

这是从严版的关键变化。我加了两个必过项：

**1. AI coding 工具实证**
不是问"你会用 AI 吗"，而是看简历里有没有提到 Cursor、Claude Code、Codex 这类专业编程工具。

只提 ChatGPT 网页版？淘汰。

为什么这么严？因为用网页版和用专业工具是两回事。网页版用户通常是复制粘贴改代码，效率低，代码质量也不稳定。专业工具用户是真的在用 AI 辅助写代码，提效明显。

**2. SDD/TDD 工程化**
简历里得提到 OpenSpec、Superpowers、spec-kit 这类工具，或者说明白自己怎么用 SDD/TDD 方法论的。

只字未提？淘汰。

这两项必须在简历上有可指认的证据。没写就是没有，不给到面试再问的机会。

### 第三层：加分项（优先级排序）

过了前两层，就看加分项了：

**Agent 应用落地（最高优先，+10 分）**
开发过 AI Agent 应用，而且真的在生产环境跑、有真实用户在用。

注意：Demo 不算，课程项目不算，纯调 API 的聊天页也不算。

复杂度高、规模大的 Agent 应用再加 6 分。

**其他加分项：**
- 金融/电商行业 AI 编程经验
- AI 全栈能力
- 第一学历 211/985/海外名校

这些不是门槛，没有也不淘汰，只是影响排序。

### 第四层：AI 灌水检测

这是最微妙的一层。

现在很多人用 AI 写简历，这本身没问题。问题是有些人用 AI 编造经历。

我的 skill 集成了 `humanizer-zh` 来检测 AI 痕迹，但关键不是"检测到 AI 痕迹就扣分"，而是区分两种情况：

**A 情形：真材实料 + AI 润色**
简历里有具体的系统名、GitHub 链接、精确的指标数据，只是文字被 AI 润色了。

这种人不扣分，甚至可能是打分最高的。

**B 情形：空泛无凭 + AI 灌水**
简历里全是"赋能""驱动""打造""优化"，但没有任何可验证的细节。

这种人扣 12 分，面试时重点核验。

识别的关键是：**AI 痕迹背后有没有硬货。**

### 输出格式

每份简历筛完，输出格式是：

```
dir-name-score-等级
```

等级分三档：初级开发、中级、高级。

不是按分数倒推等级，而是看项目经验：复杂度、独立负责程度、落地深度。

## 代码实现：Skill 的核心结构

一个 Claude Code skill 本质上是一份结构化的 Markdown 文档。

我的 skill 文件结构是这样的：

```
ai-backend-resume-screening/
├── SKILL.md                    # 主文档：流程、原则、输出格式
├── references/
│   ├── screening-criteria.md   # 筛选标准：六层结构、判定逻辑
│   └── ai-writing-integrity-check.md  # AI 灌水检测规则
└── assets/
    └── scoring-rubric.html     # 可交互的评分表
```

`SKILL.md` 开头有 frontmatter：

```markdown
---
name: ai-backend-resume-screening
description: 用于筛选「AI 后端开发工程师」岗位的简历与候选人评估（从严版）
---
```

然后是完整的执行流程，包括：
- 何时使用这个 skill
- 使用流程（分层过滤的顺序）
- 关键判定原则（硬门槛、能力门槛、加分项、AI 灌水检测）
- 输出格式

最关键的是 `references/screening-criteria.md`，这里面是六层筛选结构的详细判定逻辑。

Agent 每次执行时，会先读这份文档，然后按里面的规则一层层过滤。

### 去重机制：避免重复筛选

批量筛简历时，还有个问题：同一个人可能投多次，或者不同批次的简历里有重复。

我的解决方案是用一个本地的 `checked.md` 文件记录已经筛过的简历。

每次筛选前，Agent 会先读这个文件，跳过已经筛过的。筛完新简历后，把结果追加进去。

格式是 Markdown 表格：

```markdown
# 已筛简历记录（checked.md）

| 筛选日期 | 来源文件 | 姓名 | 城市 | score | 等级 | 判定结论 | 美化风险 | 备注 |
|---|---|---|---|---|---|---|---|---|
| 2026-06-15 | AI开发-张三-北京.pdf | 张三 | 北京 | 78 | 中级 | 推荐 | 🟢低 | |
```

这样既能去重，也能当作历史记录查询。

## 实际使用体验

这套系统上线后，我用它筛了几十份简历。

效果出乎意料地好。

**速度快。**
以前一份简历我要看 5-10 分钟，现在 Agent 几秒钟就能给出结论。

**标准稳定。**
不会因为我今天累了就放水，也不会因为看到大厂背景就降低标准。

**可追溯。**
每份简历的判定逻辑都有记录，能看到是在哪一层被筛掉的，或者因为什么加分项排前面。

**可迭代。**
发现标准有问题？改 `screening-criteria.md` 就行，下次执行自动生效。

当然也有一些局限：

**Agent 不能替代最后的判断。**
它能帮你过滤掉明显不符合的人，但最后进不进面试，还是得人来定。

**标准要足够明确。**
如果你的筛选标准本身就模糊，写成代码也没用。这个过程其实是逼着你把标准想清楚。

**需要持续调优。**
一开始的标准不可能完美，要根据实际情况不断调整。

## 从招聘到其他场景：Agent 的通用模式

回头看，这套方案的核心不是招聘，而是一个通用的 Agent 应用模式：

**1. 把判断标准显式化**
不是凭感觉做决策，而是把判断依据一条条列出来。

**2. 分层过滤，逐步收敛**
先过硬门槛，再看能力门槛，最后看加分项。每一层都有明确的判定逻辑。

**3. 可验证，可追溯**
每个决策都要有依据，能回溯到具体的规则。

**4. 人机协作，而非替代**
Agent 负责执行标准化的部分，人负责最后的判断和规则的调整。

这套模式可以用在很多场景：

- **代码审查**：把团队的 code review checklist 固化成 skill，让 Agent 先做第一轮检查
- **需求评审**：把需求文档的必备要素列出来，Agent 检查是否遗漏
- **技术方案评估**：把架构决策的考量因素写成规则，Agent 帮忙做初步分析

关键是：**哪些是可以标准化的，哪些是需要人来判断的。**

标准化的部分交给 Agent，人专注于需要创造性和判断力的部分。

## 技术实现：怎么写一个 Claude Code Skill

如果你也想写类似的 skill，核心步骤是这样的：

### 1. 定义清晰的执行流程

在 `SKILL.md` 里写明：
- 这个 skill 什么时候被触发
- 执行的步骤是什么
- 每一步的判断依据在哪里

例如：

```markdown
## 使用流程

1. **先读筛选标准**：阅读 `references/screening-criteria.md`
2. **按层过滤**：
   - 先看硬门槛
   - 再看能力门槛
   - 再看加分项
3. **给出结论与等级**
```

### 2. 把判断逻辑写成文档

不要把规则硬编码在代码里，而是写成 Markdown 文档放在 `references/` 目录。

Agent 执行时会读这些文档，按里面的规则做判断。

好处是：规则改了，不用动代码，只要改文档就行。

### 3. 提供示例和模板

在 `assets/` 目录里放一些可直接使用的文件，比如评分表、输出模板。

这样 Agent 可以直接复制使用，不用每次都重新生成。

### 4. 处理边界情况

要考虑各种异常情况：
- 简历格式不规范怎么办
- 信息缺失怎么办
- 重复筛选怎么办

在 `SKILL.md` 里把这些情况的处理逻辑写清楚。

### 5. 定义清晰的输出格式

输出要标准化，方便后续处理。

我的方案是用统一的"结论行"格式：

```
dir-name-score-等级
```

这样可以直接用脚本解析，或者导入到其他系统。

## 代码示例：screening-criteria.md 的结构

这是 `screening-criteria.md` 的核心结构（简化版）：

```markdown
# 筛选标准：AI 后端开发工程师

## 第一层：硬门槛

### 工龄
- ≤ 10 年：通过
- > 10 年：一票否决，不可放宽

### 学历
- 第一学历本科及以上：通过
- 第一学历专科及以下：一票否决，不可放宽

### 年龄
- ≤ 30 岁：通过
- > 30 岁：触发放宽机制（需要大厂经历或强 AI 落地）

## 第二层：能力门槛

### AI coding 工具实证
**必须满足**：简历明确提到使用以下工具之一
- Cursor
- Claude Code
- GitHub Copilot
- Codex

**判定依据**：
- 简历中有明确描述：通过（如"使用 Cursor 进行日常开发"）
- 只提 ChatGPT 网页版：淘汰
- 只字未提：淘汰

### SDD/TDD 工程化
**必须满足**：简历提到以下工具或方法论
- OpenSpec / Superpowers / spec-kit
- 或明确说明 SDD/TDD 实践

**判定依据**：
- 有相关工具或方法论描述：通过
- 只字未提：淘汰

## 第三层：加分项

### Agent 应用落地（+10 分）
**最高优先**：开发过 AI Agent 应用且真实落地
- 生产环境运行：+10 分
- 有真实用户使用：+10 分
- 复杂度高、规模大：额外 +6 分

**不得分**：
- 仅 Demo
- 课程项目
- 纯调 API 的聊天页

### 其他加分项
- 金融/电商行业 AI 编程经验：+5 分
- AI 全栈能力：+5 分
- 第一学历 211/985：优先推荐（同等条件排前）

## 判定逻辑

1. 任一硬门槛不通过 → 淘汰
2. 任一能力门槛不通过 → 淘汰
3. 通过全部门槛 → 60 分起评
4. 加上加分项 → 最终得分
5. 得分 > 60 → 推荐
6. 得分 ≤ 60 → 不推荐
```

Agent 读这份文档时，会按顺序执行每一层的判断，最后算出得分和等级。

## 关于 AI 灌水检测：最微妙的部分

这是整个系统里最容易出错的地方。

一开始我想的是：检测到 AI 痕迹就扣分。

结果发现不对。有些打分最高的候选人，简历里 AI 痕迹很重，但项目经历都是真的，只是文字润色过。

真正要过滤的是：**用 AI 编造经历的人。**

所以我改了检测逻辑，不看 AI 痕迹本身，而是看痕迹背后有没有硬货：

**有硬货（A 情形）：**
- 具体的系统名称
- GitHub 链接
- 精确的性能指标
- 可验证的技术细节

这种人不扣分。

**没硬货（B 情形）：**
- 满篇"赋能""驱动""打造"
- 项目描述空泛无凭
- 没有任何可验证的细节

这种人扣 12 分，面试时重点核验。

判断依据写在 `references/ai-writing-integrity-check.md` 里：

```markdown
# AI 灌水 / 简历真实性核验

## 核心原则

**用 AI 写简历不扣分。**
要过滤的是用 AI 编造/夸大经历的候选人。

## 判定流程

1. 使用 `humanizer-zh` 检测 AI 痕迹
2. 根据 AI 痕迹程度和可验证细节，判定为 A 情形或 B 情形

### A 情形：真材实料 + AI 润色
**特征**：
- AI 痕迹重
- 但有充分的可验证硬细节

**硬细节包括**：
- 真实的系统名称（如"XX 支付系统"）
- GitHub 仓库链接
- 精确的性能指标（如"QPS 从 500 提升到 2000"）
- 具体的技术栈（版本号、框架名称）

**处理**：不扣分

### B 情形：空泛无凭 + AI 灌水
**特征**：
- AI 痕迹重
- 空泛无凭，缺乏可验证细节

**常见表现**：
- 满篇"赋能""驱动""打造""优化"
- 项目描述模糊（如"某大型系统"）
- 没有精确指标
- 技术栈描述笼统

**处理**：扣 12 分，面试时重点核验

## 风险分级

- 🟢 低风险：A 情形，可验证细节充分
- 🟡 中风险：介于 A/B 之间，部分细节可验证
- 🔴 高风险：B 情形，空泛无凭

## 双重红旗

美化风险 🔴 高 且"用 AI 写代码"实证单薄、主要靠"做 AI 应用"经历撑简历
→ 可信度极低，降到边缘/淘汰候选
```

这套规则让 Agent 能准确区分"润色"和"灌水"。

**AI 灌水检测**：

- 211 学校：优先推荐

**结论**：强烈推荐

这种简历过所有门槛，加分项充足，AI 灌水风险低。是典型的"真材实料 + AI 润色"。

## 一份被淘汰的简历长什么样

反面案例（脱敏）：

**候选人背景**：

- 2 年工作经验，年龄 26
- 上一份工作在一家小型互联网公司

- 风险：🔴 高

这份简历在能力门槛第一项就被卡住了。即使没有这一条，AI 灌水风险 🔴 高也会让它排到很后面。

## 技术栈选择：为什么用 Claude Code Skill

你可能会问：为什么不用 Python 脚本，或者做个 Web 服务？

我的考虑是：

**1. 灵活性**
规则写在 Markdown 里，改起来比改代码快。不需要重新部署，改完就生效。

**2. 可读性**
非技术人员也能看懂规则，HR 或其他面试官可以直接读 `screening-criteria.md` 了解标准。

**3. 交互性**
Claude Code 的对话界面天然适合这种场景。你可以问"为什么这个人被淘汰"，Agent 会解释判断依据。

**4. 迭代速度**
写一个 skill 比开发一个完整的应用快得多。几个小时就能跑起来，然后根据实际效果快速迭代。

当然，这套方案也有局限：

- 依赖 Claude Code 环境
- 大规模批量处理时效率不如专门的服务
- 无法和其他系统深度集成

但对于个人或小团队的招聘场景，这套方案足够了。

## 延伸思考：Agent 的边界在哪里

做完这个项目，我有一些新的想法。

**Agent 不是用来替代人的，而是用来扩展人的能力的。**

它不能替代我做最后的判断，但能帮我过滤掉明显不符合的人，节省大量时间。

它不能替代我思考招聘标准，但能帮我把标准固化下来，避免执行偏差。

它不能替代面试，但能让我在面试前就对候选人有更清晰的认识。

**关键是找到那条边界：哪些是可以标准化的，哪些是需要人来判断的。**

标准化的部分交给 Agent，人专注于需要创造性和判断力的部分。这才是人机协作的正确姿势。

**另一个发现是：写 Agent 应用的过程，本身就是一次深度思考。**

为了把筛选标准写成代码，我必须把每一条规则都想清楚：
- 什么情况下通过，什么情况下淘汰
- 加分项的权重怎么定
- 边界情况怎么处理

这个过程逼着我把很多"凭感觉"的判断变成明确的规则。

结果是：即使不用 Agent，我自己筛简历的效率也提高了，因为标准更清晰了。

## 写在最后

这篇文章讲的不是"AI 有多强大"，而是"怎么把一个实际问题用 Agent 解决"。

核心不是技术，而是思路：
- 把问题拆解成可以标准化的部分和需要判断的部分
- 标准化的部分写成规则，让 Agent 执行
- 需要判断的部分留给人

这套方法不只适用于招聘，也适用于代码审查、需求评审、技术方案评估等各种场景。
