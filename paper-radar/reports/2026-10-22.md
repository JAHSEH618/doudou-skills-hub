# 当 PyTorch 不再假装只有一种硬件

这两天，四个第一方团队同时把 PyTorch 的活干到了 kernel 层：Google 与 Meta 的 TorchTPU、AMD 的 FlyDSL、IBM 的 Spyre MLIR 后端、Ant Group 与 vLLM 社区的 Humming。PyTorch 前端代码本来就能挪到 TPU、MI350 和 Spyre 上跑，kernel 层长期是"先写 CUDA、再移植别人"的格局。这一轮发布把格局改了：硬件方自己写 kernel，且各选各的方言——JAX 自定义算子、显式 tile 映射、MLIR 数据流调度、统一量化表示内的 JIT 搜索。问题从"能不能跑"变成"kernel 层听谁的方言"。

同期第二条线是 agent 安全边界画在哪里：NVIDIA 把治理放进 BlueField-4 DPU 的硬件信任域，Anthropic 红队用 Claude 审计 25 个开源项目的配置攻击面——一个落在硬件，一个落在配置项，共同前提是把 agent 当"可被劫持"的工作负载。论文侧本期重点是一个判断：harness 优化的收益，pass@1 与 pass@k 看到的是两个东西，聚合分数会掩盖难任务上的覆盖损失。共 8 篇，3 篇全文核验。

## TorchTPU：TPU 拿到一个真正的 PyTorch 后端

- Google 与 Meta 从 2025 年中开始并行开发 TorchTPU，已在 Google 内部生产使用；博客称其支持 Google Cloud 最大规模客户之一。
- 设计要点：eager 执行路径不依赖 JAX 运行时，与 PyTorch/XLA（JAX tracing、图优先）和 TorchAX（JAX 原生执行）的路线分开；运行时代码开源。
- 作者列出的现状：支持 eager 与 compiled 两种模式（含新的 DeferAndFuse eager 模式）；约 450 个 ATen 算子（跳过结构性复合/委托算子），覆盖主流深度学习架构所需的 Core ATen 算子前向与反向；自定义 kernel 可经 JAX/Pallas 或 Helion DSL 编写。
- 验证方式：Hugging Face Hub 下载量前 5000 的模型（LLM、语音、多模态等）开箱验证；CI 管线对 CPU 与 GPU 基线做覆盖、稳定性与数值等价对比，覆盖 v5e 起的 TPU 代际。
- 生态侧：TPU 多主机推理走 vLLM 与 SGLang，训练走 TorchTitan；vLLM 团队另发布了 vllm-torchtpu 后端插件（与 Inferact、Google 合作），复用现有 vLLM 模型代码。
- 作者写明的一项工程取舍：XLA 编译器按 shape 重编译，agent 与混合工作流 shape 动态，他们对可动态的张量维度做了限制（bounded dynamism），把编译开销控制在可预期范围。
- 迁移成本"几行配置"是作者自述，本期无第三方迁移成本数据。

· [来源：Hugging Face Blog · Hugging Face ❤️ TorchTPU（10-20）](https://huggingface.co/blog/hf-torchtpu)
· [来源：vLLM Blog · vLLM TorchTPU（10-20）](https://vllm.ai/blog/2026-10-20-vllm-torchtpu)

## FlyDSL：显式映射的 kernel 进入 PyTorch 算子层

- AMD 首篇 PyTorch 官方博客：用自研 kernel 编译器 FlyDSL 为 MI350（gfx950）写显式算子层，覆盖 dense/grouped GEMM、FMHA、MXFP8/MXFP4 scaled GEMM、RMSNorm、TopK。
- 定位与 Triton 互补：Triton 写 block tensor、布局交给编译器，FlyDSL 写显式 tile/row/mask 映射，编译器只管 tile 分配与屏障。作者自评：算子小时两条路线性能差距小，算子大且映射不明显时显式布局更稳。
- 算子级数据（几何均值，对照基线在原文逐条注明）：BF16 dense GEMM 1.10×（每 shape 取 ATen/Triton 较快者，15 个 shape；15 例中 10 胜 3 平 2 负，±1% 平局带）；MXFP8 1.58×、MXFP4 1.68×（对 ATen，每格式 17 个 shape）；grouped GEMM 1.20×（对 Triton，24 个 shape）。收益集中在中小规模，64×4096×4096 处 1.33×。
- 端到端：vLLM 的 MI355X A/B 测试，whole-request 加速 BF16 1.13×、MXFP8 2.04×、MXFP4 3.01×，原文明说"依赖模型与并发"。
- 同期发布 AOTriton 0.14.2b 的 SDPA kernel：forward 0.92–2.34×、backward 0.93–2.47×（对 0.13b，部分 shape 反而变慢，原文列出）。

· [来源：PyTorch Blog · FlyDSL AMD（10-21）](https://pytorch.org/blog/accelerating-pytorch-on-amd-gpus-with-flydsl/)
· 第一方博客；关键证据 = 第一方 MI355X 数据，对照基线混合（ATen/Triton）且原文注明。

## 从 KTIR 到 SpyreCode：IBM MLIR 数据流后端三部曲的中篇

- IBM 把 Spyre 处理器（32 核环形互连、每核 2MB scratchpad、片外 DRAM；数据以 128 字节 stick 搬运）的 PyTorch 后端拆成三部曲发布，这是中篇：MLIR 数据流后端。上篇是总体架构（Inductor→MLIR→codegen→runtime），下篇是编译器与 codegen。
- KTIR（RFC 0682）：一个开放的"tile 化 MLIR"方言，作为 Inductor 与后端之间的契约——Inductor 生成 KTIR，后端做 lower 与调度，再 lower 到目标运行时（此处为 SpyreRuntime）。
- 数据流模式由硬件模型决定：load（scratchpad→寄存器）→ compute → store，kernel 以 32 核环为一个并行区编译。
- Dataflow Scheduler 开源（Apache-2.0，含其 MLIR 方言）：单条 load/compute/store 流水线被展开为嵌套、double-buffered、多实例的调度树，内层循环持有缓冲乒乓与级间同步；输出表示为 DataflowIR， Spyre 的设备级 codegen 从 DataflowIR 边界开始。作者称同一条编译路径（torchinductor→KTIR→Dataflow Scheduler→DataflowIR）可复用到其他数据流硬件。
- 本篇与下篇的边界对象是 SpyreCode：一份"1 个 SpyreBinary + 1 个 job plan"的符号表示，设备分配、内存分配、kernel 启动顺序一次准备、多次启动。
- 本篇不涉及：数值精度与稳定性验证（上篇）、性能优化（下篇）。

· [来源：PyTorch Blog · From KTIR to SpyreCode（10-20）](https://pytorch.org/blog/from-ktir-to-spyrecode-an-mlir-dataflow-backend-for-ibm-spyre/)
· 第一方博客；三部曲第 2/3 篇，无性能数据。

## Humming：量化 kernel 的统一表示

- Ant Group 与 vLLM 社区开源 Humming（github.com/vllm-project/humming）：量化推理 kernel 库，支持 NVIDIA Turing 起（T4/V100/A100/H200/B300 等）及 T-Head 真武 810E 等 CUDA 兼容设备。
- 核心思路是统一量化表示：WNA16/W8A8/W4A8/W4A4 等格式统一拆成"dequant → matmul"两段，数据类型（INT4/FP8/NVFP4）与硬件代解耦——dequant 逻辑复用，matmul 按代更换。
- 配置分三层：Layer（逐通道 group size、权重/激活格式）、Compute（精度与量化/反量化路径）、Tuning（JIT 搜索空间，结果按设备缓存，避免重复搜索）。
- 性能（均为第一方自报，对照基线逐条注明）：dense W4A16 在多数测试配置上追平或超过 vLLM Marlin；小 batch 时在若干设备上达到 cuBLAS 基线的约 3–4×；大 batch H200 约 2× Marlin，部分 B300 配置 3× 以上；MoE 提供 Indexed 与 Grouped 两条路径。
- 作者总体声明："显著快于 vLLM Marlin、FlashInfer、DeepGEMM 的现有实现（在许多代表性负载上）"——定性表述，正文未给 W4A8-MXFP4 在 Hopper 上的绝对数字。
- 810E：原文称"fully supports"（功能级）；正文 benchmark 图全部是 NVIDIA 卡，未给 810E 性能数据。

· [来源：vLLM Blog · Humming（10-21）](https://vllm.ai/blog/2026-10-21-humming)
· 第一方博客；关键证据 = 第一方多卡 benchmark，无第三方复现。

## VocabX：把词表按 token 成本专项化，推理成本降 77%

- Dharma-AI（运行葡语作文自动批改服务的团队）发布 VocabX：不动模型权重与训练配方，只重调词表，在生产 SLM（基于 Qwen3-4B 的葡语作文批改器）上实测推理成本降 77%（博客标题数字，原文按"measured inference cost"表述）。
- 起点是两种浪费：碎片化——批改反馈里的领域套话被切成很多 token，模型逐个生成，推理成本与生成 token 数成正比；冗余——词表 151,669 项，每个生成 token 都要对全词表打分，其中大量条目对该任务几乎无用。
- 成本模型：生成阶段要反复读权重与随上下文增长的 KV cache；他们测的配置里一个生成 token 的成本是一个读入 token 的 7.4 倍，作者注这个比值随硬件、任务、batch、上下文长度变化。"少写 token"因此是直接的钱。
- 方法：按"每个 token 的成本"而非频率重调词表——哪些子串合并后省下最多 decode 成本，就把哪些合并进新词表，部署在同一基座模型上。
- 边界：77% 是作者自己生产系统的测量，论文在审（未公开）；方法对其他领域的迁移性未验证，作者只做了葡语批改一个场景。
- 本期池子里另一个侧面："Cache Engineering for Agents"（2610.28577）主张 agent 轨迹的主导成本是 KV cache 的 I/O 与存储，任何前缀修改使缓存失效——一个算"写了多少 token"，一个算"留了多长上下文"，同指一件事：成本由 token 的写与留决定。

· [来源：Hugging Face Blog · VocabX（10-21）](https://huggingface.co/blog/Dharma-AI/vocabx-vocabulary-specialization)
· 第一方博客；关键证据 = 第一方生产系统测量，论文在审未公开。

## Sentry：agent 的边界画进硬件信任域

- NVIDIA 在 GTC Berlin 发布 Sentry 安全层（10-21）：把 agent 当"可被劫持或漂移"的工作负载，访问策略在 BlueField-4 DPU 的硬件隔离信任域里执行，与宿主软件无关。
- 两个组件：DOCA Tower 是透明代理，终结 TLS、按 Open Policy Agent 规则评估每个 agent 请求；DOCA Argus 对 agent 执行环境做实时内存内省。两者关联：网络层请求与运行时状态合并做策略决定。
- 执行路径：in-silicon、毫秒级遏制，不依赖宿主 OS 配合；AI 分类器用于检测行为漂移。
- 遥测：attested telemetry 与 tamper-evident 记录保存在 BlueField-4 上，支持取证与企业安全平台集成。
- OpenShell 是对应的开源运行时（10-20 开发者博客）：把 agent 工作负载按不可信处理，Gateway、Supervisor、Sandbox、Policy Prover 四个组件分别管沙箱生命周期、凭证中介、负载隔离、策略权限的形式化验证。Sentry 是同一参考架构里的硬件隔离层。
- 边界：DPU 专属架构（BlueField-4），发布帖未给检测率或性能开销的量化数据。

· [来源：NVIDIA Developer Blog · Sentry（10-21）](https://developer.nvidia.com/blog/inside-nvidia-sentry-secure-ai-agents-at-runtime/)
· [来源：NVIDIA Developer Blog · OpenShell 参考架构（10-20）](https://developer.nvidia.com/blog/how-nvidia-openshell-reference-architecture-secures-and-governs-ai-agent-workloads-at-scale/)
· 第一方博客；关键证据 = 第一方架构声明，无量化评测。

## 论文

### Elicitation or Expansion：harness 优化到底优化出了什么 ·【全文】【软件系统】

FuriosaAI + 延世大学 + UC Berkeley。[arXiv 2610.27889](https://arxiv.org/abs/2610.27889)（10-20，代码：[furiosa-ai/elicitation-or-expansion](https://github.com/furiosa-ai/elicitation-or-expansion)）

- 问题：冻结模型权重、只优化 harness（提示词、控制流、工具配置）有时能超过更大模型，这个收益到底是什么？作者把指标拆开回答：pass@1 是期望成功率，pass@k（k 至 128）是 k 次里至少解对一次的概率，两者度量不同，聚合的 pass@1 会好看得误导人。
- 方法：Meta-Harness 优化器对每个任务集生成 40+ 个 harness 候选；300 个 HotpotQA 任务各跑 128 次；优化后的 harness H\* 与基础 harness H0、更强参照（更大基座或更高推理预算的同系模型）对比。
- 三个核心结果：
  1. LawBench 上，优化后的 GPT-OSS-20B harness 在 pass@1 超过 GPT-OSS-120B 基线 +16.05pp，到 pass@64 翻转为 -4.00pp。
  2. HotpotQA + AppWorld 上，聚合值接近或超过更强参照，但难子集上 40 个候选全部低于 Qwen3-32B 基线——"超过大模型"的收益来自易子集。
  3. pass@1 最好的 harness 与观察到 pass@128 最好的 harness 不是同一个——按 pass@1 选择，可能选出一个易任务占优、难任务更差的 harness。
- OOD 迁移更负面：一个文本分类 harness 在两个域外数据集上有小幅 pass@1 改善，pass@64 上全部低于基线。
- 含义：对以解出难任务为目标的场景（递归自我改进、进化搜索），选择指标应该看难子集覆盖（pass@k）；论文给出对应诊断法。
- 自报边界：基线全部是作者自己重跑，优化管线是作者自己的 Meta-Harness，4 个模型（GPT-OSS-20B/120B、Qwen3-8B/32B）与任务集均为自选。

### KV-Surgeon：删一个 key，所有 key 的 attention 都变 ·【全文】【软件系统】

ZIB + TU Berlin。[arXiv 2610.25933](https://arxiv.org/abs/2610.25933)（10-19，代码：[ZIB-IOL/KV-Surgeon](https://github.com/ZIB-IOL/KV-Surgeon)）

- 问题：KIVI 式"top-m 打分 + 独立删除"的 KV 压实里有一个耦合，作者用 Lemma 指出：softmax 重归一化使所有删除决策互相耦合——删掉任何一个 key，其余 key 的 attention 权重都变，独立打分等价于优化一个已经变形的目标。
- 方法：两个机制。ZIB（zero-impact bound）给出"不超出误差预算最多可删多少 key"的闭式界；TUB（tunable upper bound）把误差预算变成可调代价函数。两者交替使用，压实离线完成（serving 前，非 serving 中）。
- 实验设计（正文可查）：50×/100× 压缩，QuALITY、LongHealth、Long Code Arena 三个基准，4B–30B 稠密与 MoE 模型，5 个种子；SOTA 对照是 attention matching（Zweiger et al. 2026，按 attention 权重保留 key 的方法）。
- 结果：50× 处比 attention matching 最高高 4 个点（Table 17）；fast 版本以 2/5 的代价拿到大部分收益。作者写明方法面向离线压实场景，在线 serving 路径是另一个问题。
- 论文最诚实的部分：专节警告 Lemma 的混合服务陷阱——混合负载（不同请求共享层）下 zero-impact 界的假设被削弱。
- 第三方解说（zot.news）已找到，按规则不收（自动聚合站），仅内部记录。

### Token-Set Choice Confounds POPE ·【全文】【评测】

Sri Krishna College of Technology + Sri Eshwar。[arXiv 2610.25964](https://arxiv.org/abs/2610.25964)（10-19，作者研究仓库：[Kesav2k04/ugaa-research](https://github.com/Kesav2k04/ugaa-research)）

- 问题：POPE 系 VLM 幻觉基准的抽取环节——跑模型、在输出里找第一个 yes/no token、映射成 0/1——有一个作者指出的缺陷：抽取代码里的 yes/no token 集合与模型实际输出的 token 可能不匹配，测量结果依赖管线参数。
- 方法：先核查词表里有哪些 yes/no token ID，再对模型真实输出跑抽取管线、统计不匹配。论文含一个具体复现：LLaVA-1.5-7B、4-bit NF4 量化、9k POPE 题。
- 结果：token 集合选择"confounds"幻觉率测量；9 种推理时修正尝试全部未能解决，论文逐一列出每种失败的原因。
- 含义：跨论文比较幻觉率时应核对抽取代码的 token 集合——这是管线参数，不是模型属性。
- 自报边界：单一模型系（LLaVA-1.5）、9k 题；"9 种修正失败"为作者自列，无独立验证。

### 摘要五条

- **Tandem: Serving Hybrid Linear-Attention GUI Agents on Mobile NPUs** · [2610.26660](https://arxiv.org/abs/2610.26660) ·【摘要级】【硬件/agent】：混合线性注意力 GUI agent 在移动 NPU 上的 serving——agent 请求的长指令不变、每轮只更新近期历史，关键设计是循环状态的 checkpoint 策略（在哪些步保存/恢复状态），平衡 NPU 内存约束与重算代价。
- **Conjugate Compilation: Self-Improving Agentic Co-Compilation for Speculative Decoding** · [2610.25012](https://arxiv.org/abs/2610.25012) ·【摘要级】【软件系统】：把 draft 模型与 target 模型"共轭"编译——agentic 编译器搜索 draft/target 的编译参数组合，以接受率为反馈迭代调参，面向同芯片投机解码。
- **PACT: NVFP4 Data-Flow LoRA Fine-Tuning on Consumer GPUs** · [2610.25048](https://arxiv.org/abs/2610.25048) ·【摘要级】【训练/量化】：在消费级 GPU 上以 NVFP4 数据流 GEMM 做 LoRA 微调，把微调精度从 BF16 降到 NVFP4，针对消费卡显存瓶颈。
- **Cache Engineering for Agents** · [2610.28577](https://arxiv.org/abs/2610.28577) ·【摘要级】【agent/serving】：agent 轨迹的主导成本是 KV cache 的 I/O 与存储而非计算；核心问题是任何前缀修改使缓存失效，论文提出沿轨迹的缓存维护策略（哪些留、哪些重算）。
- **A Hybrid GPU and Processing-Near-Memory Architecture with Shared DRAM** · [2610.26131](https://arxiv.org/abs/2610.26131) ·【摘要级】【硬件/serving】：prefill 与 decode 分置 GPU 与 PNM（processing-near-memory）硬件、共享 DRAM，KV cache 不重复搬运，针对"prefill 计算受限、decode 内存受限"的失衡。

## Anthropic 红队：Claude 审计 25 个开源项目的配置攻击面

【短条目 / 第一方博客】

- 方法：让 Claude 用三种方法审计 25 个开源项目（500 万+ 行代码，C/C++/Java/PHP/Python）——默认配置下可达但无任何默认功能使用的代码；单独看合理、组合起来静默削弱安全的配置对；在认证或协议状态转换之前运行的复杂安全敏感代码。
- 结果：493 个问题；清点 17,000+ 配置项，其中 3,842 项与安全相关。11 个 Gated 项目全部存在非预期可达代码：93 个预认证攻击面、37 处认证前执行代码或写入状态、61 个静默削弱管理员预认证控制的配置组合。
- 最具体的一类：162 个安全敏感配置组合被静默接受（无报错、无警告、无文档），其中 94 个静默关闭安全控制，其余 68 个是控制不一致（配置声称禁用、监听器仍可达之类）。一个 "deny 规则写主机名模式 + 反向 DNS 关闭 → 永远不命中 → fail open" 的模式在 4 个互不相关的项目中独立出现；一对冲突配置静默丢弃证书检查，在同一软件里存在了 21 年。
- OpenSSH 案例：10.4 中约 4,500 行 ML-DSA-44（后量子签名）代码在默认配置下可被未认证客户端到达，约占默认 sshd 预认证代码的 16%；ML-DSA 默认不启用、管理员显式排除后代码仍可达（先解析、后检查白名单）。Anthropic 带补丁报告，10.5 把检查移到解析前，Claude 又找出两个绕过（客户端声称的密钥类型与实际发送不一致；证书 CA 签名路径不受配置清单控制）；最终修复放在解析器内部，10.6 发布移除约 1/5 的预认证可达代码。OpenSSH 10.6 release notes（10-06 发布）公开致谢 Chris Rohlf "in collaboration with Claude and Anthropic Research"。
- 工程化：三种方法合成了一个可复用 Claude skill（三遍扫描、每遍空上下文起步、每个发现用动态 trace 确认、默认配置的门控必须让项目自身测试套件结果不变），正并入 OSS-Scanner。
- 边界：493 个发现是红队自己的审计预览（单一厂商数字，无独立复现）；各问题的修复状态未公布，OpenSSH 是唯一可外部对照修复版本的案例。
