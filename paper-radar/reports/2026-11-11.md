# 一致性决定上限

论文标题里那些倍率和百分比是不是真的？本期 8 篇论文、14 条工程实践的回答集中在一个词上：一致性。内核一致性（rollout 引擎和训练引擎跑的是不是同一条代码路径）、数值一致性（FP4/FP8 的误差有没有被集中处理）、上下文一致性（KV cache 里 token 的旋转位置、检索层放进上下文的边界）——一个系统的上限，由它没对齐的那一层决定。（AIHot 只覆盖近 7 天，本期前两天的资讯以 HN 高分帖与网页搜索渠道为准。）

全文 3 篇、摘要级 5 篇。全文里，FourSight（arXiv 2611.04887）说明低比特强化学习的失败集中在少数离群序列和高方差通道，过滤加补偿可以处理；PACE（arXiv 2611.10240）说明 2,048 token 的 KV 预算即使 99.6% 命中也会掉到 64%，因为旋转位置距离在涨；SLA（arXiv 2611.06828）说明 TPU 上 1.6–2.5× 的线性注意力加速完全来自 kernel 与硬件的联合设计。工程实践 6 详 8 简，资讯 8 条，快讯 8 条。

## 对齐 rollout 与训练：失配有预算

**【论文，摘要级】** [How Much Training-Inference Mismatch Can On-Policy Distillation Tolerate?](https://arxiv.org/abs/2611.11450)（arXiv 2611.11450，v1 提交 2026-11-08，Tuo Shi 团队，NVIDIA 系）。on-policy 蒸馏（OPD）在教师模型的逐 token 引导下生成自己的响应，rollout 开销大，于是系统普遍用量化推理和异步 rollout 压成本。两者都带来 rollout 引擎与训练模型之间的训练-推理失配（TIM）。强化学习对失配的敏感早有共识，OPD 能容忍多少此前没有实测。这篇论文把所有失配来源放在同一尺度上量：三组 student-teacher 量化配置，加一组权重过时与噪声注入。结论是一个可操作的「失配预算」：OPD 能容忍相当大的失配而不损失多少训练质量，只在更高失配水平上退化；在会拖垮强化学习设置的失配下，OPD 保持稳定。机制上还有一个细节：权重噪声下的失配会改变模型生成时到达的前缀，这类错误无法靠逐 token 修正补救，因为前缀已经走偏了。论文还给了一个轻量准入检查：不必为每个 rollout 设置跑完整训练，就能对照校准好的预算筛查。工程侧，一个模型特定的 FP8 配方在保住训练质量的同时拿到 BF16 之上至少 1.93× 的 KV cache 容量；FP8 加异步 rollout 比同步 BF16 快 1.62× 达到同等训练质量。代码：[benyucong/train-inference-mismatch-opd](https://github.com/benyucong/train-inference-mismatch-opd)。

这篇论文的结论与 vLLM 侧的 REINFORCE Zero（工程实践详条目）从两头对上：REINFORCE Zero 的答案是把核对齐后异步 RL 稳定在 20,000 更新、训练步吞吐 2.40×；TIM 的答案是不完全对齐时，只要落在预算内损失可控，而且预算可以提前量出来。Artificial Analysis 对 DeepSeek V4.1 Flash 在 GB300 上的独立复测（见 X 讨论）给同方向补了一个外部参照。三个来源指向同一条判断：失配是训练系统的一级工程变量，不是二阶修正项。

## 低比特训练：误差不是均匀的

**【论文，全文】** [FourSight: Stable FP4 RL Post-Training via Sequence Filtering and Sparse Channel Compensation](https://arxiv.org/abs/2611.04887)（arXiv 2611.04887，v1 提交 2026-11-03）。NVFP4（W4A4）已经是低比特部署的通用格式，但把它放进强化学习后训练会出两个问题：rollout 质量下降，跨引擎的训练-推理失配被放大，训练不稳定。全文里撑起整个方法的是一个观察：失败不是均匀分布的。失配严重的尾 token 集中在少数离群序列上；策略权重本身大体完好；量化误差集中在少数高方差激活通道上。FourSight 的协同设计就是对着这个集中性做的：TIM 感知的序列过滤，把漂移的轨迹从策略更新里排除；稀疏精度补偿，只让方差最高的通道留在 BF16，其余保持原生 NVFP4；配套一个 SpliceGEMM 融合 kernel，prefill 与 decode 各有一条专用路径来压开销。结果是跨模型、跨引擎精度贴近 BF16，FP4 部署质量好，step-to-accuracy 提升 1.76–2.60×，到 120B 规模为止步时不超过纯 FP4 的 2.3%。这篇走了全文验证：结论的适用条件就是「误差是集中的」，如果某个模型的量化误差分布广，补偿面会扩大，收益相应缩水。解说：一条第三方人写解读（2026-11-05，[liuzhao09.github.io](https://liuzhao09.github.io/papers/foursight-fp4-rl.html)）解释了两个机制的动机与设计，可作导读，解说者观点。

**【论文，摘要级】** [BitDecoding-FP4: Native FP4 KV Cache Decoding via Algorithm-System Co-Design](https://arxiv.org/abs/2611.09825)（arXiv 2611.09825，v1 提交 2026-11-06，团队含 vLLM 核心成员 Guangming Sheng）。同一个直觉用在另一层：FP4 KV cache 的差距在算法量化与系统加速两边都有。常规量化精度掉得厉害，而追求精度的 4-bit 算法靠查表向量化，拖垮 decode 吞吐。BitDecoding-FP4 处理三个误差源：Dual-Residual Query 量化把查询拆成两个 FP4 张量，查询 logit 误差从 60% 降到 1%；Underflow-Aware 概率缩放防止长上下文概率在 E4M3 scale 下被舍进零；Outlier-Aware Key 量化用静态平滑加 Hadamard 旋转加 scale 搜索压 key 的离群值。系统侧用转置 softmax、融合概率量化与 paged KV 上的 stacked query MMA 把 softmax 瓶颈拿掉。效果：NVFP4 下精度在 BF16 KV 以内 0.5 分（MXFP4 为 1 分），强化学习 rollout 与 BF16 KV 保持一致；NVIDIA B300 上 Qwen3-4B 与 Qwen3-30B-A3B 的峰值 serving 吞吐是 BF16 KV 的 2.4–3.0×。代码：[OpenBitSys/BitDecoding-FP4](https://github.com/OpenBitSys/BitDecoding-FP4)。

两篇放在一起，判断是一致的：4-bit 的误差可以压进少数位置（离群序列、高方差通道、key 离群值），然后显式补偿。2.4–3.0× 这个数字绑在 B300 与两个 Qwen3 模型上，适用边界就是硬件。服务侧还有一条第一方参照：Zyphra 的研究页（2026-11-04）给 AMD MI355X（CDNA4/gfx950，head dim 128 与 DeepSeek-V2 MLA head 形状）的 FP8 因果 prefill attention kernel 做了第一方测量，[原文](https://www.zyphra.com/our-work/zyfa)。

## 2,048 的 cache 预算：留着不够

**【论文，全文】** [PACE: Keeping the Right Tokens in the KV Cache Is Not Enough for Long-Horizon LLM Agents](https://arxiv.org/abs/2611.10240)（arXiv 2611.10240，v1 提交 2026-11-06，Suman Chatterjee，Amazon Web Services）。长程智能体会话到上百万 token，KV cache 超出单卡容量，serving 系统留一小部分预算内的 token，其余驱逐。现有驱逐方法的区别在留哪些 token，但目标一致：后面要用的 token 还留在 cache 里。全文的结果推翻了这个目标：Qwen3-8B、100K token 的编码会话、2,048 token 预算（占会话 2%），一个 planner 引导的策略让 99.6% 的被需要 token 常驻，但同一 token 的定义与使用之间隔 2K 还是 90K 时，精度从 93% 掉到 64%。token 在 cache 里，读不出来：涨的是它们离查询的旋转位置距离。PACE 的两个组件：plan-aware retention，让智能体的 planner 告诉 cache 哪些上下文未来步骤会读；bounded positions，把留下的 token 重新编号，让查询的旋转距离在任何会话长度下都不超过约 8K。预注册的新任务评测里，100K token 时 PACE 通过 97% 的隐藏单元测试，H2O 42%，SnapKV 3%，同一预算；两个组件缺一不可，单用任一 63%（p < 10⁻⁴）。长度外推：1M 与 2M token 会话，单张 24 GB GPU，定义在使用前 0.9M/1.8M token 处，PACE 通过 99% 与 100%；同样条件下只用 bounded positions 不做预判的策略从 33% 掉到 13%。常驻状态是预算 0.30 GB 加引用存储 0.30 GB，不随会话长度增长（完整 cache 在 100K 时要 14.7 GB，1M 时要 147 GB）；重新编号是精确的，无可测的困惑度代价，wall time +9%。Mistral-7B 上不做驱逐的编码上限本身只有 40%，PACE 保住这个上限，只 retention 会掉下去。这篇对判断的补充：agent 记忆与上下文管理这条线上，「留什么」与「放哪里」是两个独立变量，现有驱逐文献大多只处理第一个。

对读的两条 X 原帖（见 X 讨论）指向同一方向：OpenBMB 让 MiniCPM 离线整理智能体记忆，ARC Prize 的 Alexis Fox 讲长程智能体的程序化记忆。

## 检索层：攻击面与快路径

**【论文，摘要级】** [Reliability Stress Testing of RAG Retrieval under Query-Relevant Corpus Poisoning](https://arxiv.org/abs/2611.04264)（arXiv 2611.04264，v1 提交 2026-11-03，Google）。外部文本要影响 RAG 系统，第一步是检索器把它放进模型上下文。这篇论文压测的就是这一步：623 个 BEIR 查询（SciFact 与 NFCorpus），变体包括文档内容、攻击者掌握的查询信息、每个目标文档的投毒预算、污染范围。主要结果：每个查询 5 个定向投毒文档（P=5，语料库占比 0.10%–0.14%），经典检索器在隔离目标设定下 nDCG@10 掉 40.2–61.5%。BM25 的大部分损失由全查询锚定解释：投毒文档把用户查询原样重复一遍就够。稠密检索器 BGE-small 上，只带查询（P=5）就达到 100% 目标暴露，加攻击 payload 对 nDCG 几乎无影响（0.269 到 0.271），检索侧的主导因素是查询本身。查询长度会改变部分信息攻击：162 条长 SciFact 查询上，随机 2 个词（只覆盖合格词的 19.9%）就能让 Hybrid 有 39.5% 目标暴露，4 个词到 89.5%。防御侧：基于重叠的准入可以挡全查询投毒，但干净检索效用掉得明显；测试的 MMR 重排设置下不改变暴露。论文明确只测检索层失效，不测下游指令遵循。这条结论与判断账本里「持久化存储是安全边界」的方向一致：防线要放在写入准入与检索边界上，检索侧的重排不是防御。X 讨论里有 rohanpaul 的对应原帖（11-05）作导读。

本期检索层优化方向的工程条目在工程实践详条目里（Apple MIPS：学习型支撑函数，128 簇 NQ 上路由召回 95% 时比质心路由快 1.9×）。

## 效率数字从哪来

**【论文，摘要级】** [Twice as Fast, Until It Isn't: Quantized Serving of Mid-Size Open LLMs](https://arxiv.org/abs/2611.04380)（arXiv 2611.04380，v1 提交 2026-11-03）。在 vLLM 或 SGLang 上 serving 9B–20B 开放权重模型，需要两个数字：相对 BF16 的加速和付出的精度代价。这篇把公开测量整理成账，发现记录是碎的：只有 2 个检查点（都是 Gemma 3 12B 的 INT4）同时有 vLLM 计时和精度分，且那个精度分只覆盖 MMLU 单一科目（AWQ 的校准科目）；batch-1 的计时早于当前引擎版本发布；AMD 与 Intel Gaudi 在这个参数段没有测量；FP4 对 BF16 的测量没有。现有计时遵循一条规律：小 batch decode 受内存带宽限制，4-bit 权重大约翻倍（Qwen2.5-14B 在 A100 上 2.12×）；batch 大了 GPU 变计算受限，收益消失（Gemma 3 12B 在 batch 256 下 1.02×），那时唯一还有效的配方是 FP8。多数已发表的精度差异在基准采样噪声以内，包括所有 HumanEval 差异。论文最后给一份 7 项报告清单。这是一篇审计不是方法，价值是给了一个读厂商标量时的检查表：哪个 batch、哪个引擎版本、哪套精度集。

**【论文，摘要级】** [Unpacking the Compute Efficiency of Strong-to-Weak OPD against GRPO](https://arxiv.org/abs/2611.08453)（arXiv 2611.08453，v1 提交 2026-11-05，Salesforce）。on-policy 蒸馏的密集信号能不能省掉达到目标精度所需的训练 FLOPs？论文系统对比 vanilla 反向 KL OPD 与 GRPO，变量包括任务难度、student-teacher 规模、领域、优化选择，度量是 held-out 精度对训练 FLOPs。结论两段：外部后训练教师配 OPD 在每 FLOP 精度上普遍输给 GRPO（教师再用 GRPO 训练也一样），且常带回复长度膨胀；教师换成 student 自己的 GRPO 检查点时局面反转，OPD 在数学域上用 1/50 的蒸馏 FLOP 恢复该检查点的精度，这个高效率在大 student、代码域和第二个模型族上保持。单域场景里 GRPO 检查点本身就是目标模型，蒸馏它只多花算力；跨域没有单检查点覆盖所有域。多教师 OPD（沿 DeepSeek-AI 2026 的设置）把按域 GRPO 训练的专家并进一个 student，蒸馏阶段只用专家训练 FLOPs 的 5.2%（2 域）或 8.0%（4 域）；连专家训练一起算，2 域混合上以少 42.0% 的总 FLOPs 达到联合 GRPO 的精度。X 讨论里有 rohanpaul 的对应原帖（11-08）作导读。

## TPU 线性注意力：一个 kernel 问题

**【论文，全文】** [Systolic Linear Attention: Co-Designing Tile-Grouped Gated Delta Attention for TPUs](https://arxiv.org/abs/2611.06828)（arXiv 2611.06828，v1 提交 2026-11-04）。GDN、KDA、GDN-2 这类门控 delta 线性注意力都是为 GPU 调的：小 tensor core tile 加快向量寄存器，逐通道衰减 rescale 与块内串行求解都便宜。Google TPU 相反，算力集中在 256×256 的 systolic 矩阵单元，向量单元相对慢，直接搬过去每个矩阵 tile 一半闲置，瓶颈在向量操作。SLA 把门控 delta 注意力围绕矩阵单元重新组织：key 加宽到 256 用分组 value 头，衰减门按 4 个 64 通道 tile 分组，chunk 求解全部用块矩阵乘，单一融合 kernel 完成。TPU v7x 上完整 SLA-R4 层比开源的 Tokamax KDA kernel 快 1.6–2.5×（精确块求逆设定下 1.4–2.4×），收益主要来自头共享与 kernel 融合。预训练侧：2,048 块 TPU v7x 上 6.5B 到 63.1B 的稀疏 MoE，SLA 比 KDA 快 11–24%，困惑度相当，小样本匹配 seed 下略低。全文验证后需要说明的边界：数字绑 TPU v7x 与 Tokamax 基线，同一层在 GPU 上没有这里的对照。与 Kimi K3.1 Pro 的 KDA 混合稀疏注意力（vLLM day-0，工程实践简条目）和 Muse Spark Open 在 TPU v7 上 62 层 decode/verify 融合 Pallas megakernel（PyTorch 博客，简条目）对读，本期同一判断：线性注意力与 MoE 的效率是实现问题，同一架构在不同硬件上上限不同。

## 工程实践

**【一方博客，详】** [Zero Mismatch, Simple Async RL: REINFORCE Zero, DeepSeek-V4.1 and Kimi K3.1](https://vllm.ai/blog/2026-11-06-zero-mismatch-async-rl)（vLLM 博客，2026-11-06；方法出自 NVIDIA Research 与 Inferact，Jian Hu 等 10 人）。异步 RL 快，但训练用的是别处生成、可能已经变质的样本。REINFORCE Zero 的做法是让 rollout 与训练核完全对齐，这样未截断的 token 级重要性采样权重就是精确的，异步训练退化成标准的 REINFORCE 更新。失配诊断 D3（逐更新对 token 求平均的 w − 1 − log w，w 为重要性权重）在标准核下达到中位水平的 442.54×，对齐后 1.50×；不对齐时 rollout 到 learner 的 KL 中位在前 1,000 更新里涨 83.33×，在线 AIME24 pass@1 从 34.27% 掉到 13.96%，最大梯度范数 38.27 对 0.0555。方法侧论文（[Inferact/zero-mismatch-rl](https://github.com/Inferact/zero-mismatch-rl)，GitHub，不在 arXiv）报告：20,000 更新稳定，policy lag 64 下可学习，12K 更新 16 GPU 上训练步吞吐是同步的 2.40×（68.55h 对 164.77h）。博客侧：DeepSeek-V4.1-Flash 的 DAPO rollout 步与快速基线差 10% 以内；AMD MI355X 上 DeepSeek-V4-Flash 36 个 GRPO 步 diff 为 0（4 节点×8 MI355X，含 resume），Kimi K3.1 的 GB300 设置（LoRA r32、冻结 MXFP4 base）在 2 节点×8 MI355X 上 token 级 diff 为 0，靠两处修复（hipBLASLt 在 4096/4097 行下的 tile 选择，以及去重）。对齐核的代价在服务侧：OSWorld 平均步 944.25s 对 884.17s（+6.8%），batch 不变的优化把 serving 吞吐损失从 62–66% 压到 7.4–10.1%（[配方 verl#8505](https://github.com/verl-project/verl/pull/8505)）。来源核验：第一方（vLLM 官方博客，方法论文在 NVIDIA Research 的 GitHub 仓库）；数字可验证（具体小时数、GPU 数、更新数、代码仓库公开）；版本绑定（vLLM 博客 2026-11-06，博客内给出所用版本与配方链接）；营销动机（官方发布，但 Artificial Analysis 的独立 GB300 复测见 X 讨论，第三方数据同方向，互证）。

**【一方博客+论文，详】** [Faster Retrieval for Better, More Efficient RAG](https://machinelearning.apple.com/research/faster-retrieval)（Apple Machine Learning Research 博客，2026-11-05；ICML 2026 论文，arXiv 2603.08001）。MIPS（最大内积检索）是推荐、搜索与 RAG 检索的核心子程序：每个查询找数据库里最匹配的向量。常规做法把 key 分簇，查询与各簇质心匹配，路由到候选簇。Apple 的方案：离线为固定数据库训练一个小网络（amortization），推理时网络直接把查询路由到最佳匹配。两种网络：SupportNet 直接学支撑函数（ICNN，与问题的凸结构数学一致），为每个数据簇学一个支撑函数，提高路由质量；KeyNet 直接输出最佳匹配的 key 向量，用基于欧拉齐次函数定理的一致性损失保持预测的几何可信，可当标准 IVF 索引前的「查询改写器」。评测：Natural Questions（约 260 万 passage）分 128 簇，SupportNet 从 XS 到 L 四个尺寸（数据库的 1%–20%）。小 SupportNet 在 1.9× 速度下达到 95% 路由召回（1.74 ms 对 3.36 ms），大模型 1.74 ms 到 97%。代码：[apple/ml-amips](https://github.com/apple/ml-amips)。来源核验：第一方（Apple 官方博客加 ICML 2026 论文双出处）；数字可验证（召回、延迟、簇数，代码公开）；版本绑定为论文实验设定（NQ 128 簇）；营销动机（官方，但论文经同行评审、代码开源，数字可复现）。
