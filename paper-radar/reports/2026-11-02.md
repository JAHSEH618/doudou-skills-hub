# 数字只在它测的那个点上成立

一篇论文标题写「2× 更快」，一个模型厂商博客写「近无损」，这个数字到底在什么条件下成立？本期 8 篇论文和 7 条工程实践给出的答案高度一致：强绑定。绑在具体卡型（Hopper 还是 Blackwell）、具体 batch 分布（1 还是 64）、具体注意力后端（fused 还是 unfused）、具体稀疏结构（dense 还是细粒度 MoE）上。标题上那个倍数是点，不是面。把绑定条件换掉，它可能变成 0.9×，甚至是能耗负收益。

本期三篇全文、五篇摘要级。全文里：MoE 投机解码（arXiv 2610.38981）在细粒度 MoE 上推翻「加速随 batch 凹」的旧直觉；FP8（arXiv 2610.39415）证明 FP8 checkpoint 的「通过精度测试」不是「可移植」；dLLM 调度（arXiv 2610.39852）把队头阻塞这个一直被当成次要因素的瓶颈量化出来。工程实践详读 3 条、简条目 4 条，TorchTPU 是上期「预计 10 月中开源」的【更新】。资讯 6 条、快讯 1 条。

## 投机解码：MoE 曲线与能量维度

**【论文，全文】** [Why Speculative Decoding Works Better Than Predicted on Sparse MoE Models](https://arxiv.org/abs/2610.38981)（arXiv 2610.38981，v1 提交 2026-10-28，Cohere）。

问题定义：现有理论预测 MoE 上的投机解码「加速-batch」关系是凹的，加速在中等 batch 达峰，因为专家饱和后验证的复用收益消失。这篇论文测了 10 个稀疏 MoE 模型（30B–1T 参数、8–512 个专家），发现近期细粒度 MoE 违反这个趋势：加速在低 batch 更高，而不是中等 batch。

机制：验证成本由两个因素共同决定，而不只是激活专家的字节数。其一是时间重叠，相邻 draft token 激活的专家集合重叠 20–45%（独立抽取的基线是 4–12%），于是 K+1 个 token 验证时的唯一专家数下降 21–34%。其二是 GPU 执行动态，在 H100 上 MoE kernel 的带宽利用率高于 attention，L2 缓存吸收了被共同路由到同一专家的重复读取。

方法与设置：论文进一步给出 IPF（Iterative Proportional Fitting，最大熵）预测框架，仅从路由重叠统计就能以小于 4% 的误差预测唯一专家数，从而在离线阶段筛 target/draft 组合而不用实测。实验用 vLLM v1、K=3 个 draft token、单张 H100、MT-Bench。

边界：10 个模型、单卡、K 固定 3；结论绑在细粒度 MoE 上，粗粒度 MoE 仍是旧的凹曲线，不能外推到所有 MoE。

**【论文，摘要级】** [Only Accepted Tokens Count: An Energy Accounting of Speculative Decoding Under Latency Targets](https://arxiv.org/abs/2610.40287)（arXiv 2610.40287，v1 提交 2026-10-29）。这篇给投机解码补上能量这个第三维。核心发现：在 dense 模型上，投机解码的主要能耗是验证而不是 drafting；随着 batch 增大，省下的能耗收窄，因为 batching 本来就在共享投机解码要摊薄到被接受 token 上的权重读取。在大批量下，block drafter 把验证推进 compute-bound 区间，省能耗变成亏能耗。另一个普适结论：每个 drafter 在对话文本上接受的 token 数都少于在代码上，每个训练过的 drafter 在低资源语言（Romansh）上接受的 token 数都少于英文，也就是说接受率是所服务文本分布的函数，不是模型常数。测量在 H100/H200、batch 到 64、5 个语料，SGLang + CUDA graphs。摘要级范围：各 drafter 的能耗分解曲线与 latency-target 约束下的最优 drafter 选择未读。

这两篇收敛到判断账本里同一条线上。J25（接受率不是吞吐）此前警告接受率可调但不免费，40287 给它加了能量维：投机解码用接受率换的不只是输出变长，还有一笔在大 batch 下可能变成亏损的能耗。J1（推理优化必须在你真实并发分布下重测）拿到机制支撑：加速-batch 曲线形状不固定，是因为专家饱和点、带宽利用率区间、能耗平衡点都随 batch 和模型稀疏度移动。两篇论文指向同一结论，本期在判断账本记为对 J1、J25 的印证。

## 当名义值不等于实值

**【论文，全文】** [Accuracy is not compatibility: two Evo 2 checkpoints hinge on one FP8 matrix multiplication](https://arxiv.org/abs/2610.39415)（arXiv 2610.39415，v1 提交 2026-10-29）。

问题与发现：Evo 2 是一个 DNA 语言模型，1B / 7B / 40B 的 FP8 checkpoint 有明确的 Hopper FP8 依赖。论文测下来：在两张 Blackwell（sm_120）GPU 上，1B 和 40B 都过不了开发者自己的 forward 测试（7B 能过），40B 在 RTX 5070 Ti 上的 next-base 精度是 25.7%，接近随机。更反直觉的是越准的越坏：BioNeMo 观察到 40B 在 Hopper 上原生 FP8 下有 99.996% 的某个 projection 输出是正确的（H100 只有约 30%），但对同一组操作数做 fp32 累加反而过不了。

方法：论文给出 mmaemu，一个 H100 FP8 GEMM 的位精确模拟器（对抓到的 1B projection 位精确复现），把依赖定位到 1B 里 21 个 projection 中的第一个：用精确求和过不了，用 H100 实测的 1.4%（不是名义 2.1%）去 scale 就过。

边界：单一模型族（Evo 2、DNA 任务），但方法本身（用位级模拟而不是精度测试判断可移植性）是可迁移的。精度测试通过不是可移植的证明，这条结论落到判断账本，强化 J19（量化无损只在任务精度层面成立）与 J14（kernel/量化加速与行为必须带硬件条件读）。

**【论文，摘要级】** [How Far Are We From On-Device VLM Inference? A Measurement Study on Edge NPUs](https://arxiv.org/abs/2610.40039)（arXiv 2610.40039，v1 提交 2026-10-29）。跨层测量研究：6 个 VLM、3 个真实边缘平台、10 个多模态 benchmark，从应用层延迟/温度钻到 kernel 层行为。推翻三个社区假设。其一，softmax 主导 attention 成本，查表法 softmax 优化消不掉那个让 NPU matrix unit 严重低利用的 pipeline bubble。其二，线性注意力的理论加速在真实 NPU 执行下消失，张量重排开销不可接受。其三，没有任何硬件后端在自回归解码上通吃，attention 张量的并行形状决定 NPU 效率，并改变 CPU-NPU 的性能平衡。另发现每个任务有 Sweet Resolution：小幅延迟成本换有意义的精度增益。摘要级范围：各 NPU 平台的 kernel 级 profiling 与 Sweet Resolution 的完整曲线未读。

**【论文，摘要级】** [Attention, Dynamic Wave and Hybrid Sequence Mixers in Language Models](https://arxiv.org/abs/2610.39854)（arXiv 2610.39854，v1 提交 2026-10-29）。把 Dynamic Wave 循环层形式化（输入相关指数衰减 + 余弦相位调制），在 TinyStories 上 profile 三个 10.94M 参数配置：Pure Transformer、Pure Wave、Hybrid Wave-Attention。Hybrid 的 perplexity 最好（5.95，对比 Transformer 6.93、Pure Wave 7.26），但效率图景由实现决定，不是由架构决定：Pure Wave 对比 unfused attention 基线省 78.7% 峰值 VRAM（1404 vs 6602 MB），对比 fused scaled-dot-product kernel 则是零优势（1404 vs 1404 MB）；训练模式下 Pure Wave 比 Transformer 贵 8.3%。把逐元素项提出循环之外，单层就加速 2.53×（不需要定制 kernel），延迟差距从 2.48× 缩到 1.12×。混合栈继承了更贵那个 mixer 的成本（峰值 VRAM 与 Pure Transformer 差 0.1%）。摘要级范围：更大规模与真实任务上的 profile 未读。

40039 和 39854 从两个独立方向收敛到同一个跨来源结论：亚二次注意力替代方案（线性 / 循环 / 混合）的效率优势是实现依赖的。理论上的渐近加速不会自动变成真实硬件上的收益，因为 fused softmax attention kernel 已经足够优化（40039：线性注意力的理论加速在真实 NPU 执行下消失；39854：与 fused 基线一比优势就归零）。这个 pattern 有两篇论文支撑，本期在判断账本新增一条；它与 J9（Blackwell 上 attention 是 softmax/SMEM-bound）互补，J9 讲代内不对称，这条讲跨架构效率的实现依赖。

## 调度：扩散 LLM 的队头阻塞

**【论文，全文】** [DWISE: Denoising Workload-Informed Scheduling Engine](https://arxiv.org/abs/2610.39852)（arXiv 2610.39852，v1 提交 2026-10-29）。

问题定义：扩散 LLM（dLLM）通过并行去噪生成文本，但现有服务框架仍用为自回归模型设计的策略调度 dLLM 请求，即 FCFS 准入 + prefill 优先。论文指出这两个策略都不适合 dLLM：FCFS 忽略 dLLM 请求的 decode 成本高度异质、到达时未知，造成严重的队头阻塞；prefill 优先（AR 服务里广泛用于降 TTFT）会显著压低 dLLM 效率，因为纯 prompt 轮次让 batch 大部分空转。

方法与数字：DWISE 按剩余去噪工作量排请求，而不是到达顺序或阶段。端到端延迟比标准 batch 调度平均降 5.4×、最大 14.9×，在 5 个模型、3 个 dLLM 家族上验证。增益拆成两块：65–78% 来自排队延迟下降，22–35% 来自负载均衡，也就是说队头阻塞（排队），不是算力失衡，是主瓶颈。

泛化：在 3B dLLM 上只用每个 bin 845 个样本，端到端延迟仍降 10.5×（13,016 → 1,241 ms），说明跨模型稳健。

边界：dLLM 专属，对 AR-LLM 调度的结论不能自动迁移；绑在去噪工作量异质、且能从请求特征预测的前提上；单卡 Hopper 级 GPU 测量。队头阻塞作为 dLLM 服务的主瓶颈，是调度方向一个此前没被量化的新点，但本期只有这一个来源，按单篇孤立结论不进账本的规则，只在此记录、不动 judgments。

## Agent 记忆：互补的增益

**【论文，摘要级】** [Long-Term Agent Memory through Complementary Curation and Consolidation](https://arxiv.org/abs/2610.39790)（arXiv 2610.39790，v1 提交 2026-10-29）。提出一个混合记忆架构：情景记忆 + 结构化关系记忆，外加保效率的 consolidation 机制。在 LoCoMo 和 LongMemEval-S 两个 benchmark 上实测：两种记忆类型持续互补，两者结合超过 SOTA 记忆框架，达到 LoCoMo 90.2%、LongMemEval-S 85.5%。摘要级范围：两种记忆的独立贡献拆分与 consolidation 的开销未读。

这篇给 J16（检索更多、记忆更多不单调有益；增益符号由任务类型和读取机制决定）补一个新样本。J16 此前的证据多是记忆没用甚至有害，这篇说明两种异构记忆的结合胜过单一，增益来自读取机制互补，不是记忆更多。样本仍是两个 benchmark、摘要级、读取机制拆分不完整，所以只作弱印证，不改写 J16。

## 评估审计：是错配，不是造假

**【论文，摘要级】** [Beyond fabrication: Misattributed numbers in papers written by AI research agents](https://arxiv.org/abs/2610.38691)（arXiv 2610.38691，v1 提交 2026-10-28）。现有 benchmark 判定 AI 科研 agent 的论文有没有诚信问题时，判断常来自单一 LLM judge，能识别出问题却说不清问题性质。这篇重新分析一个公开 benchmark 的全部 540 条公开判定（9 个 agent、15 个开放研究问题），人工标注其中 18 份提交的 256 条数字声明。核心发现：失败集中在论文与底层工作的错配，不是明目张胆的造假；约 4/5 的无依据声明对应 agent 自己文件里的数值，但来自错误的实验、指标或 run，数字存在，但是错的数字。论文给出一个确定性的 claim-to-evidence 检查器（规则在标注前固定）：相对盲标标注者，它以大于 90% 的精确率认证声明（78/85，Cohen's kappa = 0.89），但它只验证声明的一个子集，不可验证不等于假（大部分不可验证的声明仍然可追溯）。给同一个证据的 LLM verifier 能找回更多可追溯声明，但会放过约 3 倍多的错配声明，两者最好合用。摘要级范围：检查器的完整规则集与 540 条判定的逐条标注未读。

这是负面 / 校准类论文，按本期负面结果优先的取舍放在工程方法线首位。它与判断账本两条相关：J10（负面 / 校准类结论更可信）拿到一个方法样本，论文数字错配这个失败模式本质是测量伪影；J13（差分类指标必须配独立测的 null 或冻结对照臂）拿到一个实用工具，规则先固定的确定性检查器就是数字声明的预注册 null 臂。

## 工程实践

**【一方博客，详】** [How to Check and Configure NVIDIA GPUDirect Storage for Your Platform](https://developer.nvidia.com/blog/how-to-check-and-configure-nvidia-gpudirect-storage-for-your-platform/)（NVIDIA Developer Blog，2026-10-30）。GPUDirect Storage（GDS）加速 GPU 与存储之间的数据路径，但配置要看清自己的环境。NVIDIA 把 GDS 团队内部用的 gds-diag 开源成单文件命令行工具，随 NVIDIA Magnum IO 仓库分发（git clone https://github.com/NVIDIA/MagnumIO.git，Python 3.8+，无额外依赖；GDS 本身要求数据中心级 NVIDIA GPU + CUDA 12.2+，但这不是 gds-diag 的依赖）。子命令分四组：端到端（all，按路径自动跑完整诊断，裸机/VM/容器都可用）、安装前（pre-install 查 GPU 与 CUDA、support-matrix 看支持的存储目标，--static/--live）、安装后（post-install 验证、config-audit 审配置文件与环境变量）、深度诊断（container-check 覆盖 containerd/Docker/Enroot/K8s、mount-check 诊断具体挂载点）。每条 finding 带 FAIL（硬阻塞）/ WARN（潜在阻塞）/ INFO（值得注意）/ PASS（--verbose 才显示）徽章，附解释与缓解方案，但工具不自己改系统。--json 可导出结构化报告。另配一个可选 agent skill：自然语言入口，解读意图、编排多步子命令、用模型推理解释结果并提议缓解，已验证 Claude 与 Codex，把 gds-diag 目录丢进 coding assistant 或用 /gds-diag 激活。来源核验：第一方（NVIDIA GDS 团队）；可验证子命令/仓库/许可证（Apache 2.0 + CC BY 4.0）/CUDA 版本绑定；时间戳 2026-10-30；营销动机（自家产品但开源、工具确定性、可 clone 复现）。
