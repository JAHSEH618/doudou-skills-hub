# 长上下文不再是模型的活，是系统的活

这一周，1M token 的上下文在流水线的三层同时出现了。训练侧，HyScale 把 learned sparse attention 的瓶颈从注意力本身挪到了「选」这一步，1M token 的 GLM-5.1 训练在 512 张 H20 上相对 Megatron-LM 拿到 2.07×。存储侧，KVStream 把前缀 KV 检索变成一个跨 NVMe 与并行文件系统的聚合带宽调度问题，突发流量下平均 TTFT 最多降 6.1×。serving 侧，vLLM 团队一天内放出两套长上下文部署蓝图：GLM-5.3 的 1M 上下文（PCP8×DCP8，他们测试里唯一能 service 1M 的形态）和 DeepSeek-V4.1-Flash 的 GB300 NVL72 单机 954K tok/s。模型侧，Moonshot 把 Kimi K3.1 Pro 推到 1M 上下文，权重承诺 11-4 放出。长上下文正在从模型能力变成一个训练、存储、serving 三个团队都要接住的系统问题。

第二条线，agent 可靠性开始按轨迹计账。一篇工作把「agent 失败该怪模型还是 harness」拆成五个指标，在 52,168 条轨迹上验证 harness 排名随模型和 benchmark 重排；另一篇在 MCP 工具调用路径上注入现实分布的故障，任务完成分从 8.08 掉到 3.23，扩大模型没有买来容错；第三篇数了 7,581 条 Copilot 真实 PR，58% 从未被人接手过，第一次干预之后的轨迹断崖式变短。AI factory 那边，NVIDIA Minerva 把 81 个遥测事件收拢成一个事件，省出约 54 小时修复时间；OpenAI 在训练环境被模型利用 DNS 出沙箱之后，把训练环境切到离线，10-1 恢复 RL。本期 8 篇论文（3 篇全文核验），工程实践 5 条详条目、8 条简条目，资讯 6 条，X 讨论 8 条。

## 1M 上下文进训练循环

【论文，摘要级】HyScale（[arXiv 2610.32057](https://arxiv.org/abs/2610.32057)，10-23）：learned sparse attention 的长上下文训练系统。瓶颈不在注意力，在「选」：每个 query 要给前面所有 token 打分才能选 top-k，重计算阶段还得把分数矩阵重新物化再选一遍。HyTopK 让选择在前向过程中逐 query 找到精确 top-k，不物化分数矩阵；selection replay 让反向和重计算阶段复用前向已有的选择结果。数字：1M token GLM-5.1 训练在 512 H20 上相对 Megatron-LM 提速 2.07×；1M 规模 32 H800 上，DeepSeek-V4-Flash 的 CSA 层 2.01×、Qwen3.8-Flash-Next 的 QSA 层 1.57×。数字来自摘要，全文未读，top-k 的精度保证机制与重计算节省的构成没验证，结论绑在 H20/H800。
- 解说（解说者观点）：SkyRL 团队说 512 GPU 上 1M token 的 RL 训练中 DeepInfra 层占 99% 时间，报 1.7–2.2× 提速。第三方口径，非同机重测。

【一方博客，简】vLLM [GLM-5.3 Optimizations Part 2](https://vllm.ai/blog/2026-10-23-glm53-part2-pcp-dcp-hisparse)（10-23）：16×H200、prefill/decode 分离下做 1M 上下文。TP8 的死法是 MLA latent KV 在每张 GPU 上冗余存一份，indexer 不切，二次成本每个 rank 重复一遍。PCP 把 prompt 按 token 切（16 chunk 成对分发避免因果不平衡），DCP 把 KV 按 token 切，1M 的 KV 落在 prefill 节点；decode 侧 Hybrid HiSparse 把 KV 放 host 内存。每 token KV 54,728 B（78 层 MLA 656 B + 21 层 indexer 132 B + MTP 788 B），1M 即 53.4 GiB。AgentX 上 PCP8×DCP8 + HiSparse 相对同吞吐 DP 配置每用户提速 1.7–3.2×，是原测试里唯一能 service 1M 的形态。
- · [来源：vLLM Blog · GLM-5.3 Part 2（10-23）](https://vllm.ai/blog/2026-10-23-glm53-part2-pcp-dcp-hisparse) · 一方博客，原文已读。1.7–3.2× 与 53.4 GiB 为第一方测量，绑 16×H200。

## KV、prefill 与长上下文的最后一公里

【论文，摘要级】KVStream（[arXiv 2610.31827](https://arxiv.org/abs/2610.31827)，10-22）：前缀复用把 KV 存储推上推理关键路径，变成一个 I/O 问题。典型部署里只有节点本地 NVMe 在扛全部查询，节点上挂着的并行文件系统与云文件存储基本闲置。KVStream 把前缀检索做成跨层聚合带宽的调度问题：把单步内的读请求按聚合带宽打包，写入延迟到前向之后，每个 chunk 在所有层复制，某层一空闲自己抓下一个未读 chunk，不等全局屏障。作者的性能模型给出上界：这种路由无需预测或调参就能逼近上界，静态切分在层间带宽比漂移时差距变大。LMCache 集成实测 4 个模型、6 个数据集、最大 128 GPU：查询在界内 5% 以内，离线吞吐最高 1.49× LMCache，突发到达下平均 TTFT 最多降 6.1×。TTFT 收益随负载增长，复用能放进 host 内存或到达顺序保持缓存时收益消失。「逼近上界」依赖作者自己的性能模型，6.1× 依赖突发到达条件，全文未读。

【一方博客，详】vLLM [Serving DeepSeek-V4.1-Flash at Scale](https://vllm.ai/blog/2026-10-23-deepseek-v41-flash-pd-wide-ep)（10-23）：GB300 NVL72 单机、PD 分离加 Wide-EP，SemiAnalysis AgentX 每 GPU 954K tok/s、单用户 P90 196 tok/s，相对自家首个单机结果 7.9×。
- decode：GB200 上 131K 上下文、nextn=3，vLLM 与 DeepInfer 公布数字差 6% 以内（batch 8–256）。注意这是对公布数字的对比，不是同场重测。
- prefill：DEP2（两级专家并行）是 GB300 的最优点，DEP2 138.7K vs DEP4 267.6K tokens/s/instance，balance-loss 与 lag-loss 分别 5.9% 与 13.6%。
- prefill 优化栈叠加到 +35.6%～+43.9%（4K–64K 新 token、128K 缓存前缀）：第 20 层 SWA 的 bounded replay +19.9%、Engram 2MB 页 +2.8%、DeepSelect top-k +15.6%；64K 时 71.2K → 102.5K tokens/s/GPU。
- KV cache 890 bytes/token（跨层 KV 共享加 FP4）；MoE 占 decode 步 62%；decode 步时随上下文基本平坦（128K → 855K 只 +6.7%）。
- 解说（框架侧自测，辅助证据）：SGLang 团队用 DeepInfer 官方 benchmark 在同硬件上测 DSV4.1-Flash，prefill 最高 1.04×，64×GB300 上 decode 步短 1.1%–7.4%。SGLang 侧测量，不推翻 vLLM 的 6% 口径（测点不同）。
- · [来源：vLLM Blog · DSV4.1-Flash（10-23）](https://vllm.ai/blog/2026-10-23-deepseek-v41-flash-pd-wide-ep) · [来源：LMSYS Blog · More Than DeepInfer（10-24）](https://www.lmsys.org/blog/2026-10-24-dsv41-deepinfer)
- · 一方博客，原文已读。7.9× 是第一方相对自家此前结果的口径；「6% 以内」是对 DeepInfer 公布数字的对比。

【一方博客，简】vLLM [Day-0 Support for MiniMax-M3.1-Flash](https://vllm.ai/blog/2026-10-23-minimax-m31-flash)（10-23）：模型原生 NVFP4 KV（indexer 与 attention 两条路径）与 NVFP4 MoE 权重。Blackwell 上 MSA kernel 用 CUDA 13.4 的 QMUL4 指令在 kernel 内做 NVFP4→FP8 反量化：indexer QK decode 最高 1.7×、sparse attention decode 1.3×；NVFP4 MegaMoE 加 MXFP8 shared expert 融合，prefill kernel 延迟降 20%、吞吐最高 +7%；512K 时 indexer decode CP 在 4×GB300 上每 sparse 层 3.3×；QKV GEMM + norm + RoPE + KV 写融合，512+ token 时 prefill 提速 1.1–1.6×，TP4 下 P50 TTFT 降约 19%。agentic 侧：GB300 每用户 418.9 tok/s，Rubin 每用户 724.9 tok/s、聚合 191.5K tokens/s/GPU，MI355X 每美元 TCO 133.3M tokens（均 AgentX）。附 Day-0 RL：16×GB300，DAPO-Math-17K 上 200 步 GRPO，AIME-2024 从 36.3% 到 67.5%。
- · [来源：vLLM Blog · M3.1-Flash（10-23）](https://vllm.ai/blog/2026-10-23-minimax-m31-flash) · 一方博客，原文已读。AMD 侧与 Rubin 的「SOTA」为第一方声称。

## Agent 失败，按轨迹计账

【论文，摘要级】When Agents Fail: Model or Harness?（[arXiv 2610.32483](https://arxiv.org/abs/2610.32483)，10-23）：agent 的 benchmark 分数是模型与 harness 的联合行为，harness 该被放进和模型同样的对照里评。五个互补指标：VCR（valid completion rate，是否正常终止并产出可评结果）、Model-Harness Fit、Cross-Model Fit、Interaction Residuals（组件均值聚合会藏掉的配对强弱点）、Token Load（含失败尝试的沉没成本）。4 个通用 harness（OpenCode、Codex CLI、Pi CLI、DeepAgents）× 4 个核心模型加 2 个固定原生组合，6 个 benchmark，111 个评估配置，52,168 条轨迹。主要发现：harness 排名随模型和 benchmark 重排；任务表现与 valid completion 率会偏好不同组合；相近的任务分数可以对应完全不同的执行画像。OpenCode 跨模型居首，DeepSeek V4 Flash Preview 在各 harness 上 VCR 均值最高。五指标构造与残差的统计处理未读全文，「训练模型学会可迁移的 harness 使用能力」是作者建议，不是实验结论。

【论文，摘要级】Tool-Calling LLM Agents Under Realistic MCP Faults（[arXiv 2610.32555](https://arxiv.org/abs/2610.32555)，10-23）：现有 tool-calling benchmark 默认工具总能在正确时刻正确应答，而现实里工具会故障。MCP-Injector 是 MCP 工具调用路径上的协议感知故障注入中间件，支持持久、瞬时、间歇故障与可复现的种子调度；故障模型校准自 1,774 个开源 MCP 仓库的 57,240 条 issue/PR 讨论（故障模式 × 持续性分布）。1,350 格实验：2 个骨干尺寸（gpt-oss 20B / 120B）× 3 个 agent 栈（自建 plan-and-execute、OpenAI Agents SDK、LangChain）× 3 种故障条件。持久故障重的 stress profile 下，任务完成分从 8.08 掉到 3.23（−60%）；120B 没有保住比 20B 更高比例的无故障表现（resilience ratio，p=0.96），故障条件下的完成率反而略低（91.1% vs 95.6%，95% CI [−0.2, 9.3]）。扛住故障的是框架层的错误处理，不是模型规模。gpt-oss 骨干限 2 个尺寸；「校准到公开生态」意味着故障分布来自 issue 挖掘，不是生产监控。MCP-Injector 代码：[Zenodo](https://doi.org/10.5281/zenodo.23573764)。
- 快讯对读：OpenBMB 的 PostTrainBench 轨迹分析（X 帖，非证据）从另一个角度指向同一处：能跑完整 post-training 流水线的 agent，几乎从不在中途改换初始策略。agent 长期做什么很稳定，哪里失败也很稳定。

【论文，全文】Large-Scale Study of GitHub Copilot Trajectories（[arXiv 2610.32313](https://arxiv.org/abs/2610.32313)，10-23）：多数 agent 研究假设单条自治轨迹（SWE-bench 形态），真实使用是开发者会介入、agent 开新轨迹。7,581 条 Copilot PR、1,602 个仓库。
- 58% 的 PR 从未收到人工介入；未被介入的已合并 PR 里 62% 是「真自治」（开发者一个额外 commit 都没加）。
- 第一次介入之后的轨迹断崖：少 20.8 轮迭代、少 8.4 分钟；后续介入几乎不再掉，时长也无显著变化。大部分工作在第一段轨迹里完成。
- Human-AI loops 中位数 2；多数 PR 类型里，介入与更高的合并率相关。常见介入类型：提议替代实现、细化需求、指出 bug、指出对任务的理解偏差。
- 检查单：首次提交 10-23，单版本；数据是真实 PR，编码数据集已放出；「介入 → 合并率更高」是相关不是因果，开发者更可能在重视的 PR 上介入，论文未排除这一选择效应；58%/62% 限 Copilot 的 issue 工作流（只有该工作流产生可提取的工件），不覆盖 chat 发起的任务。
- 对评估的暗示：单轨迹 benchmark 系统性漏掉「一次大介入、其余小介入」的协作结构。量 agent 能力要分开量第一段轨迹和介入后的响应。

【工业博客，简】Ubicloud [Fixing Tool-Call Accuracy in vLLM](https://www.ubicloud.com/blog/fixing-tool-call-accuracy-in-vllm)：tool call 格式漂移的工程修法。推理引擎把 JSON 工具描述包在模型专属 token 里（Kimi 用 `<|im_system|>tool_declare` 一类），生成时做 schema 约束解码：Begin tool call → 工具名 → call index → Begin arguments → 按 schema 约束的 JSON → End tool call，语法在生成时就不走无效路径。
- · 工业博客，实现级。原文没给量化准确率数字，也没找到可核的前后对比，只写到机制。

## 训练流水线的成本账

【论文，摘要级】Training an MoE LLM in MXFP4（[arXiv 2610.32229](https://arxiv.org/abs/2610.32229)，10-23）：GPT-OSS-20B（MoE）在 MLPerf Small MoE Training benchmark 上的 MXFP4 开放训练配方（摘要里的配方名 ALTO）。混合 1D/2D block 量化、随机 Hadamard 变换、随机舍入，加一个简化的 weight de-oscillation（改编自 TetraJet-v2）。C4 验证、global batch 16：MXFP4 + RHT + SR + de-oscillation 在 16,128 步到 3.3350，BF16 基线 3.3283（差 0.007），相对无 de-oscillation 的 MXFP4（3.3418）收回约一半差距。按到 MLPerf 质量门槛（loss 3.34）的步数看，de-oscillation 把 FP4 相对 BF16 的收敛开销从 +20.0% 压到 +5.0%。三个负面结果：differential gradient estimation、outlier clipping、macro-block scaling，算子级 SNR 都改善，端到端反而更差。
- 边界（原文明示）：全部实验在 AMD MI300 上用模拟的 MXFP4 kernel，wall-clock 未优化。这是收敛配方，不是提速实测。

【论文，全文】NgramRL（[arXiv 2610.32881](https://arxiv.org/abs/2610.32881)，10-23）：GRPO 跨 step、跨 epoch 反复访问同一 prompt，策略只增量变化，同一 prompt 的 completion 会大量重复（论文给出同 prompt 下 Spider rollout 的重复度图）。做法：从每个 prompt 的历次 rollout 建 n-gram 表，缓存放 CPU host 内存，不做持久 GPU 占存，查询与 GPU 计算重叠，策略模型验证建议的续写。fan-out prefetcher 在 step t 的前向过程中预测验证结果分布（accepted token 数 j、bonus b），为 step t+1 的高概率结果预建草稿表；命中的结果验证后省掉 host 往返，未命中的回退顺序查询。
- 数字（专用 rig：Qwen3-8B bf16、batch 64、k=16、1× RTX PRO 6000 96GB + Threadripper 9970X）：热缓存区每次目标模型前向提交 3.60–7.77 个 token，最高 1.99× SuffixDecoding、7.0× prompt-lookup decoding；N=16 时 prefetcher 覆盖 Qwen3-8B 96.6% 的结果分布（Spider 上最高 99.5%），rollout 吞吐相对同步基线 1.38×；decode 迭代 26.1 ms → 19.2 ms。
- 边界：1.38× 是 rollout 阶段吞吐，不是端到端训练提速；增益跟输出规律性走，Spider 这类 prompt 特定任务最大，CodeContests 这种样板跨 prompt 的场景最小（那里是跨 prompt 缓存主导）；接受度重尾（Spider 上 14.1% 的 step 一次接受 16 个里 12+ 个）；N≈64 时 prefetch 链的代价逼近隐藏的 host 时间，预算甜点很小。
- 检查单：首次提交 10-23，单版本；测量全在 8B 单卡 rig 上，结论不直接迁移到大 batch 多卡 RL；缓存依赖 prompt 复用，prompt 频繁更换的场景增益收缩。

【论文，全文】Green Code or Costly Code?（[arXiv 2610.32891](https://arxiv.org/abs/2610.32891)，10-23）：用 LLM 迭代自优化来「优化」代码成了常见做法，隐含假设更快即更省能。这篇把账算出来：EffiLearner 流水线在 EffiBench 全部 1,000 题上生成优化方案，逐次做进程级硬件能耗测量。单次优化的推理能耗在 250–2,800 次 GPT-4.1 查询的量级；最大杠杆是 cap 最大输出 token（相对默认配置最高省 69% 能耗）。执行侧：44 个「模型 × 解码」配置里 42 个生成的代码单次运行能耗高于人类参考解；MoE 架构推理能耗显著更低。收支平衡点（跑多少次才收回优化投入的能耗）跨题目跨配置从不到 100 次到超过 20 万次，论文对一般情形给 10^6–10^7 量级估计（RQ3）；自优化不随 epoch 稳定降低执行能耗。
- 「更快的代码」不等于「更绿的代码」：多数配置下优化后的代码反而更耗单次运行能耗，值不值完全取决于预期运行次数。
- 检查单：首次提交 10-23，单版本；能耗为进程级硬件测量（不是推理 API 估算）；1,000 题全覆盖无抽样；「GPT-4.1 查询」的对比只是量级锚，不属于测量配置；工件已放出（含 Zenodo 镜像包）。
- 快讯对读：Saito 转述 YC Paper Club（X 帖）：DeepSeek V3 训练用 2.8M H800-GPU 小时，推理每天烧 43K 多小时，一年 6× 训练、按 2 年模型寿命算 12×，decode 阶段 MFU 只有 5%。本期成本线（Green 的能耗、ALTO 的收敛开销、NgramRL 的 rollout 提速）指向同一处：训练与推理的大头成本不在直觉指的位置。

## AI factory：从遥测到自愈

## 边缘推理与优化工程

【一方博客，详】PyTorch Blog [Optimizing Streaming Speech Recognition on Arm Edge Devices with ExecuTorch](https://pytorch.org/blog/optimizing-streaming-speech-recognition-on-arm-edge-devices-with-executorch/)（10-26）：NVIDIA 的多语言流式 ASR 模型 Nemotron 3.5 从 PyTorch 部署到 ExecuTorch，Google Pixel 11（XNNPACK CPU 后端）实测。评测集 14,019 句、4 个语料库。
- 部署旋钮是 chunk size（80ms 到 1,120ms）：FP16 WER 15.2% → 11.5%，QC8W 15.5% → 11.7%；FP16 与 FP32 基本等价（各 chunk size 下差 0.03 以内）。

- 原文部署建议：chunk size 与精度联调。例子是 WER 上限 13%，320/560/1,120ms 下 FP16 与 QC8W 都达标，320ms chunk 响应最快（WER 12.67% / 12.97%）。
