# 冻结模型也会“进步”：性能和评测都需要对照

一个没有更新过权重的模型，在两次评测之间也可能被判成“学会了新题”。Phantom Gains 把冻结模型送进与自训练模型相同的评测流程，得到的假提升足以改变对训练方法的判断。它让本期的阅读顺序变得很明确：先弄清评测会产生多少变化，再讨论训练带来了多少变化。

推理优化也有同样的归因问题。FlashPrefill V2 的注意力算子峰值与整条服务链路的 TTFT 收益相差很大；FleetSieve 则展示了平均吞吐接近时，尾延迟仍能决定配置是否可用。模型、硬件和系统各自报出的数字，只有放回基线与负载里才能比较。

## 没有训练，为什么也会测出提升

冻结对照的作用，是把测量流程自身的变化从训练收益里分开。Phantom Gains 与 GRPO unlearning 研究分别检查了逐题变化和奖励口径。

### 冻结模型为自训练提供了什么对照

Phantom Gains: Auditing Self-Improvement Against a Measured Null · UCD + Georgia Tech + 大连理工 · 2026-08-20 · [arXiv:2608.20290](https://arxiv.org/abs/2608.20290)

论文给自训练评测加了一组冻结模型对照。用于证明改进的统计量，在没有训练的模型上也会出现变化，因此训练收益必须减去测量流程本身的影响。

作者拿 Qwen3-8B 做 3 轮 rank-32 LoRA 自训练，同时把一份冻结的 θ₀ 副本推过完全相同的评测管线当作对照，找出七个测量失效点，每一个在缺对照时都会把结论反过来：

- **F1 单次贪心解码不是状态**：temperature-0 在 batching 下不确定。一个没训练过的模型自己跟自己比，产出 6 次"学会"和 9 次"退化"，corruption-to-learning ratio = 1.5——正好是这个领域常报的那种"自训练在破坏能力"的形状，凭空造出来的。串行化请求能去掉四分之三的翻转，但即使一次一条，冻结模型仍有 **2% 的贪心判定会变**。
- **F2 expansion 统计量没有自己的 null**：按现行定义（base 模型 k 次采样全错、训练后至少对一次 = expanded），冻结的 Qwen3-8B 在 k=128 下评两次，25 道没做出来的 AIME 题"扩展"了 7 道，**expansion rate = 0.280**。
- **F7（藏在 F2 的修复里）**：七次全是单次幸运采样，看似可以用"要求 m≥2 次成功"修好并把 null 压到 0。不行——那个结论只基于一次冻结对比；在他们实验天然包含的 **110 次**冻结对比上，null 是 **0.058 [0.038, 0.078]**，比它本该认证为零的那个值还大。
- 另外还有：固定 token 上限遇上风格漂移会把最有效的臂判成最有破坏性的（F3）；transition 类指标比 accuracy 少约 **10× 统计功效**，112 题的 pilot 根本分辨不出来（F4）；训练种子方差让同一方法的 clr 横跨 0.55–1.53（F5）；欠功效的探针造出一个 10 个点的幽灵安全性下降（F6）。

修好之后的实质结论：外部蒸馏能改善 base 模型极少触及的题（22 题里 8–11 题），三种自训练形式都不能（0–2 题），且回归排除了"这只是蒸馏总增益更大的副产品"（β=1.91，p<10⁻⁸）。同时自训练在 1,163 道 band 题上破坏了 88–106 道，对照的设计匹配地板是 8 道。


这些结果限定在 Qwen3-8B、rank-32 LoRA 和三轮训练。[作者代码](https://github.com/chengxuphd/phantom-gains) 提供了从归档数据重算表格的分析脚本，采用 Apache-2.0；报告当时仓库刚建立，尚无第三方复现。冻结对照可以借用多臂实验各自的 checkpoint 0，但需要足够多次重复，才能稳定估计测量噪声。

### 奖励上升以后，行为是否改变

An Empirical Study of Reward Specification and Benchmark Reliability in GRPO-based LLM Unlearning · 瓦伦西亚大学 · 2026-08-18 · [arXiv:2608.17804](https://arxiv.org/abs/2608.17804) · 摘要导读

受控的 LoRA-GRPO / RWKU 设置下比四种奖励设计（词汇级抑制、反拒答塑形、rubric 式宽答、显式拒答对比），带与不带 SFT warm-up。核心结论是负面且可迁移的：优化成功 ≠ 行为改变。RWKU forget 分数、留出集补全审计、终态训练 rollout 审计、训练动态——四个视角会指向互相矛盾的结论。作者把分歧归因到奖励 hacking 端点、GRPO 的 policy-support 限制、以及 benchmark 探针本身的错配。

虽然题面是 unlearning，价值在"同一次 RL 后训练，换个测量视角结论就翻"这个模式，跟这期前述研究是同一个病灶的不同表现。


### 同一请求换个 batch，结果就可能变化

Thinking Machines Lab / Horace He · 2025-09-10 · [博客原文](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)

文章从浮点加法顺序讲到 batch invariance：同一 kernel 在相同输入上可以逐位重现，但请求的批次形状变了，归约路径也可能变化。服务端的并发负载决定批大小，用户端便会看到不同输出。这里要区分“同一程序重复运行”与“请求换一个批次仍得到同样结果”。

这份作者侧解释适合和本期的测量研究对读。固定随机种子与贪心解码覆盖不了批次变化；核查一次回归时，还需要记录服务并发和 kernel 路径。博客中的具体实现与实验属于其发表时的版本，不据此保证现在任意推理服务的确定性。

## 从算子峰值走到可用的服务

优化结果要经过完整服务链路，才会成为用户能感受到的延迟改善。下面几份材料分别检查稀疏 prefill、尾延迟和 GPU 代码的实际执行。

### FlashPrefill V2：47× 与 4.8× 量的是不同范围

FlashPrefill V2: Block-Sparse Prefill Attention for Long-Context LLM Serving · CASIA MAIS&NLPR + 中科院大学 + 微信/腾讯 · 2026-08-20 · [arXiv:2608.19758](https://arxiv.org/abs/2608.19758)

把稀疏 prefill 从算法原型推到能进生产：mean correction 项（把被剪掉的块用其池化 K/V 统计量补回 softmax 分子分母，救极端稀疏度下的精度）、按 FA3/4 对齐重写 kernel（PackGQA、warp specialization、pingpong pipelining、FP8）、原生支持 paged KV cache 和 continuous batching，可作为 SGLang 的 attention backend 接入。

几个加速比对应不同的测量范围。标题数字 47.26×（FP8@128K）是对 **FlashAttention-2** 的——在 Hopper 上这是个过时基线。对 FA3/4 对齐的稠密基线是 30.49×（FP8）/ 17.54×（BF16），但这个比的是稀疏 vs 稠密，量的主要是稀疏率不是 kernel 水平。能拿去做决策的是端到端：接进 SGLang 后 128K 的 TTFT 降 **4.8×**。47× 和 4.8× 之间差一个数量级，这个 gap 本身就是本条最该记住的东西。


全部实测在 H20、batch size 4 上完成。H20 的算力与带宽配比会影响稀疏优化的收益，不能直接外推到 H100、H200 或 B200。已公开的 [前作仓库](https://github.com/qhfan/FlashPrefill) 使用 vLLM 0.10.0 / 0.12.0 patch loader；当时尚未核到 V2 的 SGLang 集成发布。

### FleetSieve：同样的吞吐，可能只有一组配置达标

FleetSieve: Decision-Critical Profiling for SLO-Aware LLM Fleet Configuration · 2026-08-20 · [arXiv:2608.19659](https://arxiv.org/abs/2608.19659)

问题：给推理集群选 TP 度数和副本数很难，因为性能对 TP 不单调，且可行解会随负载变化。穷举 profiling 能解决，但大量测量对最终分配决策毫无影响。FleetSieve 按"这次测量预计能多大程度改变下游分配决策"来选测哪一格，联合建模容量与尾延迟，当保守解与乐观解的差距低于容差就停。

但本条值钱的不是这个方法，是它顺手测出来的两个事实：

1. 在 Chat C128 负载点上，**TP4 和 TP8 都能服务 11.27 req/s，但 completion-p99 分别是 46.4 秒和 25.2 秒**——只有 TP8 过得了 30 秒的 SLO。吞吐相同时可行的 TP 仍然不同。仅看吞吐无法识别这组 SLO 差异。
2. 16 卡分配下，用稀疏 profiling 做出的错误决策，在 1.3× 需求时损失 1.93 req/s 和 12.4 个百分点的 max-min 满足率；0.7× 需求时富余容量把这个错误完全掩盖住了。你在低负载下测不出配置错误。

方法本身的收益作者报得很诚实：固定对比下 22,200 GPU-秒，比均匀随机省 6.9%；200 次随机揭示顺序下平均省 5.4%（95% bootstrap CI 3.5–7.2%）；Chat 类省 21.5%，Code 类它不是最省的。


实验采用 H100、31B FP8 模型和 vLLM，比较 TP2/4/8，未启用投机解码。选出的配置受请求分布与 SLO 约束；论文没有提供能直接接入现有集群的代码包。

### PTXBench：指令执行了，还要证明它快

PTXBench: Benchmark and Adapt LLMs for GPU Kernel Optimization with Architecture-specific PTX · Stanford（Olukotun 组）+ CMU + RadixArk · 2026-08-18 · [arXiv:2608.17379](https://arxiv.org/abs/2608.17379) · 摘要导读

在 H100 和 B200 上测 LLM 用架构专属 PTX 写 kernel 的能力，同时量三件事：功能正确性、目标指令是否真的在运行时被执行、以及相对前沿库的加速比。结论偏负面且有用：能力很不均衡，复杂 attention backward 上成功率大幅下降；而且"确实执行了目标指令"并不等于"性能有竞争力"——这两件事被拆开测是这项评测的价值。没有任何被评模型能在整个套件上稳定匹配前沿库。作者另用 SFT 适配了 Qwen3.6-27B，repair-conditioned 训练在若干任务上有改善。

与上周的 CAKE、以及这期落选池的 KernelArc 连读：agentic kernel 生成已经形成一条明确的线，但 PTXBench 是里面将"看起来对"和"真的快"的。


## 模型需要的上下文，能否以更低成本送达

稀疏注意力把问题放在训练与推理之间，编码 Agent 和 RAG 则把问题放在信息提供方式上。对照应包含信息是否到达模型，以及为此付出的成本。

### 稀疏注意力可以参与训练适配

Learning how to Forget: Fine-tuning for Long-Context Sparse Attention · AWS Labs · 2026-08-20 · [arXiv:2608.19920](https://arxiv.org/abs/2608.19920) · 摘要导读

给稀疏注意力做微调的方法：对任何 KV cache 策略都适用，让模型与策略协同适配，而不是把稀疏策略当推理期的事后手术。两个落地向的点——一是硬件预算低到**单张 A100 40GB** 就能跑；二是协同适配后常常超过用精确注意力（序列并行）训出来的模型，精度也可能受益。他们实验里 H2O 是最强策略，并给了配套的 SDPA kernel 实现。配套开源库 KeysAndValues：[github.com/awslabs/keys_values](https://github.com/awslabs/keys_values)。

摘要没有交代单卡 40GB 这个说法适用于什么模型规模、"常常超过"的 often 有多 often，都没核。


### 代码约定的缺失会怎样改变 Agent 行为

The Working Set of a Coding Agent: Coherence Debt in Repository-Scale Tasks · 2026-08-17 · [arXiv:2608.16630](https://arxiv.org/abs/2608.16630) · 摘要导读

把仓库级编码建模成"重建一张耦合事实图"：每次编辑需要的事实要么来自近期上下文，要么来自参数记忆，两条通道都没覆盖的部分叫 coherence debt。作者对七个模型、五种 harness 逐一供给/撤走每条通道并注入故障。数字具体：

- 四个虚构 API 迁移的 154 次闭卷试验中，没有任何模型完成过一次；把同样的事实放进 prompt 后，300 次匹配试验有 **299 次**达到 12 条要求中的至少 9 条。
- 真实 Pydantic 迁移的"改名孪生版"上（让记忆失效），**七个模型的 70 次试验里有 66 次停在同一个分数，各自通过 79 个测试中完全相同的 24 个**。
- 可用性决定结果，距离不决定：撤走一个事实，代价恰好等于它支撑的那部分工作，损伤随撤走量线性增长；而供给的事实在 128,000 字符上下文的最远端和紧挨编辑处一样好用。
- 全都通过所有测试的 harness 配置之间，token 消耗差十倍以上——因为它们以不同频率重建同样的内容；而事实被撤走时，多花钱一点也救不回来。
- 缺事实产生的是错的工作而不是没有工作：agent 被要求动手就会动手，编造文件或猜值——所以建立在"读了什么"上的观测手段，看到的是一个已经被填上的洞。
- 标准与代码冲突时 agent 跟标准走，哪怕标准规定的是更差的代码：一份过时的 convention 文件比没有文件代价更高。
- SWE-bench 上因为模型多半已经记住了那些仓库，"读取行为"不再预测成功——这解释了一批基于读取轨迹的评测为什么测不出东西。


### 复杂分块何时值得付出成本

When Is Complex Chunking Worth It? A Multi-Objective Evaluation of Chunking Methods at Scale · CIKM 2026 · 帕绍大学 + IT:U Linz · 2026-08-17 · [arXiv:2608.16586](https://arxiv.org/abs/2608.16586) · 摘要导读

八种 chunking 策略（token / sentence / late / 标题增强 / 摘要增强 / contextual / summary / semantic）× 两个可扩展语料 × 三个 embedding 模型 × 多种语料规模，同时量检索效果和系统成本（文档吞吐、查询吞吐、峰值内存）——后半截正是以往 chunking 对比普遍缺的。

结论：计算昂贵的方法很少能稳定超过简单方法；最优策略取决于 embedding 模型、数据集、语料规模和目标指标四者的组合，没有普适赢家；而且效果相近的方法在运行成本上可以差很多，所以 chunking 应当被当成多目标设计决策而不是"选个最好的"。代码 [github.com/casparil/chunking-eval](https://github.com/casparil/chunking-eval)，数据集在 HuggingFace。


### 把任务结果与执行轨迹分别评分

Anthropic · 2026-01-09 · [博客原文](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

文章把 task、trial、grader、transcript 和 outcome 分开定义。轨迹记录 Agent 说了什么、调用了什么工具；outcome 检查环境最后变成了什么。代码检查、模型评委和人工评分可以评估不同侧面，选择取决于成功条件是否能够直接验证。

和本期论文对读时，可以关注重复试验和评分器校准。一次通过、平均得分和持续稳定完成是不同的观察；模型评委也需要与人工或环境状态对照。博客提供的是评估设计方法，案例成绩来自作者，不能替代自己任务上的验证。
