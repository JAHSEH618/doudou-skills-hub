## 本周只读一篇

**Phantom Gains: Auditing Self-Improvement Against a Measured Null** · UCD + Georgia Tech + 大连理工 · 2026-08-20 · [arXiv:2608.20290](https://arxiv.org/abs/2608.20290) · 【全文】

**为什么是它**：它把"自我改进"这一整个赛道的评测方法论掀了一遍——不是说某个方法不 work，而是说**用来证明它 work 的统计量本身在冻结模型上就能刷出结果**。

作者拿 Qwen3-8B 做 3 轮 rank-32 LoRA 自训练，同时把一份**冻结的 θ₀ 副本推过完全相同的评测管线**当作对照，找出七个测量失效点，每一个在缺对照时都会把结论反过来：

- **F1 单次贪心解码不是状态**：temperature-0 在 batching 下不确定。一个没训练过的模型自己跟自己比，产出 6 次"学会"和 9 次"退化"，corruption-to-learning ratio = 1.5——正好是这个领域常报的那种"自训练在破坏能力"的形状，凭空造出来的。串行化请求能去掉四分之三的翻转，但即使一次一条，冻结模型仍有 **2% 的贪心判定会变**。
- **F2 expansion 统计量没有自己的 null**：按现行定义（base 模型 k 次采样全错、训练后至少对一次 = expanded），冻结的 Qwen3-8B 在 k=128 下评两次，25 道没做出来的 AIME 题"扩展"了 7 道，**expansion rate = 0.280**。
- **F7（藏在 F2 的修复里）**：七次全是单次幸运采样，看似可以用"要求 m≥2 次成功"修好并把 null 压到 0。不行——那个结论只基于一次冻结对比；在他们实验天然包含的 **110 次**冻结对比上，null 是 **0.058 [0.038, 0.078]**，比它本该认证为零的那个值还大。
- 另外还有：固定 token 上限遇上风格漂移会把最有效的臂判成最有破坏性的（F3）；transition 类指标比 accuracy 少约 **10× 统计功效**，112 题的 pilot 根本分辨不出来（F4）；训练种子方差让同一方法的 clr 横跨 0.55–1.53（F5）；欠功效的探针造出一个 10 个点的幽灵安全性下降（F6）。

修好之后的实质结论：**外部蒸馏**能改善 base 模型极少触及的题（22 题里 8–11 题），**三种自训练形式都不能**（0–2 题），且回归排除了"这只是蒸馏总增益更大的副产品"（β=1.91，p<10⁻⁸）。同时自训练在 1,163 道 band 题上破坏了 88–106 道，对照的设计匹配地板是 8 道。

**全文验证检查单**：

1. **预印本时间线**：v1，2026-08-20 首次提交，无换壳重投痕迹。
2. **数据采集窗口**：不适用（受控实验非调研）。
3. **代码仓库**：[github.com/chengxuphd/phantom-gains](https://github.com/chengxuphd/phantom-gains)，Apache-2.0，创建于 2026-08-19。README 明确写"论文里每个数字、表、图都由 `analysis/` 脚本从仓库文件重算，没有一个是手抄的"，且**复现不需要 GPU、不需要网络**。反面：仓库是全新的（0 star、1 个贡献者、2 次提交），还没被任何第三方验证过。
4. **基线公平性**：这篇的对照设计本身就是论点——冻结对照走同一条管线，正对照（外部教师蒸馏）在数据流、保留量、评测三方面对齐。这是本周最扎实的一处。
5. **适用边界**：单模型族（Qwen3-8B）、只测 LoRA、3 轮。**具体数值不要外推**（0.280 这个 expansion null 是 Qwen3-8B + AIME + k=128 的产物）；可以外推的是方法论——"每个报出来的统计量都要配一个单独测量的 null"，以及那个几乎白送的观察：**多臂实验里每条臂的 checkpoint 0 都是对未训练模型的一次独立评测**，null 不需要新实验就能建。作者自己也说明了这需要多少条复现才可信——比大多数三臂研究拥有的要多。

**谁该读**：所有做微调/后训练并向别人汇报"提升了多少"的人；所有维护内部 eval 看板的人。你不做自训练也该读第 4 节——F1（batching 下贪心不确定）和 F4（逐题指标功效低 10 倍）打的是任何"A/B 比较逐题差异"的做法。

## 硬件

**FlashPrefill V2: Block-Sparse Prefill Attention for Long-Context LLM Serving** · CASIA MAIS&NLPR + 中科院大学 + 微信/腾讯 · 2026-08-20 · [arXiv:2608.19758](https://arxiv.org/abs/2608.19758) · 【全文】

把稀疏 prefill 从算法原型推到能进生产：mean correction 项（把被剪掉的块用其池化 K/V 统计量补回 softmax 分子分母，救极端稀疏度下的精度）、按 FA3/4 对齐重写 kernel（PackGQA、warp specialization、pingpong pipelining、FP8）、原生支持 paged KV cache 和 continuous batching，可作为 SGLang 的 attention backend 接入。

**关键是把哪个数字当真**。标题数字 47.26×（FP8@128K）是对 **FlashAttention-2** 的——在 Hopper 上这是个过时基线。对 FA3/4 对齐的稠密基线是 30.49×（FP8）/ 17.54×（BF16），但这个比的是稀疏 vs 稠密，量的主要是稀疏率不是 kernel 水平。真正能拿去做决策的是**端到端**：接进 SGLang 后 128K 的 TTFT 降 **4.8×**。47× 和 4.8× 之间差一个数量级，这个 gap 本身就是本条最该记住的东西。

**全文验证检查单**：① 时间线干净——是公开声明的 V2，前作 FlashPrefill 是 [arXiv:2603.06199](https://arxiv.org/abs/2603.06199)（2026 年 3 月），不是改名重投；但要意识到 V2 的增量是工程（kernel + 分页）而非算法。② 数据窗口不适用。③ 代码：前作仓库 [qhfan/FlashPrefill](https://github.com/qhfan/FlashPrefill) 2026-02-06 建、54 star，**接入方式是对 vLLM 0.10.0 / 0.12.0 的 patch loader**——跟 EcoServe 一样的形态，采用即长期背 rebase。V2 的 SGLang 集成代码目前**未见发布**。④ 基线见上。⑤ **边界最关键：全部实测只在 H20 上**（batch size 4）。H20 是 Hopper 的中国特供 SKU，BF16 算力被大幅削减而 HBM 带宽基本保留——省算力类优化（稀疏注意力正是）在这种算力/带宽配比上会被系统性放大。**同一份 kernel 搬到 H100/H200/B200，收益预期显著缩水**，论文没测。

**谁该读**：在 H20/国内卡上自建长上下文推理的（这篇几乎是为你写的）；跑 SGLang 且 prefill 是瓶颈的。不在 Hopper 特供卡上的，读 mean correction 那一节的思路就够，数字别抄。

**PTXBench: Benchmark and Adapt LLMs for GPU Kernel Optimization with Architecture-specific PTX** · Stanford（Olukotun 组）+ CMU + RadixArk · 2026-08-18 · [arXiv:2608.17379](https://arxiv.org/abs/2608.17379) · 【仅摘要】

在 H100 和 B200 上测 LLM 用架构专属 PTX 写 kernel 的能力，同时量三件事：功能正确性、**目标指令是否真的在运行时被执行**、以及相对前沿库的加速比。结论偏负面且有用：能力很不均衡，复杂 attention backward 上成功率大幅下降；而且**"确实执行了目标指令"并不等于"性能有竞争力"**——这两件事被拆开测是本篇最大的方法论贡献。**没有任何被评模型能在整个套件上稳定匹配前沿库**。作者另用 SFT 适配了 Qwen3.6-27B，repair-conditioned 训练在若干任务上有改善。

与上周的 CAKE、以及本周落选池的 KernelArc 连读：agentic kernel 生成已经形成一条明确的线，但 PTXBench 是里面唯一认真区分"看起来对"和"真的快"的。

**谁该读**：写 kernel 的；正在评估要不要让 agent 参与 kernel 优化的（先读这篇再读 CAKE/KernelArc 的战报）。

**Learning how to Forget: Fine-tuning for Long-Context Sparse Attention** · AWS Labs · 2026-08-20 · [arXiv:2608.19920](https://arxiv.org/abs/2608.19920) · 【仅摘要】

给稀疏注意力做微调的方法：**对任何 KV cache 策略都适用**，让模型与策略协同适配，而不是把稀疏策略当推理期的事后手术。两个落地向的点——一是硬件预算低到**单张 A100 40GB** 就能跑；二是协同适配后**常常超过用精确注意力（序列并行）训出来的模型**，也就是说这不只是"省显存的妥协"。他们实验里 H2O 是最强策略，并给了配套的 SDPA kernel 实现。配套开源库 KeysAndValues：[github.com/awslabs/keys_values](https://github.com/awslabs/keys_values)。

注意这是【仅摘要】级：单卡 40GB 这个说法适用于什么模型规模、"常常超过"的 often 有多 often，都没核。

**谁该读**：要在有限卡上做长上下文微调的；已经在用 H2O / KV 驱逐策略但只在推理期用的——这篇说的是你可以把它训进去。

受控的 LoRA-GRPO / RWKU 设置下比四种奖励设计（词汇级抑制、反拒答塑形、rubric 式宽答、显式拒答对比），带与不带 SFT warm-up。核心结论是负面且可迁移的：**优化成功 ≠ 行为改变**。RWKU forget 分数、留出集补全审计、终态训练 rollout 审计、训练动态——四个视角会指向**互相矛盾**的结论。作者把分歧归因到奖励 hacking 端点、GRPO 的 policy-support 限制、以及 benchmark 探针本身的错配。

## 软件系统

**FleetSieve: Decision-Critical Profiling for SLO-Aware LLM Fleet Configuration** · 2026-08-20 · [arXiv:2608.19659](https://arxiv.org/abs/2608.19659) · 【全文】

问题：给推理集群选 TP 度数和副本数很难，因为**性能对 TP 不单调，且可行解会随负载变化**。穷举 profiling 能解决，但大量测量对最终分配决策毫无影响。FleetSieve 按"这次测量预计能多大程度改变下游分配决策"来选测哪一格，联合建模容量与尾延迟，当保守解与乐观解的差距低于容差就停。

**但本条真正值钱的不是这个方法，是它顺手测出来的两个事实**：

1. 在 Chat C128 负载点上，**TP4 和 TP8 都能服务 11.27 req/s，但 completion-p99 分别是 46.4 秒和 25.2 秒**——只有 TP8 过得了 30 秒的 SLO。**吞吐相同时可行的 TP 仍然不同**。只看吞吐选并行度的做法在这里直接翻车。
2. 16 卡分配下，用稀疏 profiling 做出的错误决策，在 1.3× 需求时损失 1.93 req/s 和 12.4 个百分点的 max-min 满足率；0.7× 需求时富余容量把这个错误完全掩盖住了。**你在低负载下测不出配置错误。**

方法本身的收益作者报得很诚实：固定对比下 22,200 GPU-秒，比均匀随机省 6.9%；200 次随机揭示顺序下平均省 5.4%（95% bootstrap CI 3.5–7.2%）；Chat 类省 21.5%，**Code 类它不是最省的**。

**全文验证检查单**：① v1，2026-08-20，无换壳。② 不适用。③ **未见代码仓库**——这是本条最大的短板，方法要自己重写。④ 基线充分：对比了均匀随机、固定网格序、联合最大不确定度、共享特征代理、定向主动学习、value of information、约束贝叶斯优化，全部同起点同候选表同 SLO 同分配器。⑤ 边界：**单节点 H100、31B 开源模型、FP8、vLLM 栈、TP ∈ {2,4,8}、投机解码关闭**；负载是公开 Azure conversation/code trace。跨节点、MoE、开投机解码都没测。作者自己承认"其价值仍依赖具体 workload 与标定"。

**谁该读**：自建推理集群、正在选并行度和副本数的（就为那两个事实也值）；做容量规划的。方法要不要抄看你 profiling 预算，6.9% 未必值得自己实现一遍。

**The Working Set of a Coding Agent: Coherence Debt in Repository-Scale Tasks** · 2026-08-17 · [arXiv:2608.16630](https://arxiv.org/abs/2608.16630) · 【仅摘要】

把仓库级编码建模成"重建一张耦合事实图"：每次编辑需要的事实要么来自近期上下文，要么来自参数记忆，两条通道都没覆盖的部分叫 **coherence debt**。作者对七个模型、五种 harness 逐一供给/撤走每条通道并注入故障。数字很硬：

- 四个虚构 API 迁移的 154 次闭卷试验中，**没有任何模型完成过一次**；把同样的事实放进 prompt 后，300 次匹配试验有 **299 次**达到 12 条要求中的至少 9 条。
- 真实 Pydantic 迁移的"改名孪生版"上（让记忆失效），**七个模型的 70 次试验里有 66 次停在同一个分数，各自通过 79 个测试中完全相同的 24 个**。
- **可用性决定结果，距离不决定**：撤走一个事实，代价恰好等于它支撑的那部分工作，损伤随撤走量线性增长；而供给的事实在 128,000 字符上下文的最远端和紧挨编辑处一样好用。
- **全都通过所有测试的 harness 配置之间，token 消耗差十倍以上**——因为它们以不同频率重建同样的内容；而事实被撤走时，多花钱一点也救不回来。
- 缺事实产生的是**错的工作而不是没有工作**：agent 被要求动手就会动手，编造文件或猜值——**所以建立在"读了什么"上的观测手段，看到的是一个已经被填上的洞**。
- 标准与代码冲突时 agent 跟标准走，哪怕标准规定的是更差的代码：**一份过时的 convention 文件比没有文件代价更高**。
- SWE-bench 上因为模型多半已经记住了那些仓库，"读取行为"不再预测成功——这解释了一批基于读取轨迹的评测为什么测不出东西。

**谁该读**：写 agent harness / CLAUDE.md / 项目规则文件的所有人（尤其"过时的 convention 文件比没有更糟"和"观测要看产出不看读取"这两条）；做 agent 可观测性的。

**When Is Complex Chunking Worth It? A Multi-Objective Evaluation of Chunking Methods at Scale** · CIKM 2026 · 帕绍大学 + IT:U Linz · 2026-08-17 · [arXiv:2608.16586](https://arxiv.org/abs/2608.16586) · 【仅摘要】

八种 chunking 策略（token / sentence / late / 标题增强 / 摘要增强 / contextual / summary / semantic）× 两个可扩展语料 × 三个 embedding 模型 × 多种语料规模，**同时量检索效果和系统成本**（文档吞吐、查询吞吐、峰值内存）——后半截正是以往 chunking 对比普遍缺的。

结论：**计算昂贵的方法很少能稳定超过简单方法**；最优策略取决于 embedding 模型、数据集、语料规模和目标指标四者的组合，没有普适赢家；而且**效果相近的方法在运行成本上可以差很多**，所以 chunking 应当被当成多目标设计决策而不是"选个最好的"。代码 [github.com/casparil/chunking-eval](https://github.com/casparil/chunking-eval)，数据集在 HuggingFace。

**谁该读**：做 RAG 的所有人。特别是正在考虑上 contextual chunking（那种要为每个 chunk 额外调一次 LLM 的）之前。

## 判断账本动态

**印证 4 条**：

- **J1**（推理优化必须在你真实的并发分布下重测）——FleetSieve 补进一个新形态的证据：不只是"加速比会变"，而是**吞吐相同时 SLO 可行性仍然不同**（TP4/TP8 都跑 11.27 req/s，p99 46.4s vs 25.2s），且低负载会掩盖配置错误。
- **J2**（约束别写在 tool/skill description 里，位置权重决定生效强度）——Working Set 从反方向印证了"项目文件权重高"：agent 在标准与代码冲突时跟标准走，**过时的 convention 文件比没有文件代价更高**。J2 的边界项已相应补充。
- **J6**（Agent 可靠性靠系统级设计，验证者须独立于生成者）——Working Set 追加：全部通过测试的 harness 配置 token 消耗差 >10×；且"缺事实 → 编造而非阻塞"意味着**建立在读取行为上的验证器测不到东西，验证必须打在产出上**。
- **J7**（RAG 里系统级决策压过算法选择）——When Is Complex Chunking Worth It 强印证：昂贵 chunking 很少稳定胜出，最优解随 embedding 模型/数据集/语料规模/目标指标漂移。

**新增 2 条**：

- **J13**：逐题/逐项的差分类指标（transition、expansion、pass@k）必须配单独测量的 null 或冻结对照臂，否则冻结模型自己就能刷出"能力变化"。支撑：Phantom Gains（冻结 Qwen3-8B 的 expansion null = 0.280，clr = 1.5；修复后的 m≥2 阈值 null 仍有 0.058）、Beyond Pass@k（pass@k 的 n 被误当成单次提交的测试数，绝对值虚高 0.85–0.97）、Measurement Without Validity（三层复合上界 V_total ≤ V₁×V₂×V₃）。
- **J14**：读任何 kernel/量化加速比，先查它测的是哪张卡的算力-带宽配比；中国特供 SKU（H20/L20）算力被砍而带宽保留，会系统性放大"省算力"类优化的收益。支撑：FlashPrefill V2（H20 独测，47× 微基准 vs 4.8× 端到端）、EcoServe（L20 特供卡，结论迁移性存疑）、Attn-QAT（同 kernel B200 1.3× → B300 1.74×，差在指数单元）。
