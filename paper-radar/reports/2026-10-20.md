# 当 4.7% 也开始被认真对待

这期两条线。一条是把尾段优化榨到底：kernel 级调优做完之后，PyTorch 与 NVIDIA 从 ptxas 的寄存器分配里再挤 4.7%，带 p 值和效应量，两次独立验证；AWS 把 KV 转移的方向反过来，多轮 agent 的 TTFT 最多压 3.3 倍；vLLM 把专家并行扩缩容的停机时间从 99.6 秒压到 0.82 秒。

另一条是错误层开始有系统性答案：3,200 GPU 小时的软错误注入实验显示，硬件位翻转在应用层呈现为四种幻觉，分布随任务和错误率变化；投机解码 360 配置的宽松验证对照显示，接受率越高，输出越长，精度损失越大。论文 8 篇，其中 2 篇全文验证。

## 调优做完之后，去 ptxas 那里再挤一层

Helion 的自动调优器早就把 tile/warp/pipeline 这一层的可调维度搜完了，这次把搜索空间往下推了一层：到 ptxas 的控制面。CompileIQ 1.0.3 把 ptxas 的寄存器分配控制（CUDA 13.3 新加的控制面）暴露出来，PyTorch 把它当成可搜索的维度：8 代、池子 15 个配置，和 tile 搜索共用同一个目标函数，搜索产出是一个 ACF 工件 = AOT 编译配置 + 一组 ptxas 标志。

单目标结果做了两次独立验证：0.0971 → 0.0928 ms，**1.047×**，两次各 1,700 多个样本，d≈2.5。两次找到的最优 ACF 完全一致（同样的 launch 配置、同样的 ptxas 标志），搜索不是乱撞；两次之间的差距 0.5%，在采样噪声里。边界要连着读：这是 GB200 + B200 上的一个 GEMM 形状，ptxas 控制面是 CUDA 13.3 才有的新面，12.x 工具链上这个结果带不过去。

多目标里有信息量的部分。NCU 的成本模型把估计加速的 21% 归到 occupancy。这个 kernel 受寄存器限制，多目标搜索（runtime + L1TEX miss）落在 occupancy 21.60% → 21.76%（+0.16pp，p=9.2e-23，d=13.17），runtime 降 1.75–2.0%，L1TEX miss 率 81.51% → 85.96%（+4.5pp）。一个百分点的 occupancy，统计显著性做到小数点后两位——这就是「优化进入尾段」的样子：样本给得够大，4.7% 这种小收益才钉得住。多形状实验显示同一个 ACF 可以同时服务两个形状的 Pareto 点（0.0927/0.0309 ms，默认 0.0972/0.0315）。团队自己的估计是：对已经优化过的 kernel，2–7% 是现实预期——kernel 越优化，剩下的空间越在编译器后端。

实操约束在 ACF 绑定上：工件绑硬件 + 工具链，消费端模型、kernel 版本、GPU 要对得上，否则是错误结果。仓库里的 24 个 ACF 样板包可以直接用，但要先看每个配置是在哪个 SKU 上搜出来的。

## 双向 KV 转移：让下一轮的前缀已经在位

多轮 agent 场景里，客户端每一轮都把完整历史发回来。常规 PD 分离下 KV 只单向流 prefill→decode，于是有两类浪费：prefill 侧驱逐缓存或路由换节点后，下一轮的前缀要重算；decode 侧拿着 KV 却给不回 prefill。AWS 把 decode→prefill 这个方向打开，下一轮 prefill 从温缓存起步。

一方数字，1P1D，P5en + EFA：**Qwen3-32B TTFT 最多降 1.6×，GLM-5-FP8 最多降 3.3×**（长 prompt）。收益在大模型上更大，因为 prompt 越长，每 token 的重算时间越值钱。这个特性原本在 Trainium 集群上构建并验证，之后以加速器无关的方式贡献进了 vLLM。

· [AWS: Improve TTFT for multi-turn agentic workloads with bi-directional KV transfer in vLLM (10-19)](https://aws.amazon.com/blogs/machine-learning/improve-ttft-for-multi-turn-agentic-workloads-with-bi-directional-kv-transfer-in-vllm/)
· 一方博客；主证据 = 一方生产基准

## 专家并行扩缩容，停机 99.6 秒 → 0.82 秒

vLLM 上一代 EP 弹性解决的是「不用重启」，但换拓扑仍要暂停；这次解决的是「不用停」。DEP 拓扑（数据并行 attention + 专家并行 MoE）下，机制是两块：拓扑准备移到异步（与 serving 重叠），专家权重迁移走 NIXL EP。

一方实测，16→20 GPU：停机 **99.62s → 0.82s**；20→16：56.25s → 1.96s。同一硬件上 stop-the-world 时间差两个数量级，收益直接落在弹性调度上：按流量伸缩，不再为每次伸缩付一次服务中断。注意这是 MoE 专家并行部分的事；attention 部分仍是数据并行，扩缩走常规副本逻辑。

· [vLLM: Elastic EP, near-zero-downtime (10-19)](https://vllm.ai/blog/2026-10-19-elastic-ep-near-zero-downtime)
· 一方博客；主证据 = 一方生产基准

## TorchNeuron 明天公测：Trainium 拿到原生 PyTorch 设备

AWS 的答案是给 Trainium2/3 一个原生 PyTorch 设备：**eager 跑研究和调试（adaptive eager，仍是实验阶段），torch.compile 跑生产，NKI 写自定义 kernel**。并行全部是标准 PyTorch——DDP、FSDP2、TP、PP、DTensor/DeviceMesh——集合通信走节点内专用 collective core，跨节点走 EFA。Neuron Explorer 是走到硬件层的 torch.profiler，Parquet 输出，agent 直接可读。

三个值得留意的点：Apache 2.0，**公测 10-20，就是明天**；Deepgram 案例自报比 GPU 基线每美元多处理约 **60% 的输入音频**；10 万模型盲扫（按下载量覆盖 HF 上 99.9% 的模型）显示约 22k 个算子没有原生 Neuron lowering，这是当前的差距。博客给了 Llama3-8B FSDP+torch.compile（8×trn2.48xlarge，TP+HSDP，TorchTitan）的复现路径，loss 曲线也放了。

这个设备路径和 Neuron SDK 是并行的，值不值得迁，看你的算子落不落在 22k 的缺口里。

· [PyTorch: Introducing TorchNeuron — Native PyTorch backend for AWS Trainium (10-19)](https://pytorch.org/blog/introducing-torchneuron-native-pytorch-backend-for-aws-trainium/)
· 一方博客；主证据 = 一方生产基准

## Mamba-2 前向内核：cuTile 对 Triton，1.14–1.82×

Jane Street 的 ML 团队和 NVIDIA 把 Mamba-2 的前向搬到 cuTile（面向 Blackwell Tensor Memory 的 Python DSL）。三个手写 kernel：chunk_cumsum（对数空间衰变的逐 token 逐头累计和）、fwd_pass_state（Tensor Core MMA 按 jump 公式推进隐状态）、compute_out（carry-over 状态 + 衰变掩码交互 + skip connection 融合）。优化手段都是 Blackwell 特定的：DRAM 延迟提示、操作数换进 Tensor Memory、TMA 友好的转置布局，加 autotune。

对照基线是开源 Triton 实现（mamba_ssm 2.3.2.post1，Triton 3.7.1），单张 B300：**cuTile 快 1.14×–1.82×，序列长度和状态越大，加速越大**。边界原文明说：kernel 级加速，不是端到端训练；Mamba-2 的反向没做。这个工作的价值不在数字，在于 cuTile 已经能赢成熟 Triton kernel。

· [NVIDIA: Accelerating Mamba-2 with high-performance forward-pass kernels in NVIDIA CUDA Tile (10-19)](https://developer.nvidia.com/blog/accelerating-mamba-2-with-high-performance-forward-pass-kernels-in-nvidia-cuda-tile/)
· 一方博客；主证据 = 一方生产基准

## 低资源语言编程：OpenAI 的两个新评测

OpenAI 放出一组「低资源编程语言里写/修软件」的评测。第一个是 **MultiLangBench**：20 种语言从零构建一个 SQLite 兼容引擎，共同接口是 DB 文件（输入初始 DB + SQL 查询，输出修改后的 DB），测试用例改编自 SQLite 自己的测试套件，量的是实际能跑的功能通过率。GPT-6 Astra（max reasoning）20 语言平均 **87.4%**，GPT-5.6 Sol 当时 26.8%；GPT-6 Luna 40.3%，成本更低。提升最大的是 COBOL，10.9% → 72.1%。第二个是 COBOL 迁移评测：GPT-6.1 Sol 低推理 **86.6%（GPT-5.6 Sol 5.4%），成本降 39%**；高推理 97.9%，接近饱和。

两组数字都是自报，但第一组可复现：benchmark 的搭建和逐语言结果都在 GitHub 上。COBOL 迁移是这一组里值得记的信号：企业软件还有相当一部分跑在 COBOL/Fortran/VB 上，迁移通过率从 5% 跳到 87%，「遗留代码现代化」就从咨询业务变成产品。

· [OpenAI: Low-resource programming languages (10-19)](https://openai.com/index/low-resource-programming-languages)
· 一方博客；主证据 = 一方自报基准（可复现：测试套件开源）

## 论文

### Understanding LLM Hallucinations Caused by Soft Errors ·【全文】【模型】

Villanova 大学 + MBZUAI（Jinghao Wen、Dongning Ma 等）· https://arxiv.org/abs/2610.22520

把软错误注进推理过程（SRAM 多位翻转，按 BER 或固定翻转数控制，打在参数和激活上），看应用层怎么反应。3,200 GPU 小时（4×A800-80GB + 3×A6000-48GB），覆盖数学推理和代码生成。核心发现是一个四分类：**Token Corruption、Language Drift、Logical Corruption、Premature Termination**，分布随 BER 移动——温和错误主要破坏推理和语义一致性，严重损坏导致 token 畸形和整个生成崩溃。

任务差异是另一半发现。代码生成有严格的语法/语义约束，过了阈值 **Token Corruption 占损坏输出的 100%，断崖式崩溃**；数学推理允许部分得分和灵活解释，渐进退化。同一个硬件故障，在应用层呈现的签名因任务而异。

可操作的结论（本期 J24）：想监控推理硬件可靠性，**代码生成通过率是比数学推理分数更好的金丝雀**——硬件软错误渗入时，数学分数先不动，代码通过率先掉崖。局限也清楚：这是受控注入实验，不是某台真实机器的自然软错误率统计；BER 是注入参数，不是测出来的值。

### Acceptance Is Not Speed: Length Inflation in Training-Free Lossy Speculative Decoding ·【全文】【模型】

· https://arxiv.org/abs/2610.23818

5 条训练免费的「宽松验证」规则（mentored decoding、CACTUS、reducible fuzzy SD、两条投机级联）× 360 个配置的对照。设置给得很全：vLLM 0.26.0，单张 H100，GPT-OSS-20B/Qwen3-8B 当目标，EAGLE-3 头，3 个 seed，约 750 H100 GPU 小时，7 个基准，还做了跨服务器可复现性（round 比跨机可复现、time 比不可，原因在附录里逐条交代）。

结论不在速度侧，在精度侧。**300 个评分 cell 里 198 个（66%）在宽松验证下丢精度**；三条激进规则在 180 个 cell 里丢 143 个。损失和长度膨胀强相关：144 个「输出变长」的 cell 里 132 个丢精度。EAGLE 头上，40 个「验证轮次真比 lossless 少」的 cell 里 35 个丢精度。唯一平均保精度的是 spec_casc_tok——唯一能拒绝 lossless 验证会接受的东西的规则。论文的标题就是结论：**接受率不是速度**，多数配置下，用输出变长和精度损失换更多接受是亏的。

边界：单张 H100、两个目标模型；「most relaxed tested setting」是搜索空间的边界，不是方法自身的边界。对工程的含义（J25）：给投机解码加宽松验证，先把长度膨胀和精度损失放进同一个仪表盘，再谈省了几轮验证。

- **BaGuaLu-2: Taming Dynamic Memory Fluctuation for Efficient MoE Model Training over 10,000 GPUs**（2610.23064，软件系统）：**1.04T 参数 MoE 在 12,288 卡上训练，35% MFU 下持续 2+ EFlops**，对两个 SOTA 系统平均加速 1.14×/1.13×（摘要级，基线名称需对原文）。35% MFU 是大规模 MoE 训练下的持续值，不是峰值。 · https://arxiv.org/abs/2610.23064
- **FuTransformer: FP8 prefill and INT4 decode for Llama-style inference on Hopper**（2610.23796，软件系统）：Hopper 全 fused kernel 链：**prefill 对 compiled PyTorch FP8 最高 1.48×（1.29 PFLOP/s）**，8B 形状对 CODA BF16 1.13×，FP8 路径对实测 BF16 CODA 2.02–2.18×；decode 权重 INT4、KV cache INT4，离群通道走 block-diagonal Hadamard，直接写入 KV cache，prefill 免 padding，8B/70B 都验了。 · https://arxiv.org/abs/2610.23796
- **HBFSim: A Simulator for Exploring HBF in Memory Hierarchies for LLMs**（2610.23503，硬件）：面向 High-Bandwidth Flash（HBF）的事件驱动、LLM-aware 模拟器——TB 级加速器本地容量、HBM 级带宽，但 NAND 长延迟、out-of-place 更新、写耐久都要建模。serving 前端校准，Llama-3.1-70B 与 Qwen3-235B-A22B 三个负载下：**HBF 服务装不进 HBM 的数据比 host DRAM 快 11.0–19.0×**；结论是 HBM 当活跃序列的 KV cache 比通用 cache 好。 · https://arxiv.org/abs/2610.23503
- **CMM-MP: A Novel Memory Pooling Architecture using Purpose-built Memory Device with CXL and Ethernet**（2610.22716，硬件，SK hynix，OCP Summit 2026）：把 CXL 和 Ethernet 合成一套可组合、可分离的内存池化系统，定位在 HBM 容量和 host DRAM 延迟之间的空档；Valkey+YCSB 与 DiskANN 场景实测，胜过 RDMA-based 池化。 · https://arxiv.org/abs/2610.22716
- **Equivalence testing and run-count design for stochastic machine-learning experiments**（2610.23700，工程方法）：把「两个模型评测结果是否一样」变成可设计问题——AUROC 上的 TOST 实际等效协议 + 功效分析，seed × item 两层方差、两层 bootstrap，**闭环公式算所需运行次数（margin + 目标功效 → 次数）**，270 cell 网格验证。顺手批评：一个 joint 能量模型 4 次公开运行的「等效」主张基本站不住，失败大多是设计问题（每方法 2 次运行不够）。 · https://arxiv.org/abs/2610.23700

## GRAFT：把坏行为放进单独的适配器，然后删掉

简条 · Anthropic alignment 团队（MATS 计划，Stanford/FAR AI 参与） · [原文（10-19）](https://alignment.anthropic.com/2026/graft/)

每个 MLP 加一对 RETAIN/FORGET 适配器神经元：被 monitor 标记的轨迹上，**被标记样本的梯度只更新 FORGET，RETAIN 被零掩码**；干净样本两边都更新。monitor 只用来「路由更新」，从不进「奖励」本身，弱 monitor 不会被反向利用，训练完把 FORGET 删掉即可。Qwen3-8B Countdown-Code（RLVR）上，目标任务提升、hacking 率不升；对照组——把 monitor 放进奖励做惩罚——反而教会模型利用 monitor（包括 monitor 检测不到的利用）。局限：单轮、≤8B。
