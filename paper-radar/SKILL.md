# AI 工程化论文雷达

为个人技术认知服务的论文雷达：跟踪技术动向和好的工程化实践。**不做**「你们能不能落地」的业务过滤——每篇标注「谁该读」，把适用性判断留给读者。

**论文是主干，非论文单独成节**：工程博客、技术报告、上游变更、社交快讯都收，但分级标注、独立配额、绝不与论文混排（硬规则 5）。

本 skill 的每条硬规则都来自一次真实翻车（见各规则括号注）。绕过规则 = 重演翻车。

**路径规则**：`state/` 与 `reports/` 都在本 SKILL.md 同目录下。触发后先定位 skill 自身目录（**不能假设当前工作目录就是 skill 目录**），所有账本与报告读写一律用该目录下的绝对路径。找不到 `state/seen-papers.md` 时是路径解析错了，不是账本不存在——禁止在别处新建空账本从零开始（那会让去重全失效）。

## 三种模式

- **周扫**（无参数，`/paper-radar`）：扫「上次扫描日期 → 今天」的窗口（日期记在 `state/seen-papers.md` 头部；缺失则回退 7 天）。四条线全扫。
- **定向**（带主题，如 `/paper-radar agent记忆`）：按主题捞，临时收窄范围。**下次无参数周扫自动回到四线全幅**，定向不改变常驻范围。
- **单篇验证**（带论文或非论文链接/标题，如 `/paper-radar 验证 <arXiv链接>`，或用户直接问「这篇靠谱吗」）：论文走全文验证检查单，非论文走来源核验四项，出单篇验证报告；结论照常联动两个账本。

三种模式共用同一套溯源、账本规则；体量规则适用于周扫与定向。

## 周扫执行流程

严格按序执行，每步完成才进下一步：

1. 定位 skill 自身目录，读 `state/seen-papers.md`（含头部「上次周扫」日期）与 `state/judgments.md`。
2. 确定窗口：上次周扫日期 → 今天（缺失回退 7 天）。窗口 >10 天可声明扩容（硬规则 8）。
3. 四条线逐线搜**论文**，每线 2–3 个角度（硬规则 3、4），候选逐条对账本查重。
4. 另起一轮搜**非论文信源**（一方博客 / 工业博客 / 技术报告 / 上游变更 / X 快讯），候选走硬规则 10 核验、逐条对账本查重。
5. 选出首推 2–3 篇论文（本周只读一篇 + 各线第一名），走全文验证检查单（硬规则 7）；另从非论文里选一条「本周值得一读的实践」。
6. 写报告到 `reports/YYYY-MM-DD.md` 并在对话中完整给出。
7. 回写 `state/seen-papers.md`（新推条目含落选池与非论文详条目，每条带 ID/链接；快讯不写），顺手折叠满 6 个月的旧条目，更新「上次周扫」日期。
8. 回写 `state/judgments.md`（印证/存疑/新增），与周报「判断账本动态」一节对齐。
9. **落档**（硬规则 9，见下文「落档」一节）。
10. 过一遍「交付前自检」清单（见文末）。

## 四条固定线

| 线 | 覆盖 |
|---|---|
| 硬件 | GPU 微架构与精度（FP4/NVFP4）、CXL/内存池化、kernel、互联带宽、SDC/坏卡、集群可观测性与容错 |
| 模型 | 架构（混合/线性注意力、MoE）、量化与压缩、微调方法（LoRA/SFT/RL 配方） |
| 软件系统 | 推理服务与调度、KV cache、Agent 编排、Agent 记忆、RAG、向量检索、RL 后训练基础设施 |
| 工程方法 | 评估方法论、实证/校准研究、负面结果、benchmark 批判、harness 科学 |

**硬规则 1｜叠加不替换**：用户中途补充的维度（「也要看硬件」「多来点 agent 的」）一律做**加法**，绝不把之前的维度筛掉。拿不准是收窄还是叠加时，默认叠加。（翻车：把「侧重硬件」理解成「只要硬件」，用户连补三轮才纠回来。）

**硬规则 2｜每线必报**：周扫报告四条线每线都要出现。某线没货就写「本线本周无值得推的」，不许静默跳过。（翻车：混合线性注意力整条线被漏了六轮，因为没有强制覆盖清单。）

**四条线只收论文**。非论文一律去「工程实践」节（硬规则 5）。注意命名消歧：第四条线「工程**方法**」是论文线（评估方法论、实证研究、负面结果）；「工程**实践**」是非论文节。两者不是一回事，写报告时别混。

## 信源

**硬规则 3｜主动调用 exa MCP**：skill 一经触发就用 `web_search_exa` 搜、`web_fetch_exa` 拉全文，**不等用户点名**，不用内置 WebSearch 替代。exa 不可用时必须在报告开头显式声明「本次未走 exa，覆盖面打折」，禁止静默降级。（翻车：用户被迫连发两条「还是要结合 exa的mcp」。）

**硬规则 4｜多角度搜**：每条线至少 2–3 个不同角度的查询——按 arXiv 时间窗、按会议名（含刚放榜的顶会）、按关键词簇。单角度会整线漏货：同一周按 arXiv 时间窗搜是「偏薄」，换角度搜完全不同。

**硬规则 5｜信源分级与隔离**：雷达收六类信源，但**分级、分区、分标注**，绝不混排。论文清单（四条线）永远只有论文；非论文一律进独立的「工程实践」节，配额独立，挤不动论文。（前身是「工业博客一律不进清单」——那条翻车是博客好读好写、混排时会稳定挤掉论文。现在博客进来了，但隔离带必须在，否则重演。）

| 标注 | 信源 | 能进哪 | judgments 里的地位 |
|---|---|---|---|
| 【论文】 | arXiv 预印本、会议论文、workshop 论文 | 四条线 + 本周只读一篇 | 主证据 |
| 【一方博客】 | 模型厂 / 框架方第一方工程博客（Anthropic、OpenAI、DeepSeek、Meta、vLLM 团队…） | 工程实践节 | 辅助证据 |
| 【工业博客】 | 大厂系统工程博客（Uber、Netflix、Shopify、Databricks、Character.AI…） | 工程实践节 | 辅助证据 |
| 【技术报告】 | 非 arXiv 的 tech report、model / system card、官方评测报告 | 工程实践节 | 辅助证据 |
| 【上游变更】 | 开源项目 release notes、RFC、设计文档（vLLM、SGLang、PyTorch、Ray…） | 工程实践节 | 辅助证据 |
| 【快讯】 | X 等社交平台资讯 | 只进快讯子节 | **禁止作证据** |

**首推恒为论文**：「本周只读一篇」只能从【论文】里选，非论文再好也不夺首推——工程实践节自己出一条「本周值得一读的实践」。

**非论文的搜法**（同样走 exa，同样多角度）：按来源方名字搜（`Anthropic engineering blog`、`vLLM blog`）；按项目 release 页（GitHub releases / 官方 changelog）；按主题 + 实践词（`engineering blog`、`in production`、`we scaled`）；X 快讯按账号或话题搜。

## 溯源

**硬规则 6｜每条必带可点击链接**（arXiv/DOI/会议页）。没有链接的条目不许出现。（翻车：用户明确要过「要有link」，交付的清单一个链接都没有。）

**硬规则 7｜溯源分层 + 强制标注**：
- 每条标注【全文】或【仅摘要】，让读者知道每个数字的可信度。
- **首推（本周只读一篇 + 各线第一名，合计 2–3 篇）必须全文验证**，走下面的检查单。
- 其余条目允许摘要级，但必须如实标【仅摘要】。

**全文验证检查单**（每项都来自摘要级推荐的实际翻车）：
1. **预印本真实时间线**——arXiv 首次提交是什么时候？是不是旧作换壳/改名重投？（翻车：EcoServe 是 2025 年 4 月旧作；MAP 改名 CAP 重投，数据没刷新。）
2. **数据采集窗口 vs 发表日期**——测量/调研类论文尤其要分开写。（翻车：MAP 12 月发表，数据是 4–11 月采的，读者按发表日期估新鲜度会错一档。）
3. **代码仓库状态**——开源吗？是不是老版本引擎的 source fork？维护活跃吗？（翻车：EcoServe 是 vLLM 0.7.3 fork，生产采用意味着长期背 rebase。）
4. **基线公平性**——对比的基线调过参吗？作者自评吗？
5. **硬件/版本适用边界**——结论绑在什么卡、什么规模、什么互联上？（翻车：EcoServe 的 L20 是中国特供卡，结论对 L40S/A10 不直接可迁移。）

**全文获取指引**：优先抓 arXiv 的 HTML 版（abs 页的 HTML 链接，或 `ar5iv.org/abs/<id>`）——PDF 经 exa 抓取常失败或丢公式表格。代码仓库状态直接看 GitHub 仓库页的 commit 活跃度和 fork 基线版本，不轻信论文里「code available」一句话。

**硬规则 10｜非论文必过来源核验**：工程实践节的每条详条目都必须**读原文**（不许只凭搜索摘要写），并过下面四项；过不了的降为快讯或直接不收。

1. **第一方还是转述**——转述必须回溯到原始出处并给原始链接。找不到原始出处的不收。
2. **可验证数字 + 上下文**——规模、卡型、版本、测量时间齐不齐？纯定性叙事（「我们重构后快了很多」）不进详条目。
3. **时间戳与版本绑定**——写于哪个版本？现在是否已被上游推翻？【上游变更】类尤其要核对当前版本。
4. **营销动机**——是不是自家产品发布稿？是的话必须另外给出可独立复现的方法或数据，否则降级为快讯。

核验发现的水分要**写进条目里**（如「无卡型与并发规模，数字不可与论文对比」），不是自己知道就算。

**硬规则 11｜快讯只当信号，不当证据**：【快讯】每条只准「一句话 + 发布者 + 原帖链接」，必须是可点开的**原始帖子**，不收二手转述、不收截图转述。快讯**不进 judgments、不进 seen-papers**，用途只有一个——提示下次值得定向捞什么。禁止拿快讯下任何工程结论。

## 体量（收敛纪律）

**硬规则 8｜三层金字塔，浮动上限**：
1. 报告开头强制「**本周只读一篇**」+ 一段理由（必须是全文验证过的论文）。
2. 论文详条目默认 **≤8 篇**；顶会放榜等丰收周、或窗口 >10 天的隔周补扫，可扩到 **≤12**，但必须在报告开头显式声明扩容理由——不声明就不许超 8。
3. 工程实践详条目 **≤4 条**，独立配额——不占论文名额，也不许借论文的扩容理由跟着扩。
4. 快讯 **≤5 条**，每条一句话。
5. 落选池 **≤5 条**，每条只准「标题 + 一句话 + 链接」。
6. 超出的直接不提。漏掉好过淹没。

**排序偏好**：负面结果和校准类论文优先——正向优化会被开源框架吸收，真正省钱的是「这个技术在你的场景下不 work」；且负面结论不受「信息更多 vs 协调更好」混淆的影响，天然更可信。

### 传输层：直接写文件

**用 Write 工具直接写 `$VAULT/radar/<文件名>.md`**（`$VAULT` = `/Users/okonma/Desktop/essays`）。不要读任何 `.vault-meta/transport.json`——那种快照会陈旧。

（2026-08-23 状态：这台机器 Obsidian 1.13.7，`obsidian-cli` 已随 brew cask 链到 `/opt/homebrew/bin/obsidian`，**可用**。仍然不用——理由是上面的 GUI 依赖，跟可不可用无关。）

### 笔记格式

frontmatter 用 YAML，正文是报告全文：

```yaml
---
type: radar
title: "周扫 2026-08-23"
mode: 周扫                        # 周扫 / 定向 / 单篇验证
window: 2026-08-17 → 2026-08-23   # 单篇验证填 -
paper_count: 8                    # 论文详条目数；单篇验证填 1
practice_count: 3                 # 工程实践详条目数；没有就填 0
created: 2026-08-23
updated: 2026-08-23
tags:
  - radar
  - paper
---
```

frontmatter 下面**原样贴报告全文**——不重写、不摘要、不删节。`reports/YYYY-MM-DD.md` 与 `essays/radar/` 里那份内容必须一致；两处若出现分歧，以 `reports/` 为准（报告要跟账本待在一起，否则会出现「归档里有这篇、去重账本里没有」的漏洞）。

### 已有 PDF 交叉引用

`essays/` 下已有的 PDF 就是用户手动存过的论文。写报告时如果某篇候选**在库里已有 PDF**，在该条目后面加一行 `📁 已在库：[[<PDF 文件名>]]`——vault 内 wikilink 可直接点开 PDF，让用户知道不用再下一遍。判断方式：把候选的 arXiv ID 和标题关键词去 `essays/` 下比对文件名（PDF 常按 arXiv ID 或标题命名，两种都要试）。

比对不上不用勉强——这是锦上添花，不是硬规则，别为了凑这一行去猜。

### 索引维护

每次落档后往 `essays/radar/_index.md` 的表格**顶部追加一行**（最新在上）：

```
| [[周扫 2026-08-23]] | 周扫 | 08-17 → 08-23 | 8 (+3 实践) | 2026-08-23 |
```

篇数列写「论文数」，有工程实践就追加 `(+N 实践)`；没有就只写论文数。**不加新列**——旧行是 5 列，加列会让历史行错位。

链接用 `[[wikilink]]`（vault 的 `newLinkFormat` 是 shortest、`useMarkdownLinks` 是 false，wikilink 才是原生形式）。`_index.md` 不存在就新建。

## 账本维护

### state/seen-papers.md（去重）

- 周扫**开始前先读账本**，已推过的论文不重发。
- 例外：有实质新信息（中了会、代码开源了、被后续工作反驳）→ 标 **【更新】** 重新进清单，并说明新在哪。
- 每次报告发出后，把新推的论文**追加**进账本（含落选池条目），并更新头部的「上次周扫」日期。
- 去重按内容不只按标题——同一工作可能改名重投（MAP → CAP）。
- **每条必须带 arXiv ID 或会议页链接**（无 arXiv ID 的会议论文至少带会议页链接）。没有 ID/链接，「按内容去重」和【更新】复查都做不到——防改名重投恰恰依赖 ID。2026-08-20 前的旧条目缺 ID 属历史欠账，再次遇到该论文时顺手补上。
- **非论文同样去重**：工程实践节的详条目写进账本末尾的「## 工程实践（非论文）」一节，格式带类型标注（`【一方博客】`等），链接用原文链接。**【快讯】不进账本**——半衰期短、噪音大，写进去只会让账本膨胀而挡不住什么（硬规则 11）。
- **折叠策略（防账本膨胀）**：条目满 6 个月后压缩成「`- [日期] 标题 · ID/链接`」单行，判词删掉——判词的价值已沉淀进 judgments.md，去重只需要身份信息。每次周扫回写时顺手折叠到期条目。

### state/judgments.md（工程判断账本）

跨来源收敛出来的判断是本雷达最值钱的产出，半衰期比任何单篇论文长。每条判断格式：结论一句话 + 支撑证据（来源列表）+ 适用边界 + 最后更新日期。

周扫时**双向联动**：
- 新论文**印证**某条 → 追加进该条的支撑证据，刷新日期。
- 新论文**反驳**某条 → 该条标 **【存疑】**，并在周报「判断账本动态」一节显式提醒，不许静默改写。
- 新的跨来源模式浮现（≥2 个独立来源指向同一结论，其中至少一篇是论文）→ 新增一条。
- 单篇论文的孤立结论**不进账本**——账本只收跨来源收敛的判断。
- **非论文不能单独把一条判断标【存疑】**——博客/技术报告与论文冲突时，写进该条的适用边界（如「某厂博客报告了相反现象，规模/卡型不同」），要标【存疑】得有论文级证据。否则一篇营销稿就能推翻多篇论文收敛出来的结论。

**证据规则**：支撑证据以【论文】为主。非论文（【一方博客】/【工业博客】/【技术报告】/【上游变更】）只能作辅助证据，必须标注类型如「（一方博客，辅助证据）」，且在单条判断的证据里**不得占多数、不得是唯一证据**——换言之每条判断至少要有一篇论文撑着。【快讯】一律不得作证据（硬规则 11）。

**退役规则**：账本只增不删。被彻底反驳的条目标 **【已废弃】** 并保留原文（负面结论有史料价值）；两条判断收敛合并时保留较小编号，另一条标 **【已并入 Jx】**；J 编号永不复用。

## 定向模式补充

- 报告结构同上，但只出主题相关的线，开头改为「只读一篇」+ 论文详条目 ≤8。
- 工程实践节与快讯同样出（限同主题），配额不变（≤4 / ≤5）。
- 搜索同样走 exa 多角度；同样查重、同样写账本。
- 定向问出来的论文照常记入 seen-papers.md，避免下次周扫重复推。
- 跑完照常落档（硬规则 9），文件名走 `定向 <主题> YYYY-MM-DD.md`。
- **定向模式不更新「上次周扫」日期**——该日期只属于四线全幅周扫。周三跑一次定向就把日期推到周三，下次周扫窗口会吞掉周日到周三其他三条线的论文。

## 单篇验证模式补充

- 输入是一篇论文或非论文（链接/标题），产出是单篇验证报告：逐项过检查单 + 一句话结论（值得读/当论点读/跳过）+ 谁该读。
- **论文**走全文验证检查单五项，必须拉全文（走全文获取指引），报告标【论文】【全文】；拉不到全文就如实说「仅摘要级验证，可信度打折」。
- **非论文**（博客/技术报告/release notes）走硬规则 10 的来源核验四项，报告标来源类型；结论只能进 judgments 作辅助证据，不得单独立判断。
- 验证过的对象记入 seen-papers.md（标注「单篇验证」），非论文记进「工程实践（非论文）」一节；结论与 judgments.md 双向联动（印证/反驳照常处理）。
- 跑完照常落档（硬规则 9），文件名走 `验证 <短名> YYYY-MM-DD.md`。
- 不更新「上次周扫」日期。
