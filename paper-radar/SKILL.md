# AI 工程化论文雷达

为个人技术认知服务的论文雷达：跟踪技术动向和好的工程化实践。**不做**「你们能不能落地」的业务过滤——正文说明方法的适用条件，把采用判断留给读者。

**报告是博文**：围绕具体技术问题组织标题、导言与正文，解释方法、结果和适用边界。论文、博客与 X 可以在同一主题下对读，行文明确各自的证据地位。研究过程与扫描统计保存在仓库，不进入阅读页。

本 skill 的每条硬规则都来自一次真实翻车（见各规则括号注）。绕过规则 = 重演翻车。

**路径规则**：`state/`、`reports/`、`scripts/`、`references/` 都在本 SKILL.md 同目录下。触发后先定位 skill 自身目录（**不能假设当前工作目录就是 skill 目录**），所有账本与报告读写一律用该目录下的绝对路径。找不到 `state/seen-papers.md` 时是路径解析错了，不是账本不存在——禁止在别处新建空账本从零开始（那会让去重全失效）。

执行细节拆在 `references/`：`sources.md`（脚本与各类信源怎么搜）、`charts.md`（stats.json 与三张图）、`archive.md`（落档路径与格式）、`editorial.md`（博文编辑规范）、`x-accounts.txt`（X 账号清单）。走到那一步再读。

## 三种模式

- **周扫**（无参数，`/paper-radar`）：扫「上次扫描日期 → 今天」的窗口（日期记在 `state/seen-papers.md` 头部；缺失则回退 7 天）。四条线全扫。
- **定向**（带主题，如 `/paper-radar agent记忆`）：按主题捞，临时收窄范围。**下次无参数周扫自动回到四线全幅**，定向不改变常驻范围。
- **单篇验证**（带论文或非论文链接/标题，如 `/paper-radar 验证 <arXiv链接>`，或用户直接问「这篇靠谱吗」）：论文走全文验证检查单，非论文走来源核验四项，出单篇验证报告；结论照常联动两个账本。

三种模式共用同一套溯源、账本规则；体量规则适用于周扫与定向。

## 周扫执行流程

严格按序执行，每步完成才进下一步：

1. 定位 skill 自身目录，读 `state/seen-papers.md`（含头部「上次周扫」日期）与 `state/judgments.md`。
2. 确定窗口：上次周扫日期 → 今天（缺失回退 7 天）。窗口 >10 天可声明扩容（硬规则 8）。
3. 跑 `python3 scripts/fetch_sources.py scan --since <窗口起点> --out reports/assets/<日期>/candidates.json`，拿到 AIHot 热点、关键词命中、必搜账号、HN 高分帖的候选池（硬规则 18，细节见 `references/sources.md`）。
4. 四条线逐线用 exa 搜**论文**，每线 2–3 个角度（硬规则 3、4），候选逐条对账本查重。
5. **非论文**：从候选池挑，再用 exa 补脚本盖不到的（硬规则 17）。工程实践分详 / 简两层，详条目走硬规则 10 核验；资讯按范围过滤；快讯只认 X 原帖。逐条对账本查重。
6. 选出重点解读的 2–3 篇论文，走全文验证检查单（硬规则 7）；选读能提供实现细节的工程博客，并核对 X 原帖。
7. 给每篇论文和每条实践详条目找解说（硬规则 16）：`fetch_sources.py lookup` 一次 + exa 一次，封顶。
8. 按本期主题写博文初稿到 `reports/YYYY-MM-DD.md`（硬规则 15）。
9. **过表述关**：整篇（含附录）走 `ra-人话` 与 `humanizer-zh`（硬规则 14）。
10. **出图**：写 `stats.json`（含 `graph`）、跑 `scripts/render_charts.py`、按需抓论文原图，统计图留在资源目录，解释论点的图才放进正文（硬规则 12、13，见 `references/charts.md`）。
11. 回写 `state/seen-papers.md`（论文、落选池、实践详与简条目，每条带 ID/链接；资讯与快讯不写），顺手折叠满 6 个月的旧条目，更新「上次周扫」日期。
12. 回写 `state/judgments.md`（印证/存疑/新增），与正文引用的判断保持一致。
13. **查链接再落档**：运行 `scripts/audit_links.py`，检查本期全部外链，并运行站点内部链接检查。失效地址找原始替代来源；无法验证的如实标出，不能把登录墙或抓取失败当成已验证可用。然后**落档**（硬规则 9，见 `references/archive.md`）。
14. 对话里只给本期网页、历史索引与 GitHub 原文链接 + 一句体量，**不贴报告全文**。
15. 过一遍「交付前自检」清单（见文末）。

## 四条固定线

| 线 | 覆盖 |
|---|---|
| 硬件 | GPU 微架构与精度（FP4/NVFP4）、CXL/内存池化、kernel、互联带宽、SDC/坏卡、集群可观测性与容错 |
| 模型 | 架构（混合/线性注意力、MoE）、量化与压缩、微调方法（LoRA/SFT/RL 配方） |
| 软件系统 | 推理服务与调度、KV cache、Agent 编排、Agent 记忆、RAG、向量检索、RL 后训练基础设施 |
| 工程方法 | 评估方法论、实证/校准研究、负面结果、benchmark 批判、harness 科学 |

**硬规则 1｜叠加不替换**：用户中途补充的维度（「也要看硬件」「多来点 agent 的」）一律做**加法**，绝不把之前的维度筛掉。拿不准是收窄还是叠加时，默认叠加。（翻车：把「侧重硬件」理解成「只要硬件」，用户连补三轮才纠回来。）

**硬规则 2｜每线必查**：周扫研究覆盖四条线，并在内部记录各线取舍。文章按主题组织，不强制使用四条线作标题；无合格材料的方向不写凑数章节。（翻车：混合线性注意力整条线被漏了六轮，因为没有强制覆盖清单。）

**四条线是内部论文研究范围**。非论文单独分类统计，但阅读页可以按技术主题对读（硬规则 5）。注意命名消歧：第四条线「工程**方法**」是论文线（评估方法论、实证研究、负面结果）；「工程**实践**」是非论文节。两者不是一回事。

## 信源

**硬规则 3｜主动调用 exa MCP**：skill 一经触发就用 `web_search_exa` 搜、`web_fetch_exa` 拉全文，**不等用户点名**，不用内置 WebSearch 替代。exa 不可用时向用户说明并写入仓库研究笔记，禁止静默降级；不把工具故障写入阅读正文。（翻车：用户被迫连发两条「还是要结合 exa的mcp」。）

**硬规则 4｜多角度搜**：每条线至少 2–3 个不同角度的查询——按 arXiv 时间窗、按会议名（含刚放榜的顶会）、按关键词簇。单角度会整线漏货。

**硬规则 5｜信源分级**：论文、工程博客和 X 的证据地位不同，行文中用「论文实验」「作者博客」「原帖观点」清楚区分。文章可在同一主题下对读，不强制分栏；论文仍是主干，博客与 X 不替代论文证据。（前身是「工业博客一律不进清单」——那条翻车是博客好读好写、混排时会稳定挤掉论文。现在博客进来了，但隔离带必须在，否则重演。）

| 标注 | 信源 | 能进哪 | judgments 里的地位 |
|---|---|---|---|
| 【论文】 | arXiv 预印本、会议论文、workshop 论文 | 主题正文 | 主证据 |
| 【一方博客】 | 模型厂 / 框架方第一方工程博客（Anthropic、OpenAI、DeepSeek、Meta、vLLM 团队…） | 主题正文或继续阅读 | 辅助证据 |
| 【工业博客】 | 大厂系统工程博客（Uber、Netflix、Shopify、Databricks、Character.AI…） | 主题正文或继续阅读 | 辅助证据 |
| 【技术报告】 | 非 arXiv 的 tech report、model / system card、官方评测报告 | 主题正文或继续阅读 | 辅助证据 |
| 【上游变更】 | 开源项目 release notes、RFC、设计文档（vLLM、SGLang、PyTorch、Ray…） | 主题正文或继续阅读 | 辅助证据 |
| 【资讯】 | 有第一方公告页的事件：模型/权重发布、框架大版本、硬件算力、API 定价、政策、模型厂人事融资 | 产品与工具动态 | **禁止作证据** |
| 【快讯】 | X 原帖，没有第一方公告页的 | X 讨论 | **禁止作证据** |

**论文是论证主干**：优先展开全文阅读过的论文。博客补充方法与实现，X 原帖提供作者观点与研究线索，不把帖子当作独立实验。

**硬规则 10｜非论文详条目必过来源核验**：工程实践节的每条**详条目**都必须**读原文**（不许只凭搜索摘要写），并过下面四项；过不了的降为简条目、资讯或直接不收。

1. **第一方还是转述**——转述必须回溯到原始出处并给原始链接。找不到原始出处的不收。
2. **可验证数字 + 上下文**——规模、卡型、版本、测量时间齐不齐？纯定性叙事不进详条目。
3. **时间戳与版本绑定**——写于哪个版本？现在是否已被上游推翻？【上游变更】类尤其要核对当前版本。
4. **营销动机**——是不是自家产品发布稿？是的话必须另外给出可独立复现的方法或数据，否则降级。

核验发现的水分要**写进条目里**，不是自己知道就算。

**硬规则 11｜快讯与资讯只当信号，不当证据**：【快讯】每条写清「原帖说了什么 + 为什么值得跟进 + 发布者与日期 + 原帖链接」，必须是可点开的**原始帖子**，不收二手转述、不收截图转述。【资讯】每条「一句话 + 第一方原始链接 + 来源标注」。两者**不进 judgments、不进 seen-papers**，用途只有一个——提示下次值得定向捞什么。禁止拿它们下任何工程结论。

**硬规则 17｜非论文分层与资讯范围**：工程实践分两层——**详条目**（读原文 + 硬规则 10 四项核验）和**简条目**（【仅摘要】，解释线索与尚缺的核验，不冒充全文验证）。这是在不降质量的前提下加量的唯一办法：详条目的成本是读原文，简条目不读。资讯只收四条线范围内的事，加模型厂 / 推理框架方 / 芯片方的融资、人事、组织变动（它们影响你依赖的东西走向）；消费产品、生成音乐、通用科技新闻不收。**资讯与快讯的边界：有第一方公告页的进资讯，只有 X 帖的进快讯**。（来源：2026-09-10 用户要求，非翻车复盘。）

**硬规则 18｜脚本信源与记录**：每期先跑 `scripts/fetch_sources.py scan`（AIHot + HN + X 账号清单），再用 exa 补。AIHot 的 7 天窗口、来源失败与补搜方式写入 `reports/assets/<日期>/research-notes.md`。向用户如实报告影响交付的缺口，阅读页只链接原始出处，不展示聚合发现、扫描范围或工具说明。

## 溯源

**硬规则 6｜每条必带有用的原始链接**（arXiv/DOI/会议页/原文）。核对目标标题与条目一致，不能只看 HTTP 200。正文、附录、仓库、解说、X、图表和站内目录都要检查。确认 404/删除的链接修正或去掉链接并保留失效说明；403、429、登录墙与网络错误单独标注，不能一概称为失效，也不能称为验证通过。X 优先核对原帖与官方 oEmbed。保存带检查日期的审计记录。没有可靠主来源的条目不作为推荐发布。（翻车：用户明确要过「要有link」，交付的清单一个链接都没有。）

**硬规则 7｜溯源分层 + 强制标注**：
- 摘要级来源写「摘要导读」或在行文说明信息范围；全文材料就地说明实验条件和局限，完整阅读记录留在仓库。
- **重点解读的 2–3 篇论文必须阅读全文**，走下面的检查单，研究笔记存于仓库，影响结论的事实直接写进相关段落。
- 其余条目允许摘要级，但必须明确摘要级范围。

**全文验证检查单**（每项都来自摘要级推荐的实际翻车）：
1. **预印本真实时间线**——arXiv 首次提交是什么时候？是不是旧作换壳/改名重投？（翻车：EcoServe 是 2025 年 4 月旧作；MAP 改名 CAP 重投，数据没刷新。）
2. **数据采集窗口 vs 发表日期**——测量/调研类论文尤其要分开写。（翻车：MAP 12 月发表，数据是 4–11 月采的，读者按发表日期估新鲜度会错一档。）
3. **代码仓库状态**——开源吗？是不是老版本引擎的 source fork？维护活跃吗？（翻车：EcoServe 是 vLLM 0.7.3 fork，生产采用意味着长期背 rebase。）
4. **基线公平性**——对比的基线调过参吗？作者自评吗？
5. **硬件/版本适用边界**——结论绑在什么卡、什么规模、什么互联上？（翻车：EcoServe 的 L20 是中国特供卡，结论对 L40S/A10 不直接可迁移。）

**硬规则 16｜论文附解说**：每篇论文都搜一次解说（`fetch_sources.py lookup` + exa 各一次，封顶），找到合格的附 ≤2 条，找不到只记录在内部笔记，不写占位说明。收作者 thread（标「作者侧」）、第三方人写 thread / 博客、HN 讨论串、中文媒体解读、alphaXiv 人写评论；**不收自动聚合站和 AI 摘要站**。解说**只作导读**：可摘一句解说者观点但要标「解说者观点」，不进 judgments、不进 seen-papers。实践详条目同规则。（来源：2026-09-10 用户要求。）

## 体量（收敛纪律）

**硬规则 8｜金字塔，浮动上限**：
1. 导言直接提出本期技术问题，正文围绕问题选择材料。
2. 重点展开的论文必须经过全文阅读；不以固定推荐标签控制文章结构。
3. 论文详条目默认 **≤8 篇**；顶会放榜等丰收周、或窗口 >10 天的隔周补扫，可扩到 **≤12**，扩容理由留在研究笔记。
4. 工程实践详条目 **≤6**、简条目 **≤8**；资讯 **≤8**；快讯 **≤8**。四个配额各自独立——不占论文名额，也不许借论文的扩容理由跟着扩。
5. 落选池 **≤5 条**，每条只准「标题 + 一句话 + 链接」，保存在仓库研究笔记。
6. 超出的直接不提。漏掉好过淹没。

**排序偏好**：负面结果和校准类论文优先——正向优化会被开源框架吸收，真正省钱的是「这个技术在你的场景下不 work」；且负面结论不受「信息更多 vs 协调更好」混淆的影响，天然更可信。

## 报告格式

**硬规则 15｜博文形态**（2026-09-29 用户更新）：标题和导言围绕具体问题。文章按 3–6 个主题组织，用自然段解释方法、对照、数字和局限，不强制四线标题、固定导读或逐篇字段。内容丰富依靠原始证据与实现细节，不能靠重复摘要扩写。

每期写入 `reports/YYYY-MM-DD.md`，中文。元数据保留 title、description、created、updated 与内部统计。正文形态：

- 两段直接进入技术问题的导言；按本期论证组织 3–6 个有具体含义的二级标题，不沿用「本期一屏 / 本周只读一篇 / 谁该读」模板。
- 将论文写成有因果衔接的自然段，正文就地附原文链接。解释实验设置、数字、失败条件及尚不能推出的结论。摘要级来源在行文或简短出处标记里说明。
- 博客加入实现、复盘与方法背景，X 加入有具体观点的原帖讨论；给作者与原始日期。每期主动补搜两个角度，目标 4–8 条博客、3–6 条 X，质量不足就少收。
- 读者需要的是内容。**正文、首屏、折叠栏和页尾不得出现扫描范围、检索过程、Exa/脚本、skill 名称、核验流程、本次补充数量、生成与归档说明。**「原始扫描范围与核验说明」等后台工作说明完全移出阅读页。实验条件与结果局限则在相关段落直接说明。
- 不为保留旧格式重复总结、堆标签、安排空的资讯或落选池章节。图表只有在解释文章论点时使用；扫描数量与判断编号关系图留在内部资源，不强制嵌入博文。
- 文末可有围绕主题的继续阅读，但不写工作完成记录。完整研究与来源审计存入资源文件或仓库，访问受限的链接仅在入口旁用短说明提示。

**历史更新**：保留原发布日期、扫描窗口、数字与当时证据等级，`updated` 记录编辑日。新增背景阅读标来源原始发布日期；编辑日期写入文章元数据，正文不出现「本次补充」工作说明；晚于历史窗口的内容不得写成当期新闻。不因排版编辑或补充背景阅读推进「上次周扫」，也不重算原始扫描的统计图。补充阅读单独统计；不拿后补博客/X 改写历史判断。网页同时展示发布时间和更新日期。

Pages 使用 `impeccable` 优化版式：正文宽度约 65–75ch、清晰的标题层级、可访问目录、手机阅读、深色模式和前后期导航；设计服务长文阅读。详见 `references/editorial.md`。

## 表述

`ra-人话` 在 Codex 的安装名为 `ra-renhua`（上游显示名保留）。

**硬规则 14｜报告定稿前整篇过 ra-人话 与 humanizer-zh**：先写完整初稿（含附录），再用 `ra-人话` 清理模板句式、用 `humanizer-zh` 复核自然度，然后才落盘。skill 不可用时向用户说明并在仓库记录，手工完成同等编辑；不得把 skill 或生成说明放入阅读页。（来源：2026-09-09 用户要求。）

目标是**好读好懂**，不是好看。

### 保留什么

保留所有事实、数字、来源、日期、专业术语和不确定性；摘要级材料保持清晰标记。固定标签不再强制；改用自然段后，方法、边界和读者适用性仍需讲清。关键数字可少量加粗，不能整段加粗。

### 去什么

按在本报告里的出现频率排，前三条占了绝大多数：

1. **一句里超过一个破折号**。拆成两句。
2. **段落内粗体轰炸**。一段里粗体超过两处，读者就不知道该看哪儿了。只留最该记住的那一处。
3. **金句式收尾**。「它根本不是个量程表」「这一刀最狠」这类可引用的收尾，删掉，把话说完就停。
4. 否定式排比：「不是 X，而是 Y」。直接说 Y。
5. 三段式：为了凑三项而凑的列举，按实际有几项写。
6. 空转连接词：此外、值得注意的是、需要指出的是。

### 怎么检查

改完只读 导言、导读和每个条目的开头，连起来看——**光凭这些，能不能定出这周该读哪几篇**。定不出来就是写虚了，回去改。

## 账本维护

### state/seen-papers.md（去重）

- 周扫**开始前先读账本**，已推过的论文不重发。
- 例外：有实质新信息（中了会、代码开源了、被后续工作反驳）→ 标 **【更新】** 重新进清单，并说明新在哪。
- 每次报告发出后，把新推的论文**追加**进账本（含落选池条目），并更新头部的「上次周扫」日期。
- 去重按内容不只按标题——同一工作可能改名重投（MAP → CAP）。
- **每条必须带 arXiv ID 或会议页链接**。没有 ID/链接，「按内容去重」和【更新】复查都做不到。2026-08-20 前的旧条目缺 ID 属历史欠账，再次遇到该论文时顺手补上。
- **非论文同样去重**：工程实践的详条目和简条目都写进账本末尾的「## 工程实践（非论文）」一节，格式带类型标注（`【一方博客】`等，简条目再加`【仅摘要】`），链接用原文链接。**【资讯】【快讯】不进账本**——半衰期短、噪音大，写进去只会让账本膨胀而挡不住什么（硬规则 11）。解说链接也不进账本（硬规则 16）。
- **折叠策略（防账本膨胀）**：条目满 6 个月后压缩成「`- [日期] 标题 · ID/链接`」单行，判词删掉——判词的价值已沉淀进 judgments.md。每次周扫回写时顺手折叠到期条目。

### state/judgments.md（工程判断账本）

跨来源收敛出来的判断是本雷达最值钱的产出，半衰期比任何单篇论文长。每条判断格式：结论一句话 + 支撑证据（来源列表）+ 适用边界 + 最后更新日期。

周扫时**双向联动**：
- 新论文**印证**某条 → 追加进该条的支撑证据，刷新日期。
- 新论文**反驳**某条 → 该条标 **【存疑】**，并在正文相关论点处明确说明，不许静默改写。
- 新的跨来源模式浮现（≥2 个独立来源指向同一结论，其中至少一篇是论文）→ 新增一条。
- 单篇论文的孤立结论**不进账本**——账本只收跨来源收敛的判断。
- **非论文不能单独把一条判断标【存疑】**——博客/技术报告与论文冲突时，写进该条的适用边界，要标【存疑】得有论文级证据。否则一篇营销稿就能推翻多篇论文收敛出来的结论。

**证据规则**：支撑证据以【论文】为主。非论文（【一方博客】/【工业博客】/【技术报告】/【上游变更】）只能作辅助证据，必须标注类型如「（一方博客，辅助证据）」，且在单条判断的证据里**不得占多数、不得是唯一证据**——每条判断至少要有一篇论文撑着。【资讯】【快讯】和解说一律不得作证据。

**退役规则**：账本只增不删。被彻底反驳的条目标 **【已废弃】** 并保留原文；两条判断收敛合并时保留较小编号，另一条标 **【已并入 Jx】**；J 编号永不复用。

## 定向模式补充

- 使用主题博文结构，只展开该主题相关材料，论文详条目 ≤8；过程笔记与统计仍留在仓库。
- `fetch_sources.py scan` 加 `--topic "<主题>"`。工程实践、资讯、快讯限同主题，配额不变。
- 同样查重、同样写账本、同样过 humanizer-zh、同样落档（文件名 `YYYY-MM-DD-<主题>.md`）。`stats.json` 的 `mode` 填「定向」。
- **定向模式不更新「上次周扫」日期**——该日期只属于四线全幅周扫。周三跑一次定向就把日期推到周三，下次周扫窗口会吞掉周日到周三其他三条线的论文。

## 单篇验证模式补充

- 输入是一篇论文或非论文（链接/标题），产出是围绕该材料的技术博文，说明问题、方法、实验条件、结论与适用性，合格的解说就地附上；检查流程留在仓库。
- **论文**走全文验证检查单五项，必须拉全文，报告标【论文】【全文】；拉不到全文就如实说「仅摘要级验证，可信度打折」。
- **非论文**走硬规则 10 的四项，报告标来源类型；结论只能进 judgments 作辅助证据。
- 验证过的对象记入 seen-papers.md（标注「单篇验证」）；结论与 judgments.md 双向联动。
- **不出图、不写 `stats.json`、不出资讯和快讯**。许可证允许时可以嵌该论文的关键图（硬规则 13）。
- 表述照样过 humanizer-zh；照常落档，文件名 `YYYY-MM-DD-<短名>.md`；不更新「上次周扫」日期。
