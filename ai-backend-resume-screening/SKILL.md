# AI 后端开发工程师 · 简历筛选（从严版）

把「AI 后端开发工程师」岗位 JD 的筛选要点固化成可复用的评估框架，核心是把「进化型 / 重度 AI 编程开发」和「传统纯手写搬砖」区分开——后者是这个岗位最需要过滤掉的人。

判定标准的**唯一权威**是 `references/screening-criteria.md`（六层结构、A/B/C 定档、分值、等级、面试题）；本文件只定义工作流、去重协议与输出契约。标准细节一律以 criteria 为准，不要凭印象加戏。

**判严的四根支柱**（都是从实筛翻车里长出来的，别绕过）：

1. **证据规则**（criteria 第零节）：每一分都要贴得出简历原句，**禁止推断加分**——「在银行做核心系统」＋「会用 Claude Code」推不出「用 AI 做了银行核心系统」。
2. **门槛 ② 三档制**（criteria 第二节）：SDD/TDD 按证据强度分 **A（工具级实证）/ B（流程级描述，总分封顶 85）/ C（淘汰）**。这是本 skill 唯一真正能筛掉人的地方——门槛 ① 因 HR 前置问卷通过率天然极高，分水岭全在这里。
3. **批次自检**（流程第 5 步）：通过率 > 40% 强制复核。整批尺子松掉比单份判错更难自察，也更致命。
4. **跨批次一致性**（「跨批次一致性协议」）：同一个人在不同批次拿到不同判定，是本 skill 出过的最大事故（张天硕 99 分 → 淘汰，无人察觉）。批内判得再准，跨批次自相矛盾一样是废的。

## 使用流程

> **每轮必做（先预扫、再查重、后记录）**：开始前跑 `scripts/prescan.py`，按「跨批次一致性协议」处理查重结果，只对新简历 / 需复筛者往下走；得出结论后把新结果追加进 `checked.md`。

0. **预扫（第一步，不可跳过）**：门槛 ①② 的决定性证据**经常不在 PDF 正文里**，漏读会导致整个目录误判全灭。先跑脚本，把机械活确定化：

   ```bash
   python3 <本 skill 目录>/scripts/prescan.py <简历目录> --out <输出路径>/prescan.md
   ```

   它枚举全部文件（不只 PDF）、提正文、**用 `annots()` 把批注与正文分开**、读 xlsx / docx / csv 补充表、抽身份键（手机后 4 位）、跑关键词命中矩阵、查 checked.md 去重，输出一份报告。读这份报告代替逐份手工提取。**它不做任何判定**——档位、分数、淘汰一律回读原文按 criteria 判。

   - **「⚠️ 提取失败」区块必须逐条处理**：提取到 0 字符不等于「无证据」，手工打开确认。把漏读从模型的失误变成脚本的失误只会更难发现。
   - **证据来源字段由脚本给出**（正文 / 批注 / 补充表 / 无），直接用。为「无」者门槛 ①② 判不满足——不要替他脑补。
   - 报告里的**批注原文**是门槛 ② 定档的主要依据（HR 典型三问：AI 编程代码占比多少？常用哪些 AI 工具？TDD/SDD 具体怎么做？），逐份读完再定档。
   - 某目录候选人**普遍**答了补充三问，说明 HR 已用同样问题预筛过一轮，该目录门槛 ① 通过率天然偏高，分水岭全在门槛 ②，定档要格外克制。
   - 脚本跑不起来（缺 PyMuPDF / openpyxl）时回落手工：`pdftotext -layout` 提正文，`python3` 读 xlsx 的 `xl/sharedStrings.xml`，再全局 grep `SDD|TDD|测试驱动|规格|OpenSpec|spec-kit|Superpower|Kiro|占比|单元测试` 做覆盖率普查。**回落模式下批注无法与正文分离，证据来源字段须人工判读。**

1. **读筛选标准**：`references/screening-criteria.md` 是评估唯一依据；**第零节「证据规则」与第二节「门槛 ② 三档判定」必须完整读完再开筛**。

2. **按层过滤**（顺序即优先级，遇否决项直接停；各层完整条款以 criteria 为准）：
   - **硬门槛**：技术栈须属 全栈 / Python / Java；年龄 ≤ 33（> 33 须触发放宽）；**工龄 ≤ 10（不可放宽）**；**学历本科及以上、非全日制本科可接受（无本科淘汰，不可放宽）**；**深圳候选人须有跨境电商行业经验**。任一不满足即不达标。
   - **两大能力门槛**（任一缺失即淘汰）：① **AI coding 工具实证**——Cursor / Claude Code / Codex 等专业编程工具，「用 AI 写代码」≠「做 AI 应用」；② **SDD/TDD 工程化**——按 criteria 第二节定 **A / B / C 档**：**C 档淘汰，B 档过但总分封顶 85，档位必须写进结论行**。
   - **定档前先校准**：从 `checked.md` 检索「门槛 ① 很强却仍倒在门槛 ②」的历史淘汰案例（检索方式见「去重与 checked.md」），读其淘汰理由；**新候选人的门槛 ② 证据不强于这些先例 → 同样淘汰**。写死的标准会随批次松动，具体的反面样本不会。
   - **优先方向**（加分非门槛）：Agent 应用真实落地 +10（复杂度 / 规模再 +6；仅 Demo / 课程项目不算落地、不得分）；金融 / 电商 × AI 编码；AI 全栈。Agent 加分不能弥补任何门槛缺失，且**前提是简历主体为传统业务后端**——主体即 Agent / RAG / 大模型开发者不适用加分，按画像错位淘汰。
   - **背景与放宽**：第一学历 211 / 985 / 海外名校 → 优先推荐；大厂经历 / 真实强 AI 落地 → 触发放宽，但**只放宽年龄（约 35）与非 211 本科的优先劣势**，不放宽任何否决项。
   - **淘汰信号**：工具降级（只提 ChatGPT 网页版 / 豆包 / Kimi 等聊天工具）/ 排斥 AI 代码上线 / 全传统无 AI / **画像错位（项目主体为 RAG / 大模型应用 / Agent 开发，传统业务后端单薄——岗位要传统项目借助 AI 提效，不是招人做智能体；判「主体」不判关键词，细则见 criteria 第五节）** → 一票否决；信息闭塞 → 降权。

3. **真实性核验**（对通过全部门槛者，按 `references/ai-writing-integrity-check.md`）：输出美化经历风险 🟢低 / 🟡中 / 🔴高。关键二分：**A 情形**（AI 痕迹重但硬细节充分 = 仅润色，不扣分）vs **B 情形**（痕迹重且空泛无凭 = 疑似灌水，扣 12 分 + 面试重点核验）。切勿因文风像 AI 就扣分。

4. **结论与等级**：通过全部门槛者 **60 分起评**，按 criteria「分值建议」逐项加扣得 score（**每笔加分都要贴得出简历原句，贴不出就不给**；B 档封顶 85）；再按「等级评定」依据**项目经验**给 初级开发 / 中级 / 高级（看复杂度、独立负责程度、落地深度，**不由分数倒推**）。结论行统一为 `dir-name-score-等级-门槛②档位`（见「输出格式」）。不要含糊。

5. **批次自检（出结果前必做）**：初筛最大的失效模式不是单份判错，而是**整批尺子松掉**而自己无感：
   - **通过率红线**：> 40% 必须逐一复核所有通过者的门槛 ② 定档，重点找被误判成 B 的 C（能力型自我弱化、测试后置、SDD 概念混淆最常被放过）；**某来源目录通过率 100% 时无条件全员复核**。
   - **反向误杀抽查**：淘汰理由里出现「自我弱化」「已弃用」字样的，逐条回读原句——把「用过之后基于判断弃用某工具」当成能力不足是本 skill 记录在案的误判类型（2026-08-10 任靖宇 / 孟子平），弃用不判 C，只判弃用后有无先行顺序替代。
   - **分数分布**：只有一件事是硬错误——**B 档算出 > 85**（封顶忘了）。**「B 档分数高于个别 A 档」是正常的**，不要据此砍分：A 档只保证有工具实证，若无 Agent 落地、无大厂、无 211，A 档落在 70 上下很常见；实测近半月 25 位 A 档里只有 5 位 ≥86。真正要查的是**每笔加分贴不贴得出原句**，不是分数谁高谁低。
   - **加分抽查**：最高分 2–3 人逐项列出每笔加分的简历原句，列不出的当场扣掉重算。
   - **一致性抽查**：随机取本轮 1 位淘汰者与 1 位通过者比门槛 ② 证据强度；淘汰者证据反而更硬 = 判定不一致，两人都重判。
   - **跨批次冲突**：预扫报告标出「历史判定不一致」的，逐条确认已按跨批次一致性协议处理（缺失继承 / 冲突取最低），并在输出中列明。
   - 自检结论（通过率、是否复核、调整）**写进输出**，不要只在心里过一遍。

6. **需要评分表时**：要独立文件（浏览器打开 / 发 HR）→ 复制 `assets/scoring-rubric.html` 到输出目录交付；要对话内勾选互动 → 用可视化工具渲染 inline 评分表，评分项与判定逻辑和该 HTML 保持一致。

## 去重与 checked.md

`checked.md` 是跨批次累积的本地记录，**两个用途**：① **去重**——已筛过的直接跳过、不复筛不推送；② **校准基线**——历史判定（尤其倒在门槛 ② 的淘汰案例）是本轮定档的锚点。

- **位置**：默认在被筛简历目录的**父目录**（多个批次目录共用一份，跨批次累积）；用户可指定路径。运行时在输出里告知实际路径。
- ⚠️ **文件已达数百 KB 且持续增长，不要整份读入**（会超出单次读取上限）。按需检索：
  - **查重**：预扫脚本已按「来源文件名 + 姓名 + 身份键」查完并把**全部**相关历史行列进报告，直接用。手工兜底：`grep -F "<来源文件名>" checked.md`、`grep "<姓名>" checked.md`、`grep "\[ID:<手机后4位>\]" checked.md`。
  - **校准锚点**：`grep "\[G2:C\]" checked.md | tail -30` 读最近的 C 档淘汰理由（重点看门槛 ① 很强者）；再 `tail -50 checked.md` 感受最近一两轮的整体尺度。**锚点只采样淘汰案例是刻意的**——本岗位放错的代价大于漏掉，不设通过者锚点，不要自作主张加。
- **格式**：Markdown 表格，一人一行（判定结论写在单行内，保证 grep 按行可命中）。文件不存在则创建表头：

  ```markdown
  # 已筛简历记录（checked.md）

  | 筛选日期 | 来源文件 | 姓名 | 城市 | score | 等级 | 判定结论 | 美化风险 | 备注 |
  |---|---|---|---|---|---|---|---|---|
  ```

  档位不单列一列——它随 `[G2:x]` token 写在 `判定结论` 开头，grep 更准（自由文本里「非 A 档」「原判 A 档」这类解释会让按列匹配误命中）。

  - `筛选日期`：`YYYY-MM-DD`；`来源文件`：简历文件名含后缀、原样保留——**主去重键**。
  - **`判定结论`开头必须写两个机器可读 token：`[G2:A|B|C][ID:<手机后4位>] `**（有空格结尾）。
    - `[G2:x]` 是后续批次的校准锚点，**务必如实填写**；倒在学历 / 工龄 / 门槛 ① 红线、门槛 ② 不适用者不写这个 token。
    - `[ID:x]` 是**跨批次认人的唯一可靠键**——手机后 4 位优先，无手机用邮箱前缀（`[ID:zhangsan]`），两者皆缺写 `[ID:?]` 并在备注标「身份键缺失」。城市**不是**可靠身份键：同一人在不同批次的城市字段可能是长沙 / 南京 / 长沙(郑州在职)。
    - 2026-08-06 前的历史行只回填了 `[G2:x]`（126 行），无 `[ID:x]`——旧批次的 PDF 已不在磁盘，无法补。查这些行只能靠姓名。
  - `判定结论`：token 之后**必须写清判定依据的关键原句或工具名**。写「`[G2:C][ID:6126]` 淘汰（门槛②C档：本人称『没有完全按规范去做、先做半成品的 sdd』，且测试后置）」，下一批就有尺子可量；只写「淘汰（门槛②不达标）」等于没留信息。
  - `score` / `等级` / `美化风险` 与结论行一致（未通过者等级写「淘汰」）；`备注`：`复筛` / `更新版` / `继承 <日期> 判定` / `跨批次证据冲突` / `身份键缺失` 等，无则留空。
  - **旧版兼容**：现存 checked.md 的表头是旧版（第 6 列写着「推荐星级」，实际填的是等级值）——**不重建表头**，按现有列序追加即可。
- **筛选后**：新筛 / 复筛者各**追加一行**（只追加、不改写历史行，表头唯一）；跳过者不写行；输出末尾附「去重汇总」。

### 跨批次一致性协议（筛选前必走）

同一个人反复被不同 HR 投递是常态，而**同一人在不同批次拿到不同判定**是本 skill 出过的最大事故：张天硕 2026-07-24 三份记录 99 / 95 / 95 分「推荐面试」，07-29 与 08-05 两次判 0 分淘汰，无人察觉。原因是三个批次的证据来源不同（补充表 / 本人批注 / 什么都没有），而旧规则只按文件名去重、从不对账。

```
预扫报告给出查重结果 →
├ 无任何历史记录 ────────────────────────→ 新筛
├ 身份键命中（或姓名命中且人工确认同一人）→
│   ├ 本轮无批注、无补充表（证据缺失）→ 跳过，不推送；不重判，**继承历史最强档位**
│   │                                    备注写「继承 <日期> 判定，本轮无补充材料」
│   └ 本轮有批注 / 补充表 → 与历史档位比对（预扫已自动标出「历史判定不一致」）
│         ├ 不矛盾 → 照常跳过，不推送
│         └ 矛盾  → **升级完整复筛**：取历史与本轮中的**最低档**，标双重红旗，
│                    结论行注明「跨批次证据冲突」，面试重点核验
└ 姓名命中但身份键无法确认（历史行无 ID、本份无手机无邮箱）→ 标「疑似同一人，身份键缺失」，
   按新筛走完流程，结论行点明与哪条历史记录疑似同人，由人工定夺
```

- **为什么「缺失」和「冲突」要分开**：本轮没证据通常是这个 HR 没发问卷，**人没变差**，重判等于因流程噪声误杀；本轮证据与历史打架则是真实性问题——一个人不可能既讲得出 OpenSpec 红绿重构，又把 SDD 说成「AI 编写代码规范」。
- **取最低档不是保守，是止损**：冲突意味着至少有一次判定建立在不实陈述上，而你无法知道是哪一次。
- 跨批次冲突**必须写进输出**（不只写进 checked.md），格式见「去重汇总」。
- **标准换版**：收紧标准后，旧版「通过者」默认仍按已筛过跳过，用户明确要求才按新门槛复核；但**至少把最近一轮记录按新标准回测并就地修正**（判定结论注明「【新标准回测】原 X 分 → 现 Y 分 / 改判淘汰」及理由），否则下一批拿旧尺子当锚点会被带偏。**放宽标准后反向同理**：历史记录里**仅因旧门槛被淘汰**者（如 2026-08-21 放宽前的「年龄 31–33」「专升本 / 非全日制本科」），查重命中时不继承淘汰判定，按新标准复筛并注明「【放宽复筛】」。

## 底线速查（完整规则以 criteria 为准；以下任何情况下不得违反）

- **一票否决、不可放宽**：工龄 > 10 年；无本科学历（最高学历专科及以下；专升本 / 非全日制本科算过门槛，不否决）；深圳候选人无跨境电商经验；门槛 ① 无专业工具实证；门槛 ② C 档；工具降级 / 排斥上线 / 全传统无 AI；**画像错位（项目主体为 RAG / 大模型应用 / Agent 开发）**。门槛证据须在简历上可指认，**不留到面试再问**。
- **放宽机制**（大厂 / 强 AI 落地）只作用于「年龄上限 → 约 35」与「非 211 本科的优先劣势」两项，其余一概不放宽。
- **证据规则**：无原句不给分；禁止推断加分；禁止一证多用；自报占比无正文互证 → 强度加分减半、不触发放宽；候选人**能力型**自我弱化（「只是尝试过」「半成品」「了解过」）按弱化后水平判，但**「用过一段时间后基于判断弃用」不是自我弱化**（那是工具判断力），不得据此降档——改判弃用后有无先行顺序的替代。
- **两个维度不可互替**：「用 AI 写代码」（门槛 ①）≠「做 Agent 应用」（加分项）；只有 Agent 经历救不了门槛 ①。**Agent / RAG / 大模型开发只能当加分项**——岗位要的是传统项目借助 AI 提效，不是招人做智能体；此类经历成为简历主体即画像错位淘汰，判「主体」不判关键词。
- **AI 灌水 ≠ AI 痕迹**：高 AI 痕迹＋硬细节充分（A 情形）**不得扣分**，常是顶尖打分者；🔴 高＋门槛 ① 实证单薄、靠 Agent 经历撑简历 = 双重红旗，降边缘 / 淘汰、面试从严。
- **跨批次**：本轮证据缺失 → 继承历史最强档位，不重判；本轮证据与历史冲突 → 取最低档 + 双重红旗。两者都必须写进输出，不能只记进 checked.md。
- **推荐线**：score 必须 > 60（裸 60 不推）；等级按项目经验评，不由分数倒推。

## 输出格式

每位候选人固定 5 个字段：`dir`、`name`、`score`、`等级`、`门槛②档位`，结论行 **`dir-name-score-等级-门槛②档位`**。档位必须可见——它是区分度最高的字段：同为「推荐面试」，A 档拿得出工具实证、B 档只有口头承诺，面试官要一眼看出火力压在谁身上。

- **dir**：来源文件夹 / 文件名，原样保留便于追溯；**name**：正文解析的真实姓名（解析不到写「姓名未识别」）；**score**：整数，未通过门槛者不计分（明细记 0）；**等级**：高级 / 中级 / 初级开发，未通过者记 `淘汰`（只入明细与 checked.md，不入主推荐表）。
- **推荐门槛**：主推荐表只列「通过全部门槛且 score > 60」者；裸 60 分、被扣分拉到 ≤ 60 者、未过门槛者仅在明细中列出。用户明确要求「显示全部」才展示所有人。
- **单份**：一行结论行；dir 自身常含连字符，字段间用带空格的 ` - ` 分隔以免混淆：`AI开发-张三-长沙 - 张三 - 92 - 高级 - A档`。
- **批量**：主推荐表**先按门槛 ② 档位分区（A 档一区、B 档一区），区内再按 score 降序**（同分：等级高前、第一学历 211+ 前），附「门槛②证据」列写关键工具名或原句摘要，让面试官不必回翻简历：

  **A 档 · 有工具级实证**

  | dir（目录 / 文件） | name（姓名） | score（得分） | 等级 | 门槛②证据 |
  |---|---|---|---|---|
  | AI开发-张三-长沙 | 张三 | 92 | 高级 | OpenSpec `/opsx:propose` 固化规范 + Superpowers 红绿重构 |
  | AI开发-王五-长沙 | 王五 | 76 | 中级 | spec-kit 产出接口契约，AI 按契约生成实现 |

  **B 档 · 仅流程级描述（⚠️ 无工具实证）**

  | dir（目录 / 文件） | name（姓名） | score（得分） | 等级 | 门槛②证据 |
  |---|---|---|---|---|
  | AI开发-李四-北京 | 李四 | 84 | 中级 | 「先写测试再让 AI 写代码」，无工具名、无项目级证据 |

  **不要跨区按分数混排**：B 档 85 分排在 A 档 76 分之上会让面试官误以为火力更猛，而两人的差别恰恰是「拿得出工具产出物」与「只有口头承诺」。分区把档位与分数两种信息都摆出来，先约谁由面试官定。

- **B 档一律附**：「⚠️ 面试第 2 题（SDD/TDD 用什么工具、流程怎么走）答崩即按灌水处理，该项过门槛的依据作废」。
- **明细**：需要时在结论行 / 表格下补关键命中项与缺口，并给美化风险（🟢 / 🟡 / 🔴，可附 AI 痕迹分 0–100）——🔴 高或双重红旗者标「面试重点核验真实性」；涉及年龄 > 33、工龄临界、第一学历非 211、是否触发放宽时，须在明细点明。

## 输出风格

- 中文输出，结论明确、可执行；多项判定先给总结论，再列关键命中项与缺口。
- 不要在没有依据时编造候选人经历；简历没写到的，就说「简历未体现」。
