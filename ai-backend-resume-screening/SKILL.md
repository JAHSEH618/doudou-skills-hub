# AI 后端开发工程师 · 简历筛选（从严版）

这个 skill 把一份「AI 后端开发工程师」岗位 JD 的筛选要点固化成一套可复用的评估框架。核心目标是把「进化型 / 重度 AI 编程开发」和「传统纯手写搬砖」区分开 —— 后者是这个岗位最需要过滤掉的人。本版为**提高门槛后的从严标准**：AI coding 工具、SDD/TDD 两项为**必过门槛**（缺一即淘汰），Agent 应用落地为**最高优先加分项**（真实落地 +10，仅 Demo 不算）；**工龄 > 10 年、第一学历专科直接淘汰**；通过者按项目经验评定 **初级开发 / 中级 / 高级**，结论行以 `dir-name-score-等级` 输出。同时内置一层基于 `humanizer-zh` 的真实性核验，揪出「用 AI 美化 / 编造经历」的候选人。

## 何时使用

- 用户给一份简历，问「这个人符不符合 / 能不能进面 / 帮我打个分」
- 用户要批量初筛、要一份可勾选的评分表或面试评分卡
- 用户要对通过初筛的候选人按项目经验评定等级（初级开发 / 中级 / 高级）
- 用户在讨论该岗位的筛选维度（AI 工具实证、Agent 落地、SDD/TDD、金融电商经验、AI 全栈等）
- 用户想核验简历是否被 AI 灌水 / 美化夸大，要分辨「真做过 + AI 润色」与「用 AI 编造经历」
- 用户批量 / 跨批次初筛，希望**不要重复推送已经筛过的简历或候选人**（去重，记录到本地 `checked.md`）

## 使用流程

> **每轮必做（先查重、后记录）**：开始前先按下文「去重与 checked.md」读取本地 `checked.md`、跳过已筛过的简历，只对「新简历 / 更新版」往下走；得出结论后把新结果追加进 `checked.md`。

1. **先读筛选标准**：阅读 `references/screening-criteria.md`，了解六层结构和每层的判定逻辑。这是评估的唯一依据，不要凭印象加戏。

2. **按层过滤**（顺序很重要，遇到否决项直接停）：
   - 先看**硬门槛**：任一项不满足 → 直接判不达标，分数再高也不进面。技术栈须属于 **全栈 / 会 Python / 会 Java** 之一；**年龄 ≤ 30 岁**（> 30 须触发「放宽机制」）；**工龄 ≤ 10 年**（> 10 一票否决，**不可放宽**）；**学历本科及以上**（第一学历专科及以下一票否决，**不可放宽**）。
   - 再看**两大能力门槛**（必过，任一缺失 → 直接淘汰）：① **AI coding 工具实证**——必须用 Cursor / Claude Code / Codex 等专业编程工具写代码，注意「用 AI 写代码」≠「做 AI 应用」；② **SDD/TDD 工程化**——对 SDD/TDD 有了解且使用过相关工具 / skill（OpenSpec、Superpowers、spec-kit 等）。两项都要简历上有**可指认证据**，只字未提即淘汰。
   - 再看**优先方向**（加分非门槛）：① **Agent 应用落地**（最高优先加分 +10，复杂度 / 规模再 +6）——开发过 AI Agent 应用且真实落地（生产 / 真实用户在用），仅 Demo / 课程项目不算落地、不得分，且不能替代门槛 ①；② 金融 / 电商行业 AI 编程经验；③ AI 全栈能力。命中越多越优先，没命中也不淘汰。
   - 再看**背景项**：**第一学历 211 / 985 / 海外名校 → 优先推荐**（同等条件排前、加分）；**大厂经历 / 真实强 AI 落地经验 → 触发「放宽机制」**——只放宽年龄上限（约 35）与非 211 本科的优先劣势，**不放宽**工龄、专科底线和两大能力门槛。
   - 最后看**加分项**与**淘汰信号**：工具降级 / 排斥上线 / 全传统无 AI → 一票否决；信息闭塞 → 降权。

3. **AI 灌水 / 真实性核验**（基于 `humanizer-zh`）：对通过全部门槛的候选人，按 `references/ai-writing-integrity-check.md` 检测简历的「AI 撰写痕迹」并给出 **美化经历风险**（🟢低 / 🟡中 / 🔴高）。关键是区分 **A 情形（AI 痕迹重但硬细节充分 = 仅润色，不扣分）** 与 **B 情形（AI 痕迹重且空泛无凭 = 疑似灌水，扣 12 分 + 面试重点核验）**。切勿因简历文风像 AI 就扣分——要看痕迹背后有没有可验证的真材实料。

4. **给出结论与等级**：用 `references/screening-criteria.md` 的「判定逻辑」得出结论；通过全部门槛者从 **60 分起评**，按强度 / 加分 / 扣分算出 score，并按「等级评定」依据**项目经验**给 **初级开发 / 中级 / 高级**（看复杂度、独立负责程度、落地深度，不由分数倒推）。每位候选人的结论须用统一的「结论行」格式 `dir-name-score-等级` 输出（见下文「输出格式」）。不要含糊。

5. **需要评分表时**：
   - 想要**能直接在浏览器打开 / 发给 HR** 的独立文件 → 把 `assets/scoring-rubric.html` 复制到输出目录并交付。
   - 想要**在对话里直接勾选互动** → 用可视化工具把同样的逻辑渲染成 inline 评分表（评分项、分值、实时总分、录用建议判定逻辑都和 `assets/scoring-rubric.html` 保持一致）。

## 去重与 checked.md（避免重复推送已筛过的简历）

批量 / 跨批次筛选时，用一个本地 `checked.md` 记录已筛过的简历；**每轮开始前先读它**，已记录的直接跳过、不再重复打分或推送；筛完把新结果追加进去。

### checked.md 文件

- **位置**：筛选工作目录下的 `checked.md`（本地、纯文本，可直接打开查看）。默认放在被筛简历目录的**父目录**，以**跨批次累积**（如 `AI开发-0609/`、`AI开发-0610/` 共用同一个 `checked.md`，0609 筛过的人在 0610 不再重复推送）；用户也可指定路径。运行时确定实际路径并在输出里告知。
- **格式**：Markdown 表格。文件不存在时先写表头：

  ```markdown
  # 已筛简历记录（checked.md）

  | 筛选日期 | 来源文件 | 姓名 | 城市 | score | 等级 | 判定结论 | 美化风险 | 备注 |
  |---|---|---|---|---|---|---|---|---|
  ```

- **字段**：
  - `筛选日期`：本次运行日期 `YYYY-MM-DD`。
  - `来源文件`：简历文件名（含后缀），原样保留 —— **主去重键**。
  - `姓名` / `城市`：从文件名（形如 `AI开发-{姓名}-{城市}.pdf`）或正文解析 —— **辅助去重键**，识别「同一人换文件名重投」。
  - `score` / `等级` / `判定结论` / `美化风险`：与本次「结论行」一致（未通过者 `等级` 写「淘汰」）；checked.md 同时充当**累积结果存档**，回看历史结论无需重筛。
  - `备注`：如 `复筛`、`更新版`，无则留空。
- **旧版兼容**：历史 `checked.md` 表头若仍是旧版「推荐星级」列，不必重建表头——追加行时在该列写等级值即可。

### 筛选前 —— 先查 checked.md

1. 文件不存在 → 全部按新简历处理；筛完后**创建** `checked.md`。
2. 读取 `checked.md`，逐份比对输入简历：
   - **来源文件名已在表中** → 判为「**已筛过**」，**跳过**：不重新评估、不纳入推送结果，仅计入「本次跳过」清单。
   - **姓名+城市已在表中、但文件名不同** → 疑似「同一人更新版 / 重投」，默认**重新筛选**并在 `备注` 标 `复筛`（追加新行，旧行保留作历史）；用户若明确「任何筛过的人都不再推送」，则同样跳过。
   - 都不在表中 → 新简历，进入上方分层评估。
3. **标准换版重筛**：本 skill 升级为从严版后，旧版筛过的「通过者」若需按新门槛复核，由用户明确说明；默认仍按已筛过跳过。

> 某份简历更新后需要重筛，可让用户说明，或手动删除 / 修改其在 `checked.md` 中的行。

### 筛选后 —— 追加到 checked.md

- 把**本次新筛 / 复筛**候选人的「结论行」各**追加一行**到 `checked.md`（只追加、不改写历史行，表头保持唯一）。
- 被跳过的简历不写新行。
- 在输出末尾给出去重汇总（见「输出格式 · 去重汇总」）。

## 关键判定原则（务必坚持）

- **硬门槛是闸门**：缺一项即不达标，与总分无关；技术栈聚焦 **全栈 / 会 Python / 会 Java**。
- **工龄 ≤ 10 年是一票否决、不可放宽**：工龄超过 10 年直接淘汰，大厂 / 强 AI 落地也救不回来。
- **学历底线是本科，专科直接淘汰（不可放宽）**：第一学历专科（大专）及以下 → 淘汰（专升本按第一学历 = 专科处理）；**第一学历 211 / 985 / 海外名校 → 优先推荐**；非 211 本科不淘汰，可被放宽抵消优先劣势。
- **年龄 ≤ 30 为门槛、可放宽至约 35**（大厂 / 强 AI 落地），但放宽不解除「工龄 ≤ 10」与「本科底线」。
- **两大能力门槛缺一不可**：① AI coding 工具实证 ② SDD/TDD 工程化（OpenSpec / Superpowers / spec-kit 等）。简历上无可指认证据即淘汰，**不留到面试再问**。
- **Agent 应用落地是最高优先加分、不是门槛**：真实落地（生产 / 真实用户在用）+10，复杂度 / 规模再 +6；仅 Demo / 课程项目 / 纯调 API 聊天页不算落地、不得分。没有 Agent 经历只是少这份加分，不淘汰。
- **「用 AI 写代码」与「做 Agent 应用」是两个维度、不可互替**：只有 Agent 经历而无专业 coding 工具实证 → 仍按门槛 ① 淘汰；Agent 加分不能弥补任何门槛缺失。
- **SDD/TDD 已是硬门槛**（从严版关键变化）：对 SDD/TDD 无了解、未用过相关工具 / skill → 淘汰；方法论深度（完整工作流 + 提效数据）另有加分。
- **工具降级要警惕**：候选人只提 ChatGPT 网页版 / 豆包 / Kimi / 文心一言等网页聊天工具，而非 Cursor/Claude Code/Codex 等专业编程工具 → 一票否决。
- **不敢上生产 = 不合格**：「AI 代码 Bug 多，只敢本地测试不敢上线」不符合「能驾驭 AI 生成生产代码」的要求。
- **放宽只放背景**：大厂 / 强 AI 落地仅放宽**年龄、非 211 优先劣势**；对工龄 > 10、专科、两大能力门槛、淘汰信号、🔴 灌水等核心否决项一律不放宽。
- **通过者按项目经验评级**：初级开发 / 中级 / 高级，依据项目复杂度、独立负责程度、落地深度；年限仅参考，**不由 score 倒推等级**。
- **AI 灌水 ≠ AI 痕迹**：用 AI 写简历不扣分；要过滤的是**用 AI 编造 / 夸大经历**。高 AI 痕迹 + 充分可验证硬细节（真系统名 / GitHub / 精确指标）属「仅润色」，**不得降分**（常是顶尖打分者）；高 AI 痕迹 + 空泛无凭才扣分。详见 `references/ai-writing-integrity-check.md`。
- **双重红旗**：美化风险 🔴 高 且「用 AI 写代码」实证单薄、主要靠「做 AI 应用 / Agent」经历撑简历 → 可信度极低，降到边缘 / 淘汰候选、面试从严。
- **分值仅为初始建议**：通过全部门槛 60 分起评、上限 100，**推荐须超过 60 分**（裸 60 不推）；团队可按松紧调整阈值，但分层逻辑和否决规则应保持。
- **先查 checked.md、再评估**：每轮筛选先读本地 `checked.md`，已记录的简历直接跳过、不重复推送；新筛 / 复筛结论追加回 `checked.md`。详见「去重与 checked.md」。

## 输出格式

每位候选人固定输出 **4 个字段**：`dir`、`name`、`score`、`等级`，即结论行格式 **`dir-name-score-等级`**。

**推荐门槛**：默认只推荐 **通过全部门槛且 score 超过 60 分（> 60，即 ≥ 61）** 的候选人；未通过门槛者、恰好 60 分者（仅裸过门槛、无任何加分）以及被扣分拉到 60 及以下者**仅在明细汇总中列出**，不纳入主推荐表。用户明确要求「显示全部」时才展示所有候选人。

**批量**：主推荐表按 `score` 从高到低排序（同分时等级高者前、第一学历 211+ 者前）：

| dir（目录 / 文件） | name（姓名） | score（得分） | 等级 |
|---|---|---|---|
| AI开发-张三-长沙 | 张三 | 86 | 高级 |
| AI开发-李四-北京 | 李四 | 72 | 中级 |

**单份**：一行 `dir-name-score-等级`；dir 自身常含连字符，字段间用带空格的 ` - ` 分隔以免混淆，例：`AI开发-张三-长沙 - 张三 - 86 - 高级`。

字段说明：
- **dir**：简历来源文件夹 / 文件名，原样保留，便于追溯。
- **name**：从简历正文解析的真实中文姓名；解析不到写「姓名未识别」。
- **score**：按 `references/screening-criteria.md` 的「分值建议」算出的总分（整数）：通过全部门槛 60 分起评 ± 加扣分，上限 100；未通过门槛者不计分（明细中记 0）。
- **等级**：`高级` / `中级` / `初级开发`，仅对通过全部门槛者评定（规则见 criteria「等级评定」，依据项目经验）；未通过者记 `淘汰`，只出现在明细与 checked.md，不入主推荐表。

**明细**：需要时在表格 / 结论行下方补充关键命中项与缺口，并给出**美化风险**（🟢低 / 🟡中 / 🔴高，可附 AI 痕迹分 0–100）——🔴 高或双重红旗者须标注「面试重点核验真实性」。涉及**年龄 > 30、工龄临界、第一学历非 211、是否触发放宽（大厂 / 强 AI 落地）**时，须在明细里点明。

### 去重汇总（批量筛选时附在结果表后）

批量筛选须在结果表下方附一行去重汇总，并列出被跳过者，让用户清楚「本次推送的都是新简历」：

```
本次共 5 份：新筛 3 · 复筛 1 · 跳过 1（已筛过）。checked.md：<路径>/checked.md
跳过（已筛过）：AI开发-张三-长沙.pdf（张三）— 2026-06-08 已筛过，86 分 · 高级
```

## 输出风格

- 中文输出，结论明确、可执行。
- 涉及多项判定时，先给总结论，再列关键命中项与缺口。
- 不要在没有依据时编造候选人经历；简历没写到的，就说「简历未体现」。
